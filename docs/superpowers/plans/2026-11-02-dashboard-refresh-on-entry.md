# 대시보드 조회 시 원본 갱신 구현 계획

**목표:** 팀 대시보드 진입·재진입·기간 변경·새로고침마다 Mantis 변경분을 수집한 뒤 집계한다.

**설계:** 기존 원자적 전체 저장본과 증분 수집을 재사용한다. 최초 응답은 최대 8초 동안 수집 완료를 기다린다. 더 걸리면 기존 수치를 갱신 중으로 보여 주고 완료 여부만 조회한다. 완료 확인은 새로운 수집을 시작하지 않는다. 실패하면 저장본과 기준 시각을 유지하면서 실패를 표시한다. 동시 조회는 기존 수집 스레드를 공유한다.

매번 전체 3만 건을 다시 받는 방식은 불필요하게 느리므로 사용하지 않는다. 기존 10분 수집 주기는 화면을 열지 않을 때의 보조 갱신으로 유지한다. 집계 필터·공용 계정 범위·인증은 유지한다.

**실행:** 메인 에이전트가 현재 작업 공간에서 직접 수정·검증한다. AGENTS.md에 따라 서브에이전트를 사용하지 않는다.

## 작업

- [x] 실제 임시 저장본으로 진입 후 신규 이슈 반영, 수집 지연, 수집 실패 보존을 검증하는 실패 테스트 작성·실행.
- [x] `workspace_data.load_complete_workspace`에 선택적 대기와 갱신 전 기준 시각/실패 여부를 추가하고 대시보드 요청에서만 대기.
- [x] 브라우저 진입 시 캐시 재사용을 없애고 갱신 요청, 기간 변경도 갱신 요청. 완료 확인은 읽기만 수행. 늦은 실패도 기준 시각으로 판별.
- [x] 브라우저 회귀 테스트로 재진입, 동시 진입, 완료 확인의 무한 수집 방지, 지연 후 실패·성공을 확인.
- [x] 프로젝트 검사 및 변경 사항 자체 리뷰. 배포 전후 동작 차이와 검증 범위를 보고.

## 검토 항목

- 오래된 미종료 이슈가 최근 일부 조회로 대체되지 않는가.
- 수집 스레드 시작과 파일 잠금 사이에도 갱신 중임을 표시하는가.
- 완료 확인이 다시 수집을 시작하지 않는가.
- 수집 실패 후 이전 값을 최신으로 표시하지 않는가.
- 동시에 들어온 요청이 같은 수집을 공유하는가.

## 검증 결과

- 신규 backend 테스트 3건은 기존 코드에서 실패한 뒤 수정 후 통과했다.
- frontend 진입/재진입/기간 변경/완료 확인/실패 표시는 기존 코드에서 7건 실패한 뒤 수정 후 통과했다. 파일 교체 후 잠금만 남은 경계도 성공으로 확인했다.
- `assistant_web/scripts/check.sh tests compile shell ruff mypy`: 테스트 2,812개, 커버리지 90%, 번들 일치/컴파일/셸/ruff/mypy 모두 통과.
- 실제 Mantis와 로컬 전체 저장본을 사용한 두 번의 연속 조회에서 매번 수집 시각 변경, 잔여 50건(HTS 38·MTS 12), 수집 실패/미완료 없음. 각각 8.215초·8.257초.
- 실제 검증 자료: `assistant_web/runtime/dashboard-refresh-on-entry-20261102/live-verification.json`.
- AGENTS.md에 따라 메인 에이전트가 직접 변경 사항을 검토했다. 운영 배포와 커밋은 수행하지 않았다.
