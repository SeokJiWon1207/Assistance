# Mantis 구간 검색과 재순위화 구현 계획

> 실행: 이 채팅에서 직접 구현하고 테스트 후 독립 코드 검토를 수행한다.

## 목표와 설계

사용자가 승인한 긴 이슈 분할과 검색 결합·재순위화를 적용한다. 집계, 조건 해석,
기존 Chroma 문서 형식은 유지한다. 원본 전체 저장본에서 본문·원인·조치·각 노트를
1,200자, 150자 겹침 구간으로 분리한 별도 SQLite FTS5 인덱스를 만든다.
한국어는 단어와 글자 두 개 단위 검색어를 함께 색인한다.

기존 이슈 벡터 검색과 구간 BM25 검색의 순위를 RRF로 결합한다. 상위 후보의
실제 구간을 기존 로컬 bge-m3로 임베딩하고 질문과의 코사인 유사도로 재순위화한다.
이는 전용 교차 인코더가 아니라 구간 임베딩 재순위화다. 전체 31,241개 이슈의 모든
구간을 한 번에 다시 임베딩하는 비용 없이, 뒤쪽 근거를 키워드 후보로 복구한다.
동의어만 존재하는 뒤쪽 구간의 최초 검색 누락까지 모두 해결한다고 주장하지 않는다.

키워드 후보에는 최신 원본의 기존 issue_matches_constraints를 적용한 다음 후보 수를
제한한다. 이슈별 중복은 제거한다. 후보 원본과 인덱스의 세대·연결 식별자를 확인하고,
인덱스 미준비·갱신 중에는 기존 검색으로 폴백한다. 인덱스는 임시 파일에 생성한 뒤
원자 교체한다. 요청에서 대규모 색인을 동기 실행하지 않고 백그라운드로 준비한다.
벡터 서비스 장애 시 구간 BM25/RRF 결과를 사용하고 실제 검색 방식을 메타데이터에 남긴다.

## 제약

- Python 3.12 및 assistant_web/.venv/bin/python 사용, 추가 의존성 없음.
- 원문은 기존 로컬 임베딩 서비스에만 전송한다. 비밀값을 출력하거나 저장하지 않는다.
- 집계용 저장본과 기존 Chroma DB는 변경하지 않는다.
- 진행 중인 Notion·문서 변경을 수정하거나 커밋하지 않는다.
- 정확도 수치는 합성 회귀와 실제 저장본 평가를 분리해 보고한다.

## 검토 초점

1. 분할 때문에 집계·단건 조회가 중복되거나 기존 Chroma SQL을 오염시키지 않는가.
2. 다른 고객사·담당자·매체·상태가 상위 후보를 차지해 필터 안 결과를 밀어내지 않는가.
3. 데이터 갱신·연결 변경 중 과거 원문을 새 근거처럼 전달하지 않는가.
4. 취소나 모델 장애를 정확도 향상 또는 정상 의미 검색으로 오인하지 않는가.
5. 평가의 기대 이슈는 결과 코드와 독립적으로 고정하며 답변 정확도 전체로 일반화하지 않는가.

## 실행 기록

- 시작 전 tests: 전체 성공, 커버리지 87%. 기존 사용자 변경 보존.
- 이전 대화의 설계와 이번 구현 요청을 승인 범위로 사용한다. 추가 승인 절차를 반복하지 않는다.
- 초기 전체 구축 도중 원본의 갱신 시각이 바뀌므로 VERSION=2 이슈 해시 증분 구축을
  적용했다. 31,241개 이슈 / 198,351개 구간 구축 완료, 이후 변경 없는 갱신에서
  재분할 이슈 0개를 확인했다.
- 미리 고정한 실제 질문 16개: Hit@5 기존 10/16, 결합 15/16, 재순위화 16/16.
  기존 Chroma와 최신 원본의 포괄성 차이를 포함하며 전체 답변 정확도로 일반화하지 않는다.
- 고정 저장본의 집계·조건 20문항은 기능 on/off 모두 통과하고 동일 결과였다.
  점검 도구의 오래된 매체·기본 팀 정답 기준만 현재 계약에 맞췄다.
- 최종 전체 check.sh 통과: 1,629개 테스트, 커버리지 87%, mypy 125파일 성공.
  독립 검토 지적 2건 수정과 회귀 테스트 후 재검토 완료.
- 상세 설계·재현·측정 한계: assistant_web/docs/MANTIS_HYBRID_RETRIEVAL.md.
