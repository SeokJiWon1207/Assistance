# 초기 준비 및 원본 검색 지연 개선 검증

사용자 요청: 검색 정확도와 메모리 보호를 유지하면서 첫 요청 27초, 동시 요청 25초의 초기 준비와 전체 원본 검색 비용을 줄이고 운영 배포 후 같은 질문을 검증한다.

## 구현 및 완료 조건

- [x] 프로젝트·담당자·보고자 목록을 작은 영속 카탈로그에 저장한다. DB/WAL 세대가 변경되면 새 목록을 만들며 실패·손상 시 원래 조회로 복구한다.
- [x] 배포 사전 검사와 스냅샷 교체 시 카탈로그를 준비한다.
- [x] 전체 원본과 같은 SQLite 세대에 정규화 검색 텍스트를 저장한다. SQL로 후보를 선별하고 기존 원본 검증을 적용한다. 검색어 AND 및 동의어 OR 의미를 유지한다.
- [x] 전체·증분 동기화와 함께 검색 텍스트를 갱신한다. 원본의 외부 변경, 미완성·구형 인덱스는 기존 전체 검색으로 복구한다.
- [x] 요청별 스트리밍, 취소·시간 제한과 동시 요청 제한을 유지한다. 같은 SQLite 연결의 겹친 커서 실행은 잠금으로 보호한다.
- [x] 최신 운영 버전의 검색 근거 및 추가 정보 검색 변경을 보존한다.
- [x] 운영 배포, 실제 화면 답변, 응답 시간, 메모리를 검증한다.

## 검증

최종 운영 코드 조합으로 Python 테스트 1,135개 통과(13.632초). Ruff, mypy 110개 파일, 배포 셸 구문 검사 통과. 공유 연결 병렬 검토에서 36,000회 조회의 중복·누락 없음.

실제 원본 31,233건의 8개 질의에서 기존 전체 검색과 새 경로의 결과 객체(검색 조건, 건수, 순서, 본문 및 근거)가 일치했다. 대상 질의의 로컬 원본 검색은 5.746초에서 0.134초로 줄었다. 넓은 검색 또는 검색어 없는 질의는 모든 원본을 읽어야 할 수 있어 같은 개선 폭을 보장하지 않는다.

## 운영 측정

질문: `HTS에서 VB스크립트를 자바스크립트로 교체 문의 들어온거 있어?`

Chrome의 새 대화에서 회사 모델로 전송했다. 시간은 감사 로그의 `beforeFinalizationMs + verificationAndFormattingMs`로 산출한 서버 답변 처리 시간이며 브라우저 네트워크·렌더링 시간은 제외한다.

| 요청 | 이전 측정 | 배포 후 |
| --- | ---: | ---: |
| 서비스 시작 후 첫 질문 | 27.019초 | 2.789초 |
| 반복 질문 | 12.408초 | 2.217초 |
| 동시 요청 1 | 25.407초 | 2.294초 |
| 동시 요청 2 | 25.508초 | 2.336초 |

첫 질문의 초기 준비는 14.341초 → 0.385초, 검색은 10.574초 → 0.284초. 남은 주요 비용은 모델을 통한 조건 해석(약 1.9~2.1초)이다.

답변은 HTS와 `VB스크립트`, `자바스크립트`, `교체`를 모두 유지하며, 전체 저장본 31,233건에서 일치 0건을 안내했다. 검색 완료·스냅샷 완료와 전체 필터 적용을 감사 로그로 확인했다. 네 건의 성공 답변이 모두 같은 결과였고 두 동시 요청은 HTTP 200, 초과 요청은 429였다.

0.25초 간격 메모리 측정: 단일 요청 구간 최고 RSS 711.11MiB, 동시 요청 최고 RSS 713.96MiB. 동시 요청 시작 709.70MiB에서 최고 약 4.26MiB 증가했다. 서버 가용 메모리 최소 730.62MiB. 서비스 cgroup 최고 1,157.80MiB에는 회수 가능한 파일 캐시 최대 455.84MiB가 포함된다. OOM·OOM kill·서비스 재시작 모두 0회.

이는 위 요청과 동시성에서 관측한 결과이며 모든 요청 부하에 대한 무제한 보장은 아니다. 원본 검색용 저장 데이터는 디스크에 두며 요청마다 전체 본문을 메모리에 올리지 않는다.
