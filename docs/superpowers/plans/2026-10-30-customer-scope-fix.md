# 고객사 범위 보존 구현 계획

사용자가 승인한 고객사 누락·부분 일치 수정, Gemini 재해석, 제목·본문·정상 문서 보존을 직접 구현한다. 서브에이전트와 커밋은 사용하지 않는다. 기존 작업 트리 변경을 보존한다.

설계: 공통 고객사 식별로 구조화 값과 자유 텍스트를 구분한다. 원문에서 명시한 포함·제외 고객사를 모델 계획과 독립 대조하고 누락·변조는 재해석한다. Luna 두 번 뒤 수정 가능한 고객사 오류에만 설정된 Gemini를 한 번 사용하며 동일 검증과 요청 시간 제한을 적용한다. 검색 완전성을 보장할 수 없는 제목 전용 필터는 추가하지 않는다.

- [x] 구현 전 코드·17문항/19턴·원천 기준을 보존하고 실제 변경 전 비교를 실행한다.
- [x] 고객사 필터·별칭·복수·제외·제목 밖 속성·리터럴 검색의 실패 테스트를 만든다.
- [x] 공통 고객사 식별과 Notion API/후처리 비교를 수정한다.
- [x] 명시 고객사 집합 검증·프롬프트·한 번의 대체 모델 재해석을 구현한다.
- [x] 라우팅 사례, 후속 변경·해제·독립 질문, 제한 시간·실패 시 조회 차단을 검증한다.
- [x] 전체 check.sh, 실제 고정 문항 전후 정확도·응답 시간·원천 변동을 비교한다.
- [x] 표준 스크립트로 서버에 적용하고 최종 기록을 남긴다.

검토 중점: 회사명이 제목 밖 메모에만 있는 문서, 실제 고객사 속성과 제목의 다른 회사가 충돌하는 문서, 한국투자/신한 약칭 충돌, 포함·제외의 혼합과 복수 고객사, 이전 대화가 있는 새 질문. 이 입력들을 테스트로 고정한다.

산출물과 원문 응답은 Git 제외 경로 `assistant_web/runtime/customer-scope-fix-20261030`에 보관한다. 모델·원천 HTTP 변동이 있으므로 17문항의 점수와 시간만으로 전체 품질·속도 개선을 단정하지 않는다.


## 구현 및 검증 기록

- 등록 고객사 사전의 모든 별칭이 본래 고객사로 식별되는지 검사한다. 접미사를 합성해 삼성증권/삼성선물, 하나/외환선물을 합치는 방식을 제거했다. ‘문서 하나’, ‘그중 하나’의 수량 표현을 고객사 하나로 해석하지 않도록 했다.
- `customer_identity.py`에서 고객사 속성은 정규화한 회사명으로, 속성이 비어 있으면 기존 제목·속성 검색 텍스트를 별칭 경계로 비교한다. `한투`가 `신한투자증권`의 일부로 매칭되는 것을 막는다.
- API의 select/multi_select 필터도 같은 고객사 식별을 사용한다. 고객사 값이 빈 행을 후보에서 제외하지 않으며, rich_text 고객사 속성이 함께 있으면 select 조건만으로 좁히지 않는다.
- 제목 전용 필터는 메모 등에만 고객사명이 있는 정상 문서를 누락하므로 사용하지 않았다. 고객사 속성이 있는 DB와 없는 DB 모두, 목록은 실제 검증을 통과한 문서가 충분해진 시점에만 조기 종료한다. 페이지 상한에 도달한 조회는 불완전함을 표시한다.
- 본문·제목·리터럴을 지정하지 않은 일반적인 ‘관련 문서’ 질문에서 모델이 주제를 본문 전용 keyword로 출력하면 검증된 주제값을 terms로 정리한다. 명시적 본문·제목·문자열 요청과 후속 조건은 바꾸지 않는다. 중간 실측에서 이 구분 누락으로 180초 제한을 초과한 문제를 확인했다.
- 프롬프트와 검증에서 고객사·일반 주제·제목/본문 리터럴을 구분한다. 복수 고객사는 OR 집합을 보존하며, 누락·잘못된 고객사·제외 조건 누락은 조건을 넓히지 않고 재해석한다.
- Luna 두 번 뒤에도 고객사 검증이 실패하면 설정된 Gemini를 한 번 호출한다. 동일 검증·전체 요청 제한을 적용하고 Gemini 실패 이후 추가 재해석은 하지 않는다. 다른 종류의 검증 오류를 무조건 대체 모델로 보내지는 않는다.
- 본문 표현 ‘들어간’도 contains로 해석한다. 제목으로 오인하지 않으며, 실제 Luna로 본문 한투 검색·한투 제외·한투와 신한 복수 고객사 세 계획을 별도 확인했다.
- 순수 제목·본문 구문 분석기를 `text_scope.py`로 분리해 새 계층 순환 없이 재사용했다. 기존 `notion/query_text.py`의 공개 경로는 유지했다. 구조 검사 기준선은 완화하지 않았다.
- 신규 계약 테스트 22개와 라우팅 회귀 사례를 추가했다. `check.sh` 전체 단계 통과: 2,714개 테스트, 커버리지 90%, compile/shell/ruff/mypy/audit 통과. audit의 기존 예외 5개는 변경하지 않았다.
- 별도 실제 Gemini 호출은 HTTP 402로 실패했다. 누락 계획 두 번 뒤 Gemini 한 번 호출과 최종 clarify를 확인했고, 성공·재검증·제한 시간·추가 모델 호출 차단은 결정형 테스트로 확인했다. 실제 Gemini의 성공 응답 검증은 외부 서비스가 응답할 수 있을 때까지 남는다.
- 표준 재시작 스크립트와 `/health` 정상 응답을 확인했다. 최종 실측 중에는 로컬 서버의 캐시 예열 간섭을 줄이기 위해 잠시 중지했고, 측정 후 다시 적용했다.

## 실측 결과

| 문항 | 변경 전 | 고객사 수정 후 |
| --- | --- | --- |
| 한투 관련 최근 문서 | 92.085초, 신한 문서 5건 | 98.729초, 한투 관련 문서 5건 |
| 한투 조건검색 서버 문서 | 180.350초, 시간 초과 | 151.815초, 한투 관련 문서 5건 |

- 반환된 10건 모두 원문 고객사 속성 또는 한투 업무가 적힌 보고서 속성으로 관련성을 확인했다. 최근 문서 5건은 직접 고객사 속성이 있는 2건과 한투 업무를 포함한 주간보고서 3건이다. 서버 질문의 5건은 모두 고객사 속성으로 한투를 확인했다.
- 전체 실측의 자동 점수는 변경 전 15/17, 변경 후 15/17이다. 변경 후 새 실패 1건은 Mantis 담당자 후속 질문을 모델이 설명 과업으로 상속한 경우였다. 단일 대상의 현재 담당자를 묻는 질문은 속성 조회로 정규화하고, 서비스가 붙이는 이슈 번호도 처리했다. 과거 담당자·변경 이력 설명은 보존했다.
- 보완한 동일 2턴 대화를 `owner-retest-final`에서 실제 모델로 재실행해 1/1 통과했다. 보완은 `unified_validation.py`의 현재 담당자 조건문 하나이며, 기존 19턴 중 해당 턴 하나에만 적용됨을 확인했다. 그 조건문을 제거한 코드 해시는 전체 실측 코드와 일치한다. 현재 코드 전체의 해시는 재검증 실행의 해시와 일치한다.
- 전체 실측과 보완 대화의 재검증을 합친 문항별 검증 결과는 **16/17, 기존 문항 15/15**다. 원측정과 재검증 기록은 분리해 보관했다.
- 남은 자동 실패 1건은 한투 업무가 포함된 정상 주간보고서에 `NH투자증권`도 등장해 금지어 기준에 걸린 것이다. 문서별 고객사 관련성 검증은 두 질문 모두 5/5 통과했다. 자동 기준을 사후에 바꾸거나 정상 보고서를 검색에서 제외하지 않았다.
- 19턴 전체 지연은 평균 35.110→33.762초, 중앙값 30.047→30.049초다. 첫 한투 질문은 6.644초 느려졌고 두 번째는 시간 초과를 벗어났다. 전체 속도 개선을 단정하지 않는다. 이 시간은 전체 실측 기록이며, 담당자 대화의 별도 재검증 시간을 섞지 않았다.
- 전체 실측의 원천 429 응답은 변경 전 29회, 변경 후 0회였다. 공통 요청 640개 중 응답이 달랐던 형태는 26개이며, 기준 Notion 문서 3개의 원문 해시는 같았다. 실행 시간과 점수의 외부 변동 가능성을 함께 기록한다.
- 최종 `check.sh` 전체 단계 통과: **2,714개 테스트, 커버리지 90%**. 실제 Luna의 본문 한투 검색·제외·복수 고객사 계획 3건도 확인했다. Gemini는 HTTP 402로 실제 성공 응답 검증이 남아 있다.

검증 파일: `comparison.json`(전체 원측정), `final-verification.json`(보완 후 검증 행렬·코드 해시 확인), `customer-source-audit.json`(문서별 고객사 근거), `owner-retest-final/report.json`(담당자 후속 재검증). 모두 위 Git 제외 실험 폴더 안에 있다.


## 비교 방법과 판정 범위

- 변경 전 코드 사본과 기존 15문항 + 문제 재현 2문항(총 17문항/19턴)을 구현 전에 보존했다. 기준선은 `before`, 적용 대상의 실제 비교는 `after-release`다. 문항·모델 설정·설정 파일·실행 스크립트·원천 저장본의 해시를 대조한다.
- 실제 Notion 읽기는 같은 허용 범위에서 호출하지만 외부 응답과 429는 변할 수 있다. 원천 HTTP 기록과 지정된 문서의 원문 해시를 함께 비교한다. 시간 초과도 정확도·응답 시간 집계에서 제외하지 않는다. 최종 실측은 로컬 서버를 중지해 캐시 예열의 추가 요청을 줄였다. 따라서 지연 차이를 코드만의 성능 효과로 단정하지 않는다.
- 두 고객사 문항은 자동채점과 별도로 반환 문서가 한투 관련 문서인지 원문 속성을 확인한다. 고객사 속성이 없더라도 한투 업무가 실제 포함된 주간보고서는 정상 결과로 유지한다. 다른 고객사 이름을 무조건 금지한 자동 기준은 이런 문서도 실패 처리할 수 있다. 이번 문항의 기준을 사후에 바꾸지 않고 자동 점수와 문서 근거 판정을 구분해 기록한다.
- 본문 ‘한투’, 한투 제외, 한투와 신한 복수 고객사의 세 질문은 실제 Luna의 계획만 추가 확인했다. 17문항의 정확도나 응답 시간 통계에는 합치지 않는다.
- 중간 실측과 중단한 실행도 보관한다. 미기록 요청 때문에 완전한 재생이 성립하지 않은 부가 실험은 통과 근거로 사용하지 않는다. 최종 검증 근거는 결정형 회귀 테스트, 실제 모델 실행, 원문 대조다.
