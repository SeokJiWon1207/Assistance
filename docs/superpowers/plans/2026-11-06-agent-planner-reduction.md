# 앞단 플래너 축소 구현 계획

> 실행: 사용자가 승인한 하네스 2단계를 메인 에이전트가 직접 구현한다. 위임·커밋·배포 없이 기존 작업 파일을 보존한다. writing-plans, executing-plans, test-driven-development 절차를 적용한다.

**목표:** 에이전트가 조건 해석과 조회 순서를 결정하고 서버가 기존 조건·근거·전송 검증을 보증한다. 집계 보정 중 미해결 조건이 사라지는 실패를 재현하고 방지한다.

**설계:** 활성 정책의 일반 요청에서 별도 `plan_question` 호출을 제거한다. 앞단은 사용자에게 묶인 감사 문맥과 순번만 복원한다. 에이전트의 `prepare_query` 도구가 제안 조건을 기존 `validate_plan` 및 실행 계약으로 검증한다. 실패한 제안은 서버에 보관하고 후속 호출은 변경 필드만 병합한다. 검증 전 조회는 불가능하며 확정 뒤에는 조건을 변경하지 못한다. 검증된 읽기는 기존 조회 도구와 근거 원장으로 이어진다. 쓰기·일반 대화·아직 도구화하지 않은 보고서는 검증된 계획으로만 기존 경로에 넘긴다. 해석 실패를 무조건 기존 생성으로 우회하지 않는다.

**선택:** 플래너 프롬프트 보정만으로는 실행 전 차단과 별도 호출이 남는다. 모든 조건 검증을 없애는 방식은 승인 범위가 아니다. 따라서 기존 검증기를 에이전트 도구로 옮기되 호환 계획 형식은 유지한다. 단계별 서로 다른 조건 집합은 다음 단계다.

**제약:** Python 3.12, AGENT_MODE_ENABLED와 도구 검증·모델 허용 목록·마스킹·공통 예산 유지. 현재 상태/기간 검증·집계 수치 검증·부분 조회 구분을 완화하지 않는다. 최신 N건 모집단 제한과 Notion 단독 목록은 기존 엔진 유지. 같은 승인 범위의 Luna/Gemini 검증만 수행한다.

## 검토 초점

- 첫 제안이 잘못됐어도 보정이 미해결·고객사·기간을 조용히 지우지 않는가.
- 검증 도구 없이 조회하거나 다른 사용자의 감사 기록으로 조건을 만드는가.
- 원천 비활성·도구/모델 한도·해석 실패가 무검증 생성이나 전체 0건으로 바뀌는가.
- 검증된 일반 대화/쓰기/특수 보고서 위임이 기존 권한·승인 흐름을 보존하는가.
- 확정 조건이 실제 도구·최종 검증·감사·후속 순번에 동일하게 적용되는가.
