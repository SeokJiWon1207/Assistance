# Mantis·Notion 기반 홈 업무 추천 설계

작성일: 2026-11-09

## 요청과 결정 범위

사용자는 ChatGPT 홈의 출처 링크가 있는 추천처럼, 기존 Mantis 조회와 **기존 Notion API 연결·검색·본문 읽기를 모두 활용**하는 AI비서 추천 기능의 구현 계획을 요청했다. 첫 릴리스부터 Mantis 단독, Notion 단독, Mantis+Notion 연결 추천을 지원한다. 이 문서는 구현 계획의 기준이며 제품 코드 구현·배포는 아직 수행하지 않는다.

최대 3개 표시, 후보 수, 시간 예산, 캐시 정책 등 아래 수치는 구현을 위한 제안 기본값이다. 실제 운영 성능을 측정해 조정하며 이미 측정한 수치로 해석하지 않는다.

## 접근법

| 접근 | 판단 |
|---|---|
| Mantis 규칙 추천을 먼저 출시하고 Notion은 나중에 추가 | 이번 요청의 두 원천 동시 활용을 충족하지 않으므로 채택하지 않는다. |
| 홈 접속마다 채팅 에이전트로 전체 자료 조사 | 현재 채팅 대기열과 모델·원천 조회 비용이 커지므로 채택하지 않는다. |
| 두 원천에서 제한된 후보 수집 → 현재 근거 확인 → 규칙 및 선택적 모델로 작업 선택 → 캐시 | 채택한다. 원천 연결과 검증은 재사용하고 추천 정책만 별도 서비스로 둔다. |

추천 생성은 채팅 요청과 분리한다. 모델이 꺼지거나 실패해도 **두 원천의 확인된 속성·본문에 기반한 규칙 추천**이 동작한다. 에이전트 기능 플래그를 켜는 것이 선행 조건이 아니다.

## 현재 코드에서 재사용할 부분

- `backend/workspace_data.py:load_complete_workspace`: 담당 범위로 필터링할 수 있는 전체 저장본, `fetchedAt`, `search_complete`, `cacheUntil`.
- `backend/workspace.py:user_mantis_name`, `backend/storage/workspace_rows.py:_issue_summary`, `backend/reports/team_brief.py:_priority_content`: 기존 업무와 동일한 담당자·상태·목표일·위험 근거. 추천 구현을 위해 기존 점수를 바꾸지 않는다.
- `backend/workspace_notifications.py`: 완전한 같은 세대 사이에서 관찰한 배정·노트 활동. 최초 기준선을 새 활동으로 취급하지 않는다.
- `backend/notion/search.py:execute_notion_search`: 기존 API 키와 DB 설정으로 속성 검색. 생성된 검색문이 필터를 바꾸지 않도록 `derive_text_constraints=False`를 사용한다.
- `backend/notion/read_scope.py:resolve_notion_read_scope`, `page_links.py:page_record`, `semantic_search.py:read_current_page`: 현재 접근 범위·소속·속성·본문 확인.
- `backend/notion/retrieval_candidates.py:hybrid_candidates`: 저장된 제목·본문은 관련 후보 탐색에만 사용한다. 현재 본문 근거로 승격하지 않는다.
- `backend/evidence/stages.py:stage_events`: 개발·QC·고객 전달·고객 검증·운영 반영의 완료/예정/실패를 분리한다. 원래 이슈 중심 규칙이므로 Notion의 소유 본문 구절에 적용하는 어댑터와 회귀 사례가 필요하다.
- `backend/llm.py:model_transfer_scope`, `post_model_chat` 및 `backend/tools/redaction.py`: 허용 목적지 검사와 마스킹. 직접 모델 HTTP 호출을 추가하지 않는다.
- `backend/static/modules/chat_empty_state.js`, `events.js`, `bootstrap.js`: 홈 추천 영역, 입력창 채우기, 비동기 초기화.

현재 `build_my_workspace()`가 Notion을 숨기는 것은 내 업무 화면에만 해당한다. 이 동작을 변경하거나 `_my_notion_pages()`를 그대로 재활성화하지 않는다. 추천 서비스가 기존 Notion 검색·현재 본문 읽기 기능을 직접 조합한다.

## 사용자 경험

1. 빈 대화의 인사 아래, 팀 템플릿 위에 최대 3개의 추천을 표시한다. 기존 템플릿·최근 기록은 유지한다.
2. 각 추천은 원천 표시, 한 줄 제목, 근거 링크, 개별 숨김 버튼을 제공한다. 상세 질문과 확인 시각은 키보드·모바일에서도 여는 미리보기로 제공한다.
3. 추천 클릭은 상세 질문을 입력창에 채우며 자동 전송하지 않는다. 이미 작성한 내용이나 수정 중 메시지를 덮어쓰지 않고 미리보기에서 명시적으로 넣도록 한다.
4. 링크는 출처 열기, 행은 질문 채우기로 동작을 분리한다. `button` 안에 `a`를 중첩하지 않는다.
5. 생성 중에도 채팅을 사용할 수 있다. 유효한 기존 추천을 표시하고, 캐시가 없으면 추천 영역에만 준비 상태를 표시한다. 실패·후보 부족 때 3개를 억지로 채우지 않는다.
6. 두 원천을 조회하되 슬롯을 원천별로 강제 할당하지 않는다. 동등한 후보끼리는 원천 다양성을 고려한다. 한 원천 장애를 다른 원천의 무결과로 표시하지 않는다.
7. 추천에서 사용한 원천이 채팅 도구 설정에서 꺼져 있으면 이를 안내한다. 도구를 몰래 켜거나 다른 원천으로 질문을 바꾸지 않는다.

## 후보와 관련성

### Mantis

사용자 담당 미종료 이슈의 지연·장기화·높은 우선순위, 관찰된 새 노트·배정에서 최대 12개 후보를 얻는다. 추천 요청으로 전체 Mantis 수집을 새로 시작하지 않고 기존 저장본 갱신기를 이용한다. 만료·불완전 데이터에서 새 변화·전체 건수·급증을 확정하지 않는다.

새 노트 등 상세 해석이 필요한 상위 후보만 기존 상세 조회로 보강한다. 최대 4개 이슈 본문을 읽으며 관련 문서 탐색 시 확인된 Notion 링크·이슈 번호·구체적 주제만 사용한다.

### Notion

두 가지 경로를 합쳐 최대 12개 후보를 만든다.

- 사용자 이름과 담당자 매핑이 명확하면 기존 담당자 속성 의미에 따라 담당 문서의 기한·상태·최근 수정 속성을 읽는다. 담당자가 없는 문서 DB의 기여자 역할은 담당자와 구분해 표시한다. 이름이 모호하거나 매핑이 없으면 개인 문서 전체로 범위를 넓히지 않는다.
- 내 담당 Mantis 이슈에 실제 기록된 Notion 링크, 또는 구체적 고객사·기능 주제와 관련된 문서를 찾는다. 이는 '관련 문서'이며 '내 담당 문서'로 오인하지 않는다. 개인 Notion 매핑이 없어도 이 경로는 사용할 수 있다.

개인 담당 문서 탐색은 서버에서 확정한 `owner`와 정렬 조건을 `execute_notion_search(..., include_blocks=False, derive_text_constraints=False)`에 전달한다. 관련 문서 경로에서는 이슈 담당자 조건을 Notion 문서 작성자 조건으로 복사하지 않는다. API에 허용된 DB·하위 DB 경계를 별도로 지킨다. API 키가 읽을 수 있는 범위와 사용자 관련성은 서로 다른 개념이다.

인덱스가 없어도 속성 API 조회와 확인된 직접 링크 읽기로 동작한다. 원천 범위가 불완전하면 전역 검색으로 우회하지 않고 확인된 범위만 사용한다. 본문 추천은 상위 최대 4개 페이지의 현재 본문을 읽은 뒤 만든다. 제목 후보·오래된 벡터 발췌·잘린 본문만으로 완료·미완료를 단정하지 않는다.

### 연결 추천

- 직접 링크 또는 문서 내 동일 이슈 번호는 강한 연결 근거다. 고객사와 주제가 비슷한 것만으로 같은 업무라고 확정하지 않는다.
- 같은 업무라도 개발 완료와 고객 검증 대기는 다른 단계다. 차이 자체를 오류·모순으로 표시하지 않는다.
- 현재 본문에서 확인된 단계별 구절과 날짜를 제시하며, 최신순 판단이 불가능하면 상태 비교 요청으로만 제안한다.
- 확정 근거가 없는 경우 문구는 “진행 상태를 대조해요”, “남은 확인 항목을 정리해요”로 제한한다. '검증 기록을 못 찾음'을 '검증하지 않음'으로 바꾸지 않는다.
- 초기 작업 유형: `review_progress`, `summarize_changes`, `compare_records`, `prepare_checklist`. 체크리스트는 기존 설명 경로로 요청하며 전용 QA 보고서 엔진이 이미 있다고 가정하지 않는다.

## 모델 사용과 표시 문구

규칙이 검증된 후보·출처·허용 작업 유형을 만든다. 선택적 모델은 후보 ID와 작업 유형, 제한된 이유 코드만 고른다. 제목·링크·날짜·건수·완료 문구는 서버가 확인된 사실과 고정 템플릿으로 렌더링한다. 모델 자유문장을 그대로 홈의 확정 사실로 내보내지 않는다.

한 갱신당 모델 호출은 최대 1회, 제한 시간 12초, 출력 최대 1,200토큰이다. 입력은 마스킹한 상위 6개 후보의 필요한 구절만 사용하며 총 12,000자를 넘기지 않는다. 모델은 원천 선택·사용자 범위·링크를 변경할 수 없다. 오류, 잘못된 ID, 미허용 action, 시간 초과는 규칙 결과로 복귀한다.

`HOME_SUGGESTIONS_ENABLED=false`, `HOME_SUGGESTIONS_MODEL_ID=` 및 전용 `HOME_SUGGESTIONS_ALLOWED_MODEL_IDS`, `HOME_SUGGESTIONS_ALLOWED_ENDPOINT_ORIGINS`를 설정한다. 모델 설정이 비거나 허용 목록이 맞지 않으면 호출하지 않는다. 운영 추천에는 기존 회사 승인 모델만 설정한다. 테스트·검증용 Luna/Gemini 전송 승인을 운영 추천의 자동 폴백 승인으로 확대하지 않는다. 에이전트 전용 도구 지원 검증을 이 기능의 필수 조건으로 만들지 않는다.

## 데이터·API 계약

`GET /api/suggestions?limit=3`: 인증 사용자 캐시만 읽는다. `1 <= limit <= 3`. 외부 조회·모델 호출·작업 등록 없음.

`POST /api/suggestions/refresh`: 인증된 사용자 범위의 갱신 요청. 중복 요청은 같은 작업으로 합치고 `202`와 `generationId`를 반환한다. 갱신 중 반복 클릭으로 작업을 늘리지 않는다. 동일 사용자 60초 내 재시작은 기존 상태를 반환한다.

`POST /api/suggestions/{id}/dismiss`: 현재 사용자에게 속한 추천만 숨김. 재호출은 멱등이며 다른 사용자 항목은 404.

`POST /api/suggestions/{id}/prepare`: 클릭 시 현재 원천·관련성·버전을 재확인하고 입력할 `prompt`와 `revision`을 반환한다. 채팅 실행이나 원천 쓰기는 하지 않는다. 삭제·접근 철회·담당 해제는 410, 재확인 장애는 503. 화면은 이 응답을 기다려도 작성 중 텍스트를 덮어쓰지 않는다.

추천 응답 필드:

- `id`, `kind`, `title`, `promptPreview`, `reasonCode`, `revision`, `dedupeKey`
- `sources[]`: `type` (`mantis|notion`), `id`, `title`, `url`, `revision`, `observedAt`, `validUntil`, `grade` (`properties|body`)
- `generatedAt`, `expiresAt`; 서버 내부 근거 구절은 검증·미리보기에 필요한 최소 범위만 보관
- 목록에는 `state` (`disabled|ready|pending|partial|unavailable`), `generationId`, `sourceStatus`, `retryAfterSeconds`
- 연결·토큰 fingerprint는 서버 캐시 키에만 사용하며 API·로그에 출력하지 않는다.

첫 버전은 `ChatRequest` 변경 없이 자족적인 상세 질문을 입력한다. 질문은 이슈 ID, Notion URL, 작업 목적과 “최신 기록을 다시 확인”하라는 요청을 포함한다. 기존 대화의 '위 문서' 같은 암묵적 참조를 만들지 않는다. 본문은 데이터이며 본문 안의 지시를 시스템 명령으로 취급하지 않는다.

## 캐시·작업 수명

추천 묶음의 키는 사용자 UID, 담당자 매핑, Mantis 연결, Notion 연결·읽기 범위, 정책 버전을 포함한다. 추천 항목의 revision은 참조 원본의 의미 있는 버전으로 계산한다. Mantis 전체 수집 시각만 바뀌어도 숨김이 풀리는 구조를 금지한다.

- 캐시 최대 10분, 실제 만료는 각 원천의 유효기간 중 가장 이른 값이다. 만료된 항목을 '최신'으로 계속 표시하지 않는다.
- Notion 속성·소속·본문은 생성 직전 검증하며 prepare에서도 접근·버전을 재확인한다. 캐시 TTL 안의 변경 발견 지연은 존재하므로 확인 시각을 표시하고, 접근 철회를 알게 되면 관련 캐시를 즉시 제거한다.
- 서로 관련된 같은 이슈·문서의 후보는 하나로 합친다. 동일 `dedupeKey + revision`의 숨김은 갱신 후에도 유지한다. 새 노트·실제 상태/내용 변화는 새 revision으로 다시 후보가 될 수 있다.
- `workspace.sqlite3`에 캐시, 숨김, 작업 lease 테이블을 추가한다. 계정 삭제에 모두 포함한다. 만료 캐시·종료 작업은 갱신 시 정리하고 숨김은 최근 사용 30일 기준으로 정리한다.
- 프로세스당 생성 워커 1개, 대기 사용자 최대 8명. 사용자별 DB lease 90초로 여러 프로세스의 중복 생성을 막는다. lease 토큰과 사용자/연결 범위를 게시 직전에 재확인한다. 오래된 워커가 새 결과를 덮어쓸 수 없다.
- 생성 예산은 최대 60초의 `ExecutionBudget`으로 원천 조회와 모델 호출 전체를 묶는다. Mantis 수집·보강 10초, Notion 후보·본문 35초, 모델 12초 이내의 하위 예산을 적용해 한 원천이 다른 원천의 기회를 소진하지 않게 한다. 동기 호출의 실제 종료 전 슬롯을 재사용하지 않는다. 부분 성공은 독립적으로 보존하고, 취소된 작업·삭제된 계정 결과는 게시하지 않는다.
- 홈에서 캐시 조회 후 필요한 경우에만 refresh 1회. pending은 5초 간격 최대 12회 조회하고, 화면 이탈·대화 시작·계정 전환 시 폴링을 종료한다.

## 추천 순서와 실패 처리

긴급/지연 → 명시적 후속 확인 요청 → 새 기록 → 장기화 순서에 개인 관련성·확인 시각을 반영한다. 기존 위험 점수는 변경하지 않는다. 강한 연결 근거가 있는 복합 추천을 동등 후보보다 우선하고, 순위가 동등하면 다른 원천·다른 업무를 선택한다. 날짜는 프로젝트의 날짜 유틸리티와 동일한 기준을 사용한다.

Notion 429/장애, Mantis 만료, 모호한 이름, 본문 미완료, 모델 실패를 각각 구분한다. 유효한 다른 원천 추천은 계속 표시한다. 두 원천 모두 확인하지 못하면 팀 템플릿으로 자연스럽게 복귀한다. 원천 검색 결과 개수를 전체 업무 개수로 쓰지 않는다.

## 검증과 완료 기준

- 두 원천 모두 성공하는 fixture에서 각각의 단독 추천과 근거가 연결된 복합 추천을 생성할 수 있다.
- 잘못된 관계, 이전 버전, 미검증 본문, 다른 사용자 항목이 추천·prepare에 포함되지 않는다.
- Notion 장애 시 Mantis, Mantis 장애 시 Notion의 유효 결과가 유지된다.
- 사용자 숨김·원본 변경·계정 삭제·동시 갱신·종료 시 워커 수명이 일관된다.
- 입력창 덮어쓰기, 자동 전송, 기존 대화 재렌더링 손실이 없다.
- 기본 OFF일 때 추가 원천 API/모델 조회가 없다. GET 캐시 조회가 외부 호출을 하지 않는다는 계약을 테스트한다.
- 라우팅 회귀에는 Mantis 단독, Notion URL 단독, 두 원천 비교, 확인 목록 질문을 추가한다. 실행 답변도 기존 근거·출처 검증을 거친다.
- 루트에서 `assistant_web/scripts/check.sh`를 통과한다. 현재 작업 트리의 기존 실패는 새 실패와 구분해 기록한다.

## 범위 밖

Google Drive 신규 연결, Notion/Mantis 쓰기, 자동 메시지 전송, 전사 문서 무제한 분석, 개인 대화 내용의 백그라운드 학습, 신규 전용 QA 문서 엔진은 포함하지 않는다. 추천 생성과 클릭 후 답변 품질을 별도로 평가한다.
