# 남은 결정형 기능의 에이전트 도구 연결

하네스 후속 작업 2번으로 Notion 단독 건수·목록·현재 속성, 공수·주간·월간 보고서, 최근 N건 모집단 조회를 일반 에이전트 도구에 연결했다. 모델이 실행 순서와 추가 읽기를 선택하고, 기존 서버 엔진이 계산과 최종 검증을 담당한다. 기존 조건·근거·수치 검증과 전송 정책은 유지했다.

## 구현과 검증 경계

- `count_notion_pages`, `list_notion_pages`는 검증된 조건·정렬·검색어로 전체 조회를 수행한다. 의미 검색 후보 수나 표시 창의 완료를 전체 건수로 사용하지 않는다. 전체 조회를 마치지 못하면 `total_count=null`이며 0건으로 확정하지 않는다.
- `get_notion_page_properties`는 이번 요청에서 확보한 페이지 참조만 받는다. 현재 접근 권한·소속·조건과 속성 페이지네이션을 확인한다. 현재 상태·담당자 등을 원장과 후속 질문에 반영하되 본문을 읽었다고 표시하지 않는다.
- `build_issue_report(kind=effort/weekly/monthly)`는 검증된 보고서 목적·필터·공수 방식으로 기존 계산기를 호출한다. 기존 `deterministic_*` 최종 검증기를 재사용하고, 모델이 만든 숫자로 결과를 대체하지 않는다. 주간·월간 지표별 날짜 처리에도 나머지 명시 조건을 보존한다. 부분 원천은 전체 보고서로 단정하지 않는다.
- `population_limit`는 최근/최신 N건이라는 필터 적용 전 모집단이고 `limit`는 표시 개수다. 기존 API 응답 순서에서 모집단을 정한 뒤 조건을 적용한다. 같은 요청의 건수·목록·단순 그룹 집계는 같은 모집단을 사용한다. 미완료 시 전체 저장본으로 우회하거나 확정 건수를 내지 않는다.
- 기존 조건 단계 검증·인용 원장·수치 재계산을 유지했다. Notion 결과에는 실행 계약과 서버 생성 결과를 대조하는 `agent_notion_contract`, `agent_notion_result` 차단 검사를 추가했다. 실제 질문에 없는 사람 이름이나 조건으로 재해석하지 않고 검증된 구조화 조건으로 기존 속성 대조를 수행한다.

새 구현은 `backend/tools/notion_queries.py`, `issue_reports.py`, `population.py`, `backend/services/agent/deterministic_answers.py`에 있다. 도구 등록·계약·조건 단계·원장·최종 응답과 검증 연결도 함께 수정했다. 지원 범위는 `assistant_web/docs/AGENT_HARNESS.md`에 반영했다.

## 실제 비교 환경

- 변경 전은 이번 작업 시작 시점의 코드이며, 이미 여러 조회 범위의 독립 비교를 지원하는 일반 에이전트 경로다. 변경 후 복제본에는 이번 작업의 백엔드 23개 파일만 적용했다. 작업 중 별도로 변경된 UI·설정은 비교에 섞지 않았다.
- 동일 저장본을 실행별 폴더로 복제해 실제 `ChatService`를 실행했다. query-shadow는 false이며, 변경 전후의 실제 응답을 비교했다. 운영 설정·서버는 변경하지 않았다.
- Mantis 저장 시각은 **2026-11-06 15:15:31 KST**다. Notion 240개 DB의 가장 오래된 목록 갱신은 **14:59:14 KST**다. 시작·매 턴·종료에 최신성을 확인했고 유효 시간 **7,200초를 늘리지 않았다**.
- Mantis 전체 JSON을 독립 SQL로 읽어 고객사·미해결 상태·정렬과 상태별 정답을 계산했다. 도구가 반환한 숫자를 정답으로 재사용하지 않았다. 모든 선정 실행의 Mantis 저장본 SHA-256은 같고 실행 중 변경되지 않았다.
- 승인된 `gpt-6-luna`와 기존 마스킹·허용 목록을 사용했다. 선정 실행에는 Gemini 폴백, 429, HTTP 오류가 없었다. 네트워크 접근은 모델 호출·로컬 임베딩·원천 읽기/검색 범위였다.
- 반복 비교는 `legacy-compound-*` 3회와 `verified-compound-*` 3회다. 이후 Notion 단독 속성 검색을 보완한 최종 코드로 `release-compound-1`과 후속 질문을 한 번 더 실행했다. 따라서 **최종 파일과 완전히 같은 코드의 복합 질문은 1회**, 그 직전 코드의 반복은 3회다. 최종 23개 파일과 `after-release/backend`의 바이트 일치를 확인했다.

실행 질문:

1. `전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.`
2. 각 복합 질문의 후속: `그중 두 번째 이슈 번호와 제목만 다시 알려줘.`
3. `전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.`
4. `노션에서 제목이 "존재하지 않는 항목 357006"인 문서가 몇 건인지 알려줘.`
5. `노션에서 제목이 "eFriend Force 저장/불러오기 연동되지 않는 현상 원인 및 개선 후 영향도 정리"인 문서의 상태와 담당자 속성을 알려줘.`

변경 전 복합 1회차는 필요한 건수·목록·본문을 확보한 뒤 `call_limit`으로 종료했다. 변경 후 선정 복합 4회는 모두 `sufficient_evidence`로 종료했다. 표본이 적고 모델 호출의 편차가 있어 속도나 비용이 개선됐다고 일반화하지 않는다.

선정한 11개 실행 묶음은 후속 질문을 포함해 18응답이다. 차단 검증 실패는 없었다. 복합 답변에는 기존 `model_content_review=review`가 유지됐다. 속성 답변에는 전체 목록 탐색에 대한 `search_completeness=warning`이 남았지만, 해당 페이지의 현재 속성 읽기는 완료했고 전체 목록의 완전성은 주장하지 않았다. 부재 질문은 전체 조회 완료를 확인한 뒤에만 0건으로 답했다.

**가이드 관련성의 기존 한계는 유지된다.** 읽은 문서는 같은 7695 화면의 저장/불러오기·롤백 참고 자료다. #29186의 화살표 메모 기능을 직접 설명하는 가이드를 찾았다는 뜻이 아니다. 원장에서도 참고 등급과 적용할 수 없는 조건을 유지했다. 이번 검증은 정확한 건수·목록·순서·후속 제목과 실제 참고 본문 읽기를 확인한 것이며, 미뤄 둔 가이드 관련성 문제의 해결을 주장하지 않는다.

## 실제 실행에서 발견해 수정한 문제

1. Notion 단독 계획의 정렬 기본값을 도구 계약과 다르게 읽어 원천 호출 전에 거부했다. 검증된 기본 정렬을 양쪽에서 동일하게 적용했으며, 모델이 실제 정렬을 바꾸는 경우는 계속 거부한다.
2. `담당자 속성을 알려줘`의 `속성을`을 기존 정규식이 사람 이름으로 해석했다. 최종 속성 검증은 유효한 실행 계약의 조건으로 수행하고 기존 원문 대조를 유지했다. 원천 검색도 구조화 조건을 받은 경우 질문을 다시 정규식으로 해석하지 않도록 연결했다. 수정 전에는 실제 존재하는 제목을 0건으로 잘못 처리한 실행이 있었으며, 최종 코드에서는 같은 질문으로 현재 속성을 읽어 답했다.
3. 표시 창만 완료된 빈 결과가 완전한 0건처럼 처리될 수 있어 전체 조회와 후보 건수 완료 여부를 함께 확인하도록 했다. 속성 원문이 길면 모델에 전달하는 값은 제한하지만 원장과 서버 검증용 값은 보존한다.

개발 중 실패한 `primary`/`corrected`/속성 실행은 통과 표본에 섞지 않았으며 원시 기록을 보존했다. 평가 스크립트의 상태 코드와 표시명 비교 오류도 원천 코드별 고정 매핑으로 바로잡았다. 서버 검증 기준을 낮추는 변경은 하지 않았다.

## 오프라인 회귀와 남은 범위

- `assistant_web/scripts/check.sh tests` 통과: **3,221건, 커버리지 91%**.
- `assistant_web/scripts/check.sh compile shell ruff mypy` 통과: Python·프런트엔드 빌드 검사, 셸 검사, Ruff, **mypy 302파일**. 이번 작업에는 의존성 변경이 없다.
- 새 테스트 17건은 Notion 전체 0건/부분 0건/표시 창 완료, 조건 누락·변조, 다른 요청의 페이지 참조, 현재 속성·접근 철회, 원천 검색과 검증의 조건 일치, 모집단 선택 순서·캐시·불완전 조회, 보고서 목적·필터를 검사한다. 공수는 실제 필드에서 2.50을 재계산하고 출력 수치를 99.00으로 바꾸면 기존 검증이 차단하는 것도 확인했다. 주간·월간은 제목·미해결 조건이 유지됨을 확인했다. 관련 기존 테스트와 라우팅 fixture 5개를 함께 갱신했다.
- 공수·주간·월간과 최근 N건 모집단은 이번 단계에서 오프라인 실제 엔진 회귀로 검증했다. 실제 Luna 반복 비교는 위의 한투 질문과 Notion 보조 질문 범위다.
- 모집단 제한과 기간별/다차원 집계 또는 보고서의 조합은 명시적으로 거부한다. 지원되지 않는 조합을 전체 집계로 바꾸지 않는다.
- 모델이 고른 추가 읽기와 자유로운 최종 응답 합성을 통합하는 일은 후속 단계다. 이번 보고서 도구의 최종 출력은 기존 결정형 보고서와 검증 모드를 유지한다.
- 운영 서버 재시작·배포·기본 활성화 설정 변경은 하지 않았다.

원시 증거는 `assistant_web/runtime/agent-remaining-tools-20261106/`의 `summary.json`, `score.py`, `final-provenance.json`, `source/freshness.json`, `verification-tests.log`, `verification-static.log`와 각 실행의 `result.json`·`tools.json`·`models.json`에 있다. 원문을 포함한 런타임 파일은 커밋 대상이 아니다.
