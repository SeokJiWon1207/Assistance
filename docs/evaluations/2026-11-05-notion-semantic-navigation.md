# Notion 본문 의미 검색·페이지 탐색 검증 — 2026-11-05

본문 의미 검색과 하위·연결·관계 페이지 탐색을 구현했다. 실제 Luna 실행에서 한투 조건검색 서버의 접속 가이드 본문 읽기는 2/2회 확인했다. 기존 한투 복합 질문의 건수·목록·후속 순번은 3/3회 맞았지만, 두 번째 이슈의 비교차트 가이드 본문은 0/3회 확보했다. **가이드 탐색까지 모두 해결된 결과는 아니다.**

## 구현

- `search_notion_body`: 저장된 본문을 1,200자 구간으로 나눠 로컬 Ollama `bge-m3:latest`로 의미 검색한다. 연결·모델·내용 해시를 구분하고 수정된 구간만 갱신한다. 외부 임베딩 전송·리디렉션은 허용하지 않는다.
- 저장된 텍스트와 벡터는 후보 선정용이다. 결과에 넣기 전에 현재 Notion API에서 접근·소속·속성·본문을 확인한다. 현재 본문에 그대로 존재하는 검색 구간만 발췌하며, 긴 코드 본문도 JSON 크기 제한 때문에 통째로 사라지지 않도록 제한한다.
- `list_notion_page_links`: 현재 요청의 문서 ref에서 출발해 child page, page mention, Notion 링크, `link_to_page`, 관계형 속성을 따라간다. 목적지의 허용 DB와 조건을 다시 검증하고 별도 ref를 발급한다. 부모와 자식의 본문은 합치지 않는다. 깊이·중복·시간·호출 한도를 적용한다.
- 기존 도구 인자 조건 계약, 근거 등급, 원장, 마스킹, 인용 검증을 유지했다. 의미 검색은 항상 `coverage=top_k`, `search_complete=false`다. 빈 결과·색인 미준비·본문 비활성화는 전체 부재가 아니다.
- 서버 캐시 갱신 주기에 최대 256구간·30초의 증분 색인 갱신을 연결하고, 초기 구축용 `scripts/sync_notion_semantic_index.py`를 추가했다. 본문 수집은 기존 유지보수 경로를 사용한다.
- 설명 주제를 명시하지 않은 `title equals` 조건으로 바꾸는 계획을 거절하고 모델이 고치게 했다. 실제로 “조건검색 서버 문서”를 정확 제목으로 단정해 0건이 되던 사례를 확인했다. 인용한 정확 제목과 기존 대화의 검증된 제목 조건은 유지한다.
- 건수·목록 원장이 생겨 서버가 최종 답변을 구성하는 경우, 사용하지 않는 모델 합성용 예약 2회를 조사에 돌려준다. 모델 8회·도구 8회·요청 180초·최종 처리 시간 45초는 유지하며, 일반 설명의 인용 검증 예약분은 유지한다.

## 검증 조건

검증 데이터와 감사 DB는 `assistant_web/runtime/two-week-regression-20261104-155759/notion-semantic-20261105/`에 격리했다. 운영 저장본·서버 설정은 변경하지 않았다. Notion은 읽기 API만 허용했다.

최종 6개 실행은 동일한 코드 지문과 시작 저장본 지문으로 수행했다. [summary.json](../../assistant_web/runtime/two-week-regression-20261104-155759/notion-semantic-20261105/summary.json)에 지문과 실제 도구 호출 요약을 남겼다. 목록 나이는 실행 전후 2,797~3,278초였고 모두 정상 7,200초 유효기간 안이었다. 만료 시간을 늘리지 않았다. 이번 미확보 결과를 저장본 만료 탓으로 분류하지 않는다.

목록에는 16,806페이지가 있으며, 수집된 비어 있지 않은 본문 3,422페이지·4,717구간을 색인했다. 이는 전체 페이지의 본문 수집 완료를 뜻하지 않는다. 모델은 승인된 Luna를 사용했고 임베딩은 로컬에서 실행했다.

## 같은 한투 복합 질문 3회

> 전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.

매회 이어서 “그중 두 번째 이슈 번호와 제목만 다시 알려줘.”를 실행했다. 독립 SQL 대조값은 6건, 최근 등록순 `[31714, 31659, 29186]`, 두 번째는 `#31659 [MTS] 비교차트 내 추가된 종목의 장 중 실시간 업데이트 되지 않는 현상`이다.

| 실행 | 복합 질문 | 후속 질문 | 건수·순서·제목 | 현재 본문 확인 페이지 | 명시적 본문 읽기 | 관련 가이드 확보 | 종료 사유 |
|---|---:|---:|---|---:|---:|---|---|
| compound-verified-1 | 40.2초 | 3.9초 | 일치 | 2 | 1 | 미확보 | partial_evidence |
| compound-verified-2 | 102.8초 | 4.3초 | 일치 | 7 | 1 | 미확보 | partial_evidence |
| compound-verified-3 | 89.2초 | 5.2초 | 일치 | 6 | 1 | 미확보 | call_limit |

모든 실행에서 의미 검색이 호출됐다. 2·3회차는 제목 검색으로 대상 이슈의 Notion 기록을 찾고 본문을 읽은 뒤 관계 페이지 탐색도 실행했다. 해당 이슈 기록의 본문은 비어 있었고, 연결된 담당자 관계 페이지는 사용 가이드로 확인되지 않았다. 3회차는 실제 모델/도구 한도에도 도달했다. 마지막 모델 초안 대신 서버 원장의 건수·목록과 가이드 미확보 안내를 사용했다.

이슈 조회 점수의 통과를 가이드 확보 통과로 계산하지 않았다. “관련 가이드가 존재하지 않는다”는 결론도 내리지 않았다. 최종 3회에서 Notion 요청은 각각 38·183·161건, 429 응답은 1·3·0건이었다.

## 실제 가이드 본문 읽기

같은 질문 “한투 조건검색 서버 문서에서 서버 접속 방법을 설명해줘.”를 2회 실행했다.

| 실행 | 시간 | 실제 도구 흐름 | 본문 확인 |
|---|---:|---|---|
| server-verified-1 | 40.2초 | search_notion_body → get_notion_page_content | 성공 |
| server-verified-2 | 46.6초 | search_notion_body → get_notion_page_content | 성공 |

두 실행 모두 **한투 인도네시아 서버 조건검색 원격접속방법**(페이지 `22a9eccfeda48023b7e4ca0d96a38ae3`)의 현재 본문을 읽었다. FortiClient VPN 접속 후 Hiware로 접속하는 순서를 본문에서 확인했다. 인증정보는 마스킹한 도구 결과로 전달했다. 페이지 제목만 찾은 것을 본문 읽기로 계산하지 않았다. 각각 Notion 요청 70·71건, 429 응답 0·1건이며 종료 사유는 `sufficient_evidence`였다.

별도 보조 질문 “Notion 문서만 이용해서 한투 조건검색 서버 관련 기록과 연결된 페이지의 본문을 읽고, 확인한 내용을 설명해줘.”는 **미완료**였다. 모델이 제목 검색을 선택해 109.4초를 썼고, 이후 현재 본문 확인에서 429가 발생했다. 이 실행은 142.2초에 `deadline`으로 끝났고 `list_notion_page_links`까지 진행하지 못했다. Notion 요청 178건·429 5건이었다. 페이지 탐색의 실 API 실행은 앞의 복합 질문 2·3회차에서 확인했지만, 이 보조 질문의 연결 문서 본문 읽기는 성공으로 기록하지 않는다.

## 남은 제한

비교차트의 실제 사용 가이드를 확보하는 것은 여전히 남았다. 현재 색인에 없는 본문, 고객사 조건을 충족하지 않는 일반 가이드, 모델의 후보 선택과 호출 상한을 나누어 추가 검증해야 한다. 일반 가이드를 찾기 위해 고객사 조건을 자동으로 해제하지 않았다. 제목 검색의 긴 API 조회와 429 대응도 보조 질문에서 재현됐다.

코드와 격리 검증까지 수행했으며 운영 서버 재시작·배포·커밋은 하지 않았다. 초기 색인 구축 및 갱신 명령은 [AGENT_HARNESS.md](../../assistant_web/docs/AGENT_HARNESS.md)의 “Notion 본문 의미 검색과 페이지 탐색” 절을 따른다.

구현한 링크 형태는 [Notion block 명세](https://developers.notion.com/reference/block)와 [rich text 명세](https://developers.notion.com/reference/rich-text), 로컬 임베딩 호출 형식은 [Ollama embed API](https://docs.ollama.com/api/embed)를 확인했다.
