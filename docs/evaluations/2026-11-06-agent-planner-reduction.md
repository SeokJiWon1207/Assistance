# 앞단 플래너 축소 및 한투 비교 검증

## 변경 범위

활성 에이전트 경로에서 별도 `plan_question` 호출을 제거했다. 앞단은 인증 사용자에게 묶인 서버 감사 문맥과 표시 순번을 복원한다. 에이전트가 `prepare_query`에 조건과 출력 목적을 제안하고 기존 검증기를 통과한 뒤 건수·목록·집계·본문 도구의 순서를 결정한다.

검증 전에는 데이터 도구를 노출하지 않는다. 검증된 일반 대화·쓰기·미도구화 보고서·특수 모집단 조회는 기존 실행기에 넘긴다. 조건 준비 실패나 예산 소진은 확인 필요 응답으로 끝나며 무검증 검색·생성으로 넘어가지 않는다. 기존 쓰기 권한과 전송 정책은 그대로다. 운영 재시작·배포는 하지 않았다.

## 미해결 조건 손실 보완

이전 실행은 집계 `group_by` 중복을 고치기 위해 전체 계획을 재생성하면서 `status.mode=open`을 `unspecified`로 바꿨다. 상태 누락 검사가 이를 차단한 것이 10월 집계 실패의 원인이었다.

새 도구는 첫 초안을 서버에 보관하고 보정 호출은 `changes`에 변경할 최상위 필드만 보낸다. `{"group_by":null}`만 고치면 상태·고객사·기간을 다시 생성하지 않는다. 중첩 객체와 배열은 해당 필드 전체를 교체하며, 기존 전체 검증을 재실행한다. 거부한 변경은 반영하지 않는다. 확정한 조건은 같은 요청 안에서 잠근다.

회귀 테스트는 집계 필드 보정 후 `open`, 한투, 10월 기간이 유지되는 것과, 보정에 상태 삭제를 명시하면 여전히 거부되는 것을 확인한다. 실제 복합 질문에서도 잘못된 중복 상태 필터를 거부한 뒤 `filters`만 고쳐 `open`을 유지하는 동작을 관찰했다.

## 검증 방법

- 비교 기준은 직전 1단계가 완료된 코드다. 이번 작업 시작 시 `runtime/agent-planner-reduction-20261106/before`에 코드·설정을 보존했다.
- 두 경로 모두 일반 `ChatService`를 호출했다. query shadow는 사용하지 않았다. 기존 코드와 변경 코드를 교대로 실행했다.
- 같은 원본에서 각 실행용 복제 저장본을 만들었다. 시작·후속·종료 시 Mantis와 Notion 유효성을 확인했다. Notion 기본 유효기간 7,200초를 늘리거나 갱신 시각을 고치지 않았다.
- Mantis 저장본은 2026-11-06 12:30:14 KST 갱신, 31,349건이다. Notion 목록 240개 DB의 갱신 시각은 11:47:48~11:50:09 KST다.
- 사전 승인된 Luna를 사용했다. 원문·인증정보 마스킹과 허용 목적지 검사를 유지했다. Mantis/Notion은 읽기 전용 요청만 허용했다.
- 원시 SQLite에서 프로젝트·현재 상태·등록일을 직접 읽어 정답을 별도로 계산했다. 미해결은 resolved/closed를 제외한 6개 상태다.
- 본 비교는 질문 3종 × 경로 2개 × 3회 = 18회이며, 복합 질문 뒤 순번 확인 6회를 추가했다. 예비 실행은 별도로 보관하고 반복 성적에 포함하지 않는다.

질문은 다음과 같다.

1. 전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.
2. 전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.
3. 2026년 10월 전사 한투 미해결 이슈를 매체별로 집계해줘. 표만 보여줘.

복합 질문의 후속은 “그중 두 번째 이슈 번호와 제목만 다시 알려줘.”다.

정답은 총 5건, 최근 순서 `31659 → 29186 → 28764`, 상태별 정보 부족 3건·할당된 이슈 2건, 10월 매체별 MTS 1건이다. 후속 대상은 #29186이다.

이번 변경 전 반복에서는 이전 보고서의 상태 손실 실패가 다시 발생하지 않았다. 따라서 성공률 향상을 입증한 비교로 해석하지 않는다. 변경 후 9개 본 질문 모두 조건을 보존했고, 별도 앞단 모델 호출 없이 같은 정답을 유지했다. 기존 실패 형태는 결정형 재현 테스트로 검증했다.

변경 후 복합 3회 모두 첫 제안이 상태를 잘못된 연산자로 필터에 중복했다. 기존 검증기가 거부하자 모델이 `changes.filters`만 제출했고, 최상위 `status.mode=open`과 고객사·범위·정렬·limit를 보존해 이어서 조회했다. 기간 집계 3회는 첫 제안으로 통과했다. 해석·보정·조회가 공통 에이전트 예산에 기록됐다.

| 본 질문 지연 | 변경 전 각 실행(초) | 변경 후 각 실행(초) |
|---|---|---|
| 복합 | 42.1 / 44.8 / 38.8 | 38.5 / 45.2 / 81.6 |
| 상태별 | 8.0 / 6.5 / 7.6 | 7.0 / 7.3 / 6.8 |
| 10월 매체별 | 7.7 / 9.6 / 7.3 | 8.0 / 7.1 / 6.5 |

속도 개선을 주장하지 않는다. 마지막 복합 실행은 Notion 추가 탐색으로 모델/도구 각각 14회를 사용했다. 상한 16회와 요청 마감 180초는 유지했고 호출/시간 한도로 중단된 실행은 없었다. 변경 후 두 번째 복합 실행에서 Notion 429가 2회 있었으나 재시도 후 본문 읽기를 완료했다.

18회 본 질문과 6회 후속 전체의 Luna HTTP 호출은 변경 전 44회, 변경 후 51회다. Notion 성공 응답은 64→109회, 429는 0→2회다. Gemini 전환이나 모델 HTTP 오류는 없었다. 기존 `agentReview.modelRequests`는 별도 앞단 해석 호출을 제외하지만 변경 후에는 조건 준비도 포함하므로 이 필드만 직접 비교하지 않았다.

복합 질문 6회의 전체 검증 표시는 모두 `warning`이다. 수치·순번·조건·원장 검사는 통과했고, 기존 `model_content_review`의 사람 검토 안내가 남아 있다. 이를 전체 검증 `pass`로 바꾸지 않았다. 두 집계 질문은 모든 실행이 `pass`다.

Notion 본문 읽기는 변경 후 3/3 완료했다. 다만 읽은 저장/불러오기·롤백 문서는 같은 7695 화면의 참고 자료이며, #29186의 화살표 메모 기능에 대한 직접 가이드로 확정할 수 없다. 마지막 실행의 QC 회의록도 기존 분류에서 가이드로 표시됐지만 직접 기능 가이드 성공으로 세지 않았다. 해당 자료는 조건 미적용 참고 영역에만 남겼다.

각 경로의 최종 코드가 실행 도중 변경되지 않았고, 18회 모두 같은 Mantis 저장본 해시를 사용했으며, 시작·종료 시 목록이 유효했음을 `final-provenance.json`으로 확인했다. `summary.json`, 실행별 `result.json`·마스킹된 `models.json`·`tools.json`은 저장소에서 제외되는 `assistant_web/runtime/agent-planner-reduction-20261106/`에 보관한다.

## 검증 기준 유지

`validate_plan`, `validate_execution_contract`, `check_clause`, `check_status`, 조회 수치·집계 검증, 집계 설명·문서 주장 검증, 원천 조건 대응 함수 12개가 변경 전과 AST 기준으로 같다. 모델 전송 정책 파일도 바이트 기준으로 동일하다. 기록은 런타임의 `preserved-validation.json`에 있다.

`assistant_web/scripts/check.sh tests compile shell ruff mypy`는 종료 코드 0이다. 테스트 3,160건, 커버리지 90%, mypy 291개 소스를 통과했다. 새 회귀는 검증 전 조회 차단, 부분 보정, 상태 삭제 거부, 확정 후 조건 변경 거부, 원천 비활성, 공통 예산, 기존 쓰기 권한, 최종 집계 표 변조 차단을 포함한다.

검사 과정에서 발견한 모듈 순환은 지원 범위 판정을 `eligibility.py`로 분리해 해소했다. 기존 검증 기준선은 갱신하지 않았다.

## 구조적 한계

현재는 요청 하나의 공통 조건 계약이며 `operation` 등 기존 호환 형식을 유지한다. 단계마다 서로 다른 조건으로 조회하는 재계획과 나머지 보고서 도구화는 후속 범위다. 활성 정책이 없거나 명시적 shadow인 경우에는 기존 앞단 플래너를 사용한다.

Notion 참고 본문을 읽었다는 사실과 해당 기능의 직접 가이드를 찾았다는 의미적 성공은 구분한다. 이번 구조 변경은 보류한 가이드 검색 품질 문제를 해결했다고 주장하지 않는다.
