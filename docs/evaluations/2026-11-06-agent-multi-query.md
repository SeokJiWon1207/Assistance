# 여러 조회 범위의 독립 검증과 비교

하네스 후속 작업 1번인 고객사·등록 기간별 독립 조회와 비교를 구현했다. 모델이 비교 범위와 도구 실행 순서를 정하고, 서버가 범위별 기존 조건 계약·원천 결과를 검증한 뒤 차이와 합계를 계산한다. 최종 코드의 실제 Luna 비교 9회와 기존 한투 질문 회귀가 통과했다.

## 구현

- `prepare_query.proposal.comparison={axis, cohorts}`로 고객사 또는 등록 기간 2~4개를 제안한다. 고객사는 현재 질문의 명시된 고객사 집합, 기간은 정확한 원문 구절과 기존 달력 계산으로 검증한다. 공통 미해결·담당자·팀·화면·키워드 조건을 각 단일 계획에 보존한다.
- 모델이 `query_scope_id=S1..S4`와 전체 조건으로 기존 건수·목록·집계 도구를 호출한다. 이후 같은 범위의 `condition_ref`를 사용할 수 있다. 범위를 생략하거나 다른 범위의 필터·참조를 섞으면 원천 실행 전에 거절한다. 순서는 서버가 고정하지 않는다.
- 각 범위의 원장을 별도로 보존한다. 조사용으로 좁힌 결과는 비교 총건수로 승격하지 않는다. 같은 범위의 건수·목록·집계는 실제 필터·정렬·표시 창·집계 기준이 같으면 저장본 스캔을 공유한다.
- 전체 일치 ID로 각 쌍의 차이(왼쪽−오른쪽), 단순 합계, 합집합 건수, 중복 집계분을 계산한다. 화면에 표시한 일부 목록이나 모델 초안의 수치를 사용하지 않는다.
- 하나라도 미조회·미완료이거나 요청한 목록·집계가 없으면 차이·합계는 미확정이다. 전체 조회를 마친 0건과 구분한다. 범위별 조건과 조회 완전성을 응답에 표시한다.
- 기존 `agent_query_result`, `agent_aggregation_result`, `agent_step_conditions`, 인용·전송 정책·조건 근거 검증을 유지하고 `agent_comparison_result`를 추가했다. 범위 계약, 전체 ID 집합, 같은 저장 시각, 계산과 표시 내용을 대조하고 오류는 전달을 차단한다.

주요 파일은 `backend/intent/comparison_contract.py`, `query_comparison.py`, `backend/services/agent/planning.py`, `query_comparison.py`, `orchestrator.py`, `backend/tools/query_conditions.py`, `step_conditions.py`, `registry.py`, `ledger.py`, `backend/evaluation/agent_comparison.py`다. 지원 범위 문서는 `assistant_web/docs/AGENT_HARNESS.md`에 있다.

## 비교 환경과 평가 기준

- 변경 전: 3단계 조건 검증까지 완료한 코드. 변경 후: 같은 코드 복제본에 이번 하네스 파일 17개만 교체했다. 작업 중 별도로 변경된 고객사 선택 UI·설정 등의 변경은 섞지 않았다.
- 동일 Mantis·Notion 저장본을 각 실행 폴더로 복제하고 실제 `ChatService` 일반 에이전트 경로를 실행했다. `AGENT_MODE_ENABLED=true`, query-shadow=false이며 운영 설정 변경·서버 재시작·배포는 하지 않았다.
- Mantis 저장 시각: **2026-11-06 13:44:54 KST**. Notion 240 DB의 가장 오래된 목록 갱신: **13:17:23 KST**. 시작·매 턴·종료에 최신성을 확인했고 목록 유효 시간 7,200초를 늘리지 않았다.
- 전체 Mantis JSON을 독립 SQL로 읽어 고객사 프로젝트와 미해결 6개 상태를 적용했다. 원천 엔진·모델의 건수를 정답으로 재사용하지 않았다. 고객사별 전체 ID, 등록 기간별 전체 ID, 상태별 수치와 실제 답변을 대조했다.
- 승인된 `gpt-6-luna`와 기존 마스킹·모델 전송 허용 목록을 적용했다. 외부 원천은 읽기·검색 요청만 허용했다. Gemini 폴백은 없었다.
- 최종 비교는 `legacy-*` 9회와 `verified-*` 11회, 각각 복합 질문의 후속 1회까지 **총 22응답**이다. 개발 중 실행한 `primary-*`, `final-*`와 사전 점검은 이 표의 최종 통과율에 포함하지 않았고 기록은 보존했다.
- 모든 선정 실행은 Mantis 저장본 SHA-256이 같고 실행 중 코드·Mantis 저장본 변경이 없었다. 최종 워크스페이스의 17개 하네스 파일은 실제 검증한 `after-verified/backend`와 바이트 단위로 동일하다.

질문은 다음과 같다.

1. 전사 한투와 KB의 미해결 이슈 건수를 각각 조회해서 비교해줘.
2. 전사 한투 미해결 이슈를 이번 달과 지난달 등록 건수로 비교해줘.
3. 전사 한투와 KB의 미해결 이슈를 상태별 건수로 비교해줘.
4. 전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.
5. 전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.
6. 복합 질문 후속: 그중 두 번째 이슈 번호와 제목만 다시 알려줘.

고객사별 상태 정답은 한투 **정보 부족 3, 할당 2**, KB **확인 4, 할당 1, 개발완료 1, 정보 부족 2**다.

개선된 고객사 비교에서는 **한투−KB=-3건**, 단순 합계·중복 제외 합계 모두 **13건**을 검증했다. 기간 비교에서는 **이번 달−지난달=-1건**, 합계 **1건**을 검증했다. 이번 달 0건은 전체 조회를 마친 결과다. 두 기간은 등록일 기준이며 현재 월의 종료일은 기존 달력 검증이 허용하는 오늘/말일 표현을 유지하고 응답에 실제 적용 기간을 표시한다.

변경 전 고객사 비교도 고객사별 그룹 집계로 숫자는 맞았다. 다만 독립 조건 계약과 명시적 차이·합집합 대조는 없었다. 변경 전 기간 비교는 한 번은 고객사를 누락하고 10월 전사 미해결 22건을, 한 번은 한투 10월과 9월의 비교를 답했으며 나머지 한 번은 조건 확인으로 끝났다. 앞의 두 응답은 내부 검증이 pass였지만 질문의 두 기간에 대한 정답은 아니었다. 이번 평가는 내부 pass 여부뿐 아니라 독립 SQL 정답과 요청 범위를 대조했다.

기존 단일 상태 집계의 변경 전 1회는 건수 5건만 답하고 요청한 상태별 표를 만들지 못했다. 이는 이번 표본의 결과이며 이전 측정 전체가 실패했다는 의미는 아니다. 모델 선택의 편차와 정답 기준을 함께 기록했다.

최종 9개 비교 응답은 모두 검증 pass·전달 allowed였다. 개선된 기간 1회차에서 모델이 불필요한 전월 집계 인자를 네 번 제안했지만 서버가 모두 거부했고, 모델이 유효한 건수·목록 도구로 바꾸어 완료했다. 미해결·한투·기간은 유지됐다. 최종 실행에는 429, 모델 장애, 시간·호출 한도 종료가 없었다. 실행 수가 서로 다르므로 전체 호출량을 직접 비용 개선으로 해석하지 않는다.

## 반복 검증 중 보완한 사항

1. 기간별 독립 비교에 기존 `aggregation.period` 형식을 함께 제안해 보정 루프에 머무는 문제가 있었다. 검증을 통과시키는 방향으로 완화하지 않고, 비교 계약에서는 `aggregation=null`, 단순 건수는 `operation=count`라는 구체적인 보정 방법을 반환했다. 비교 지침과 기존 집계 지침의 적용 범위도 명시했다. 같은 질문으로 최종 3회를 다시 수행했다.
2. 기존 복합 질문이 선택 필드 `comparison:null`을 보낸 경우에도 비교 계약으로 처리하는 회귀가 있었다. 비교 없음의 null은 기존 단일 계획 검증을 받도록 수정했다. 이미 제안한 실제 비교를 보정 중 null로 삭제하는 우회는 차단했다. 같은 한투 복합·후속 질문을 다시 실행해 통과했다.

두 문제는 먼저 실패하는 회귀 테스트로 확인한 뒤 수정했으며 원래 실패한 실제 실행 기록을 삭제하지 않았다.

## 결정형 검증과 남은 범위

- `assistant_web/scripts/check.sh tests compile shell ruff mypy` 통과. **테스트 3,200건, 커버리지 91%, mypy 297파일**. 프런트엔드 빌드 산출물 일치 검사도 통과했다. 의존성 변경은 없다.
- 새 비교 테스트 21건은 범위 누락·중복·없는 고객사·잘못된 날짜·미해결 누락, 부분 보정, 교차 범위 참조, 캐시 공유와 분리, 전체 ID의 겹침, 50개씩 표시하는 큰 목록, 완전한 0건·부분 0건·미조회, 조사 결과 격리, 그룹 집계, 숫자·범위·저장 시각 변조, 일반 복합 질문과 후속 경계를 검사한다. 라우팅 fixture 2개도 추가했다.
- 지원은 **고객사 또는 등록 기간 한 축의 Mantis 건수·목록·단일 그룹 이슈 건수 집계**다. 공수·다른 원천 간 합계·여러 축의 동시 비교·필수 조건 해제는 포함하지 않는다. 비교 후 생략된 조건/순번은 여러 목록에서 임의로 복원하지 않으며 이슈 번호 또는 조회 조건을 명시해야 한다.
- **Notion 기능 가이드 관련성은 기존 제한이 남는다.** 최종 복합 질문은 같은 7695 화면의 저장/불러오기·롤백 참고 문서 본문을 읽었다. #29186의 화살표 메모 기능을 직접 설명하는 가이드가 확인됐다는 뜻은 아니다. 복합 질문 통과는 건수·목록·순서·후속 제목 기준이며 원문과의 관련성 확대 작업은 이번 범위가 아니다. 최종 전체 상태 warning은 기존 `model_content_review=review` 때문이고 실패한 차단 검사는 없다.
- 운영 서버 재시작·배포·기본 활성화 설정 변경은 하지 않았다.

원시 증거는 로컬 `assistant_web/runtime/agent-multi-query-20261106/`의 `summary.json`, `score.py`, `final-provenance.json`, `source/freshness.json`, `offline-checks.log`, 각 실행의 `result.json`·`tools.json`·`models.json`에 있다. 원문을 포함한 런타임 파일은 커밋 대상이 아니다.
