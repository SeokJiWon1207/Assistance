# 조건 조회 기반 이슈 문서 작성 변경

본문 확보 후 반복 조회와 `oauthlib` 의존성 감사 실패를 보완했다.
같은 17건 인수인계 질문의 두 실행에서 문서 검증을 모두 마쳤으며, 상세 비교는 마지막 절에 기록했다.
이후 세 문서 종류와 0건·부분 조회·대량 결과·후속 질문으로 확대한 검증은
[2026-11-06 평가](2026-11-06-agent-document-matrix.md)에 별도로 기록했다.
확대 검증은 36개 조합 중 24개 성공이며, 사후 분석·고객 안내의 작성 단계 실패가 남아 있다.

## 확인한 원인

실제 감사 기록의 질문은 다음과 같다.

> 화면번호 0000 최근 8주 이슈를 개발팀에 전달할 수 있게 증상·고객사·재현 조건 중심으로 요약해줘

기록된 계획은 `mantis/report/handoff`이고 `issue_ids=[]`였다. 기존 채팅 서비스는 에이전트보다
결정형 보고서를 먼저 실행했고, 단일 이슈만 받는 문서 빌더가 결과를 반환하지 않자 단일 번호를
요구하는 확인 응답으로 종료했다. 문서 종류 분류 자체보다 실행 경로의 단일 이슈 제약이 문제였다.

추가로 해당 감사 기록의 최근 8주 기간은 `2026-09-01~2026-11-05`였고,
`terms=["증상", "고객사", "재현 조건"]`가 들어 있었다. 이 기간은 8주와 일치하지 않는다.

## 변경

- 허용된 에이전트 요청에서 인수인계·사후 분석·고객 안내 초안을 결정형 분기보다 먼저 처리한다.
- 모델이 검증된 조건으로 건수·목록을 조회하고 상세 본문을 읽는다. 이미 확인한 번호 최대 5개를 함께
  읽는 도구를 추가했다. 단일 호출과 같은 조건·출처 검증을 적용하며 원천 호출은 순차 실행한다.
- 모델이 작성한 문장에 같은 이슈의 원문 문단 ID를 연결하고, 수치·진행 단계·추정·고객 정보 검사를
  거친 뒤 별도 모델 호출로 의미를 대조한다. 이 두 호출도 기존 모델 예산에 포함한다.
- 목록을 읽었더라도 문서 작성·검토용 호출과 시간을 예약한다. 목록만으로는 본문을 읽은 것으로 세지 않는다.
- 전체 조회 0건, 조회 미완료, 본문 확보, 문장 검증 범위를 구분한다. 표시 개수 미지정 시 후보 최대 20건이며,
  한도 때문에 일부만 확인한 경우 완전한 문서로 표시하지 않는다.
- 최근 N주는 오늘을 포함한 N×7일로 서버에서 대조한다. 특정 번호의 노트 기간을 이슈 등록일로 바꾸지는 않는다.
- 문서 출력 항목은 검색어로 사용하지 않는다. 새 문서 계획의 검색 주제는 근거가 있는 구조화된 필터로 지정한다.
- 고객 안내문 본문에는 내부 번호·담당자·경로·코드를 넣지 않는다. 조회·검증 근거는 별도 응답과 감사 메타로 남긴다.

| 범위 | 기존 기본 팀 범위 |

필드 또는 제목 표기를 각각 인정한다. 이 계약에 맞춰 독립 대조를 수정했으며 화면 검색 동작은 변경하지 않았다.

이 결과는 실제 데이터 조회의 정확성을 확인한 것이며 실제 모델의 문서 품질 검증 결과는 아니다.

## 승인 후 실제 모델 반복 검증 (2026-11-06)

처음에는 최근 8주 원문의 외부 전송이 기존 승인 범위를 벗어나 자동 승인 심사에서 거절됐다.
사용자가 대상 17건의 원문을 Luna로, 장애 시 기존 허용 Gemini로 전송하는 3회 검증을 명시적으로 승인한 뒤 실행했다.
세 번 모두 실제 `ChatService.build_response`를 호출했으며 Luna만 사용했다. Gemini 폴백은 발생하지 않았다.

비교 대상 17건을 유지하기 위해 질문의 기준일은 2026-11-05로 고정했다. 각 실행은 같은 목록 저장본과
도구 검증 기록을 별도 런타임에 복제했다. 목록 저장본의 갱신 시각은 `2026-11-05T09:13:26.928524+00:00`이다.
검증 당일에는 이미 오래된 저장본이므로 **과거 기준 저장본 재생**으로 측정했다. 저장본 조회에만 갱신 후 60초의
기준 시계를 적용했고 메타데이터·TTL·HTTP 제한 시간·요청 전체 마감은 바꾸지 않았다. 각 복제본의 파일 해시도 유지됐다.
따라서 아래 수치는 현재 운영 저장본의 최신성이나 운영 환경 전체 성능을 입증하지 않는다.

목록은 고정 저장본으로 조회하고 상세 원문은 실행 시점 Mantis API로 읽었다. 네트워크 가드는 승인된 17개 번호의
상세 GET과 기존 허용 모델 주소의 POST만 허용했다. 세 번 모두 상세 API 17회가 성공했고 429는 없었다.

| 회차 | 적용한 변경 | 소요 시간 | 전체 조회 / 원문 확보 | 검증 문장이 있는 이슈 | 에이전트 모델 / 도구 호출 | 조사 종료 |
|---|---|---:|---:|---:|---:|---|
| 1 | B안 최초 구현 | 50.89초 | 17 / 17 | 7 | 16 / 13 | `call_limit` |
| 2 | 읽기 진행 상태·발췌 분배 보완 | 36.99초 | 17 / 17 | 16 | 8 / 5 | `sufficient_evidence` |
| 3 | 누락·거절 이슈의 1회 보정 추가 | 48.97초 | 17 / 17 | 16 | 12 / 6 | `sufficient_evidence` |

모델 호출 수는 에이전트 예산 기준이며 각 실행의 앞단 계획 호출 1회는 별도다. 1회차 도구 요청은 15회였고,
그중 동일 인자 재호출 2회는 실행 전에 거절돼 도구 예산에 산입되지 않았다. 회차 사이에 수정을 적용했으므로
이 결과를 같은 최종 버전의 3회 성공률로 해석하면 안 된다.

세 번 모두 화면번호·56일 기간·기본 팀 범위를 유지했으며 독립 대조의 17개 ID와 정확히 일치했다.
단일 이슈 번호를 요구하는 응답은 발생하지 않았고 `agent_issue_document` 경로로 문서를 작성했다.
다만 최종 문서 판정은 세 번 모두 `partial`, `complete=false`, `retrievalOutcome=partial_evidence`였다.
`sufficient_evidence`는 조사 단계의 종료 사유이며 모든 요약 문장이 검증됐다는 뜻이 아니다.

### 반복 검증 중 보완한 내용

1. 원문을 이미 읽었는데 표시용 도구 응답의 잘림을 보고 다시 읽는 흐름을 확인했다. 원장이 누적한
   `document_progress`를 잘리지 않는 메타로 전달하고 남은 후보만 읽도록 했다. 2·3회차에는 호출 한도로 끝나지 않았다.
2. 1회차의 본문 미완료 2건은 원천 읽기 실패가 아니었다. 전체 안전 발췌는 15,303자로 기존 30,000자 한도 안이었지만
   이슈별 균등 분할 때문에 긴 이슈 2개가 잘렸다. 전체가 한도 안일 때 남는 공간을 공유하도록 고쳤고
   2·3회차의 `incompleteBodyIds`는 빈 목록이었다.
3. 초안에서 빠지거나 문장이 거절된 이슈는 남은 예산 안에서 한 번 재작성하고 다시 독립 검토한다.
   재검토에도 실패한 문장을 강제로 채택하지 않으며, 기존에 검증된 문장은 보존한다.
4. 검증된 요약이 없는 이슈도 제목·고객사를 표시하고 요약 검증 보류로 남긴다. 이 표시 수정은 3회차 이후 적용했다.
   저장된 초안·검토 응답 4개를 네트워크 차단 상태에서 재생해 원래 입력과 판정이 동일한지 대조했고,
   17개 제목 표시·16개 이슈의 검증 문장·1개 이슈의 보류 표시를 확인했다. 추가 실모델 호출은 하지 않았다.

### 초기 3회 검증에서 남았던 한계

- 마지막 실행에서 KB증권 소스 동기화 요청 `#31505`는 원문을 확보했으나 초안에서 누락됐다.
  보정 문장도 독립 검토에서 거절되어 요약을 보류했다. 검색 누락이나 본문 읽기 실패가 아니다.
- `#31699`는 증상 문장은 통과했지만 재현 조건 문장이 거절됐다. 보정에서도 완전히 검증된 이슈로 복구하지 못했다.
  따라서 “16건 검증”은 각 이슈에 검증된 문장이 있다는 뜻이며, 요청한 모든 항목이 채워졌다는 뜻은 아니다.
- 3회차의 미해결 검증 이슈는 `#31699`, `#31505`다. 원문과 문장 검토기의 판단을 더 대조할 여지가 있다.
  이번 변경에서는 정확성 검증을 완화하거나 해당 문장을 통과 처리하지 않았다.

실행 원본은 `assistant_web/runtime/agent-document-fix-20261105/approved-{1,2,3}/result.json`,
최종 표시 재생 결과는 같은 경로의 `approved-3/final-render-replay.json`과 `.md`에 보관했다.
원문이 포함된 실행 산출물은 런타임에만 두며 커밋 대상에 포함하지 않는다.

## 거절 문장 보완 재검증 (2026-11-06)

사용자가 두 보류 항목을 보완하고 같은 질문으로 다시 실행하도록 요청했다. 기준일·기간·팀 범위·17개 ID·
과거 기준 저장본 재생 방식은 위와 같으며, 데이터 전송도 기존에 승인된 모델과 원문 범위로 제한했다.

### 원인 대조

- `#31505`: 원문 본문에 차트 소스 동기화를 위한 소스 전달이 기록돼 있다. 초기 초안에서 빠졌고 보정 문장은
  의미 검토에서 거절됐다. 당시 응답에는 `false`만 있고 사유가 없어 정확한 내부 판단 이유는 복원할 수 없다.
- `#31699`: 재현 필드에 조작 순서와 **재현 확인 중** 상태가 실제로 있다. 초기 재현 문장은 의미 검토에서 거절됐다.
  이후 보정은 재현 조건을 비웠으며, 대신 쓴 증상 문장에는 인용한 문단에 없는 `HTS`를 넣었다.
  이 보정 문장은 기존 숫자·영문 근거 검사에서 `unsupported_literal`로 차단된 것을 재현했다.
- 이전에 거절된 두 의미 검토 문장을 같은 원문으로 다시 대조하되 거절 사유도 요청했을 때는 둘 다 통과했다.
  원문 누락이 아니며 판정 편차가 관찰됐다는 근거다. 이 진단 호출의 통과 판정을 기존 답변에 덮어쓰지는 않았다.
- 재작성에는 정적 검사에서 거절된 문장과 의미 검토의 사유가 전달되지 않았다. 또한 항목이 아니라 이슈 전체를
  교체해 이미 검증된 증상을 잃거나, 거절된 재현 조건을 비워도 이슈가 복구됐다고 판정할 수 있었다.

### 보완한 처리와 검증 기준

1. 작성·검토에 동일한 항목 정의를 전달한다. 작업 요청은 요청으로, 확인 중인 재현 절차는 그 상태를 보존해 쓴다.
   각 문장이 쓰는 숫자·영문 용어도 실제 인용한 문단에 연결한다.
2. 공통 문장 검사의 조건은 그대로 두고 거절 코드도 반환하도록 바꿨다. 의미 검토는 불리언 판정과 함께
   거절 구절·사유를 받는다. 사유가 있어도 `false`를 통과로 뒤집지 않으며 원문 대조를 다시 거친다.
3. 보정에 문장·항목·문단 ID·거절 단계·사유를 전달하고 항목 단위로 병합한다. 기존 검증 문장을 보존하며,
   거절된 항목을 생략하거나 비우면 미해결로 유지한다.
4. 추가 대조에서 프로젝트 고객사명을 원문의 발신자로 쓴 문장을 발견했다. 고객사는 서버가 별도로 표시하고
   작성 입력에서 해당 메타를 제외했다. 문장에 고객사명이 있으면 인용 문단에서도 확인하도록 검사한다.
   중간 실행 2회차의 초안을 재생했을 때 인용 문단만으로 고객사 주체를 확인할 수 없는 7문장이 이 검사에서 차단됐다.
5. 고객사 보완 후의 실행에서는 요청하지 않은 원인·조치까지 길게 작성하다가 초안이 출력 한도에서 잘렸다.
   잘린 초안을 채택하지 않은 실패도 기록했다. 질문에서 요청한 항목만 작성하게 하고, 예산이 충분할 때 한 번
   축약 재작성한 뒤 독립 검토한다. 요청·출력·호출 한도는 늘리지 않았다.

### 기준 유지 대조

- 저장된 실제 초안 문장 58개를 변경 전 공통 검사와 변경 후 검사에 입력했다. 통과 57개·거절 1개로

  정적 검사에서, 재현 확인 중을 재현 완료로 바꾼 문장은 독립 의미 검토에서 각각 거절됐다. 잘못된 대조 문장 통과는 0개다.

  원인을 추측하지 않게 했다. 검증 기준을 통과하지 못한 문장은 계속 본문에서 제외한다.

`retrievalOutcome=sufficient_evidence`와 완전한 문서 판정을 얻었다. **반복 호출 비효율까지 해결된 것은 아니다.**

## 후속 작업: 반복 조회 종료와 의존성 감사 (2026-11-06)

### 반복 조회 원인과 변경

기존 최종 실행은 다섯 번째 도구 호출에서 17건 본문을 모두 확보한 뒤에도 상세 조회를 아홉 번 더 요청했다.
원천 API는 요청 내 저장된 원문을 재사용했지만 조사 모델·도구 예산은 계속 소진됐다. 완료 상태를 모델에 알려 주는
프롬프트만으로는 반복을 확실히 끝내지 못했다.

Mantis 단독 문서 요청은 다음 조건이 충족되면 서버가 조사 루프를 종료하고 기존 작성·독립 검토로 전환한다.

- 확정 조건의 조회가 완료됐고, 표시 대상 모두가 조건 적용 등급의 상세 읽기로 확인됐다.
- 각 상세의 본문 근거가 완료됐으며 사용할 수 있는 발췌가 있다. 제목만 읽거나 부분 본문이면 해당하지 않는다.
- 완전한 0건도 바로 마무리한다. 조회 미완료와 Notion 포함 요청은 이 종료 조건을 적용하지 않는다.

`document_progress`에 본문 미완료 목록과 `all_listed_complete`를 추가했다. 단계 전환은 감사에
`collection_complete / document_bodies_ready`로 남긴다. 문장 검증·최종 예약·모델/도구/시간 한도는 유지한다.
표시 한도 때문에 전체 결과 중 일부만 읽었으면 문서의 부분 범위 판정도 유지한다.
