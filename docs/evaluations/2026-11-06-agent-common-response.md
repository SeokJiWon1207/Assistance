# 공통 응답 흐름과 남은 읽기 라우팅 정리

하네스 개선 3번으로 결과 수집·설명·최종 조합을 공통 흐름에 연결했다. 모델은 조회 도구와 설명할 원천·표시 순서를 정하며, 서버는 각 결과의 기존 조건·원문·수치 검증을 유지한다. 실제로 본문까지 읽고도 속성 결과만 반환하던 Notion 요청은 이제 속성과 검증을 통과한 본문 설명을 함께 반환한다.

## 구현

- `prepare_query`에 `answer_sections`, `explanation_sources`를 추가했다. 결과 부분을 생략하거나 임의 문구를 넣을 수 없으며, 설명 원천은 검증한 계획의 원천 안에서만 선택한다. 보정 시 고객사·미해결 등 기존 조건을 보존한다.
- `_finish`의 첫 결과 우선 종료를 결과 부분 수집으로 바꿨다. 보고서+추가 목록, 보고서+원문 설명, Notion 속성+본문을 함께 보존한다. 단일 부분은 기존 응답 모드, 복수 부분은 `agent_composed`를 사용한다.
- `response_parts.py`가 서버에서 내용·출처·기존 검증 모드를 기록한다. `agent_response.py`는 각 부분의 기존 검증기를 다시 실행하고, `agent_response_composition`은 최종 조합의 추가·누락·변조를 차단한다. 원래 건수·집계·보고서 수치를 모델 초안으로 재작성하지 않는다.
- 현재 본문을 읽지 않은 Notion 후보·속성을 본문 근거로 사용하지 않는다. 설명 근거가 부족하면 확인한 결과와 설명 보류를 함께 표시한다. 사후 원문 접근이 철회되면 앞서 만든 결과도 함께 보류한다.
- 자유 설명은 고정된 세 제목 대신 문단·목록을 허용하되, 기존 인용 원장·참고 등급 검사와 검증 실패 문장 제외를 유지한다. 인용 원문에 없는 수량과 단위 없는 숫자도 제외한다. 이슈 번호는 기존 ID 대조·인용 보정 검사가 처리한다.
- 일반 경로와 shadow의 읽기 지원 판정을 `eligibility.py`로 모았다. Mantis 단건 읽기와 일반 설명에도 조회 도구를 연결하고, 관련 Notion 도구는 질문 정규식 대신 검증한 원천·사용자 설정으로 연결한다.
- 목록 순번은 실제 번호 목록을 기준으로 감사·후속 질문에 전달한다. 보고서와 설명의 출처 순서가 후속 질문의 “두 번째”를 바꾸지 않는다.
- 비교가 없는 질문에서는 도구 정의의 `query_scope_id`를 숨긴다. 비교 질문에는 해당 원천의 실제 범위 ID만 노출한다. 임의로 보낸 범위는 실행 단계에서도 계속 거부한다.

인증된 순번 복원, 일반 대화·쓰기·미지원 보고서의 기존 경로, 원천 접근 제한, 모델 허용 목록·마스킹·요청 예산은 유지한다. 모든 정규식이나 레거시 처리를 제거한 변경은 아니다.

## 실제 비교 방법

- 변경 전은 이번 작업 시작 시점의 코드다. 최종 복제본 `after-complete`에는 이번 작업의 백엔드 **10개 파일만** 반영했고, 현재 작업 파일과 바이트 일치를 확인했다. 다른 작업의 UI·설정은 비교에 섞지 않았다.
- 실행별 독립 런타임에서 실제 `ChatService`를 사용했다. query-shadow는 false다. 변경 전후 모두 일반 에이전트 경로이며, 이전 단계의 서버 중심 레거시 경로와 비교한 것은 아니다.
- Mantis 저장 시각은 **2026-11-06 16:04:34 KST**, Notion 240개 DB의 가장 오래된 목록 갱신은 **14:59:14 KST**다. 시작·매 턴·종료에 최신성을 검사했고 TTL **7,200초를 늘리지 않았다**. 최종 선정 실행에서 Notion 목록 나이는 5,665~5,869초였다.
- 동일 Mantis 저장본을 읽는 독립 SQL로 고객사·미해결 상태·정렬·상태별 정답을 계산했다. 원천 저장본은 실행 중 변경되지 않았으며 모든 선정 실행의 SHA-256이 같았다.
- 승인된 Luna(`gpt-6-luna`)와 기존 전송 정책을 사용했다. 최종 선정 실행은 모델 요청 40회가 모두 HTTP 200이었고, Gemini 폴백과 429·HTTP 오류는 없었다. 초기 변경 전 속성+본문 실행에는 Notion 429 1회가 있었다.

질문은 이전 단계와 같은 한투 복합·후속·집계 질문이며, 본문 누락 확인에는 이미 읽었던 같은 Notion 가이드만 사용했다.

1. `전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.`
2. 각 복합 질문의 후속: `그중 두 번째 이슈 번호와 제목만 다시 알려줘.`
3. `전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.`
4. `노션에서 제목이 "eFriend Force 저장/불러오기 연동되지 않는 현상 원인 및 개선 후 영향도 정리"인 문서의 상태와 담당자 속성, 본문 내용을 함께 설명해줘.`

## 최종 결과

최종 코드 `complete-*`의 5개 실행 묶음, 후속 질문 포함 **8응답**을 변경 전 `legacy-*`의 같은 8응답과 비교했다. 최종 반복은 모두 같은 코드이며, 개발 중 중간 버전을 최종 통과 표본에 섞지 않았다.

| 항목 | 독립 기준 | 변경 전 | 최종 코드 |
| --- | --- | ---: | ---: |
| 한투 미해결 건수와 조건 | 전사·한투·미해결, 전체 5건 | 3/3 | 3/3 |
| 최근 목록·표시 순서 | #31659 → #29186 → #28764 | 3/3 | 3/3 |
| 두 번째 후속 번호·제목 | #29186 및 원문 제목 | 3/3 | 3/3 |
| 관련 참고 본문 읽기 | 현재 본문 읽기 완료·두 번째 이슈 연결 | 3/3 | 3/3 |
| 상태별 집계 | 정보 부족 3, 할당된 이슈 2 | 1/1 | 1/1 |
| Notion 속성+본문 동시 응답 | 현재 속성과 본문 설명을 모두 표시 | 본문 누락 | 1/1 |

최종 8응답 모두 `sufficient_evidence`로 종료했고 최종 검증에 fail은 없었다. 복합·후속 응답에는 기존 `model_content_review=review`가 남는다. Notion 속성+본문 응답에는 전체 탐색의 `search_completeness=warning`과 서술 검토 표시가 남으며, 실제 대상 문서의 현재 본문 읽기는 완료했다. 원문 접근·단계별 조건·수치 검증을 통과한 것과 모든 서술의 의미를 보증하는 것은 구분한다.

Notion 본문 설명에는 `ChartIndex.dat` 저장 목록 공유와 저장 파일 분리·변환 영향이 남았다. 초안의 **3문장은 인용 또는 수치 대조를 통과하지 못해 제외**했고, 그 안내도 최종 답변에 유지했다. 속성만 조회한 것을 본문 읽기로 간주하거나 제외한 문장을 통과로 바꾸지 않았다.

최종 복합 2회차에서 모델이 조건 참조와 조사 목적을 맞지 않게 보낸 도구 호출 1회는 기존 검증이 거부했다. 이후 올바른 인자로 다시 조회해 완료했다. 후속 질문에서 발생했던 불필요한 비교 범위 오류는 최종 3회에 재발하지 않았다.

**가이드 관련성의 기존 한계는 남는다.** 읽은 문서는 같은 7695 화면의 저장/불러오기·롤백 참고 자료이며, #29186의 화살표 메모 기능을 직접 설명하는 가이드를 찾았다는 뜻은 아니다. 참고 등급과 상태 조건 미적용 표시를 유지했다. 앞서 미뤄 둔 검색 관련성 문제를 이번 변경으로 해결했다고 보지 않는다.

## 개발 중 발견과 보완

1. 초기 공통 조합은 Notion 가이드만 설명하면 되는 질문에서 Mantis 설명까지 생성해 호출 한도에 도달했다(`primary-compound-1/2`). 모델의 `explanation_sources`로 설명 대상을 명시하고, 현재 읽은 참고 가이드는 기존 검증된 발췌로 표시하도록 보완했다.
2. `primary-compound-3`, `verified-compound-2`, `final-compound-1`의 후속 질문은 실제로 실패했다. 단건 도구 정의에도 비교 범위 인자가 노출돼 모델이 없는 `S1`을 반복 제출했다. 요청별 도구 정의와 보정 안내를 수정한 뒤 `complete-compound-*` 3회 모두 통과했다. 성공한 앞 질문만 보고 이 중간 실행들을 통과로 계산하지 않았다.
3. 보고서·설명 출처가 번호 목록의 후속 순서를 오염시킬 수 있어 목록을 순번 기준으로 고정했다. 원문 접근 철회 시 앞 부분도 보류하며, Notion 설명 검증은 유효한 실행 계약의 구조화 조건을 재사용한다.
4. 단위 없는 숫자 검사를 추가했을 때 `#이슈번호`까지 수량으로 중복 처리해 기존 인용 보정을 건너뛰는 회귀가 있었다. 이슈 ID 검증과 수량 검증을 분리하고, 잘못된 ID와 같은 문장에 있는 임의 수량은 여전히 차단함을 확인했다.

개발 중 결과와 실패 로그는 그대로 보존했다. `score.py`는 각 결과를 SQL 정답·현재 본문 읽기·최종 표시·후속 제목과 대조하며, 최종 판단은 `complete-*`로 한정한다.
