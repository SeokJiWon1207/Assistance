# 고객사 변경 후속의 표시 개수 보존과 반복 검증

고객사 변경 후속에서 최근 3건 대신 전체 5건을 표시하던 문제를 수정했다. 같은 한투·KB·NH 질문을 순차 1개/병렬 2개, 각각 3회, 총 72응답으로 재검증했다. 고객사 변경 후속은 순차 9/9·병렬 9/9건에서 요청한 최근 3건을 표시했다. 건수·ID·순번·집계는 모두 정답과 일치했고 기존 검증과 승인 범위 차단을 유지했다. 전체 완료는 두 방식 모두 27/36이며 Notion 직접 가이드 미확인 18응답은 계속 미완료로 남겼다.

## 확인한 원인

직전 비교의 순차 1회차에서 NH 조회 뒤 “고객사만 한투로 바꿔서 전체 건수와 최근 3건을 다시 보여줘.”라고 요청했다. 계획은 `limit=200`이었고, 고객사·미해결·전사 범위는 맞았다. 최종 목록은 `[31659,29186,28764,26654,24182]`로 5건이 표시됐다. 기대 목록은 앞의 3건이다.

계획 검증은 개수의 허용 범위만 검사했다. 후속 질문에 새 개수가 명시되면 이전 개수와의 동일성 검사를 생략했지만, 새 개수와 계획 값의 일치는 검사하지 않았다. 도구 계약과 최종 수치 검증도 잘못 확정된 계획의 200을 우선했다. 계획·도구·답변이 서로 일치해도 사용자 요청과 어긋나는 경우였다.

감사 기록으로 직접 확인한 사실은 계획 200 수락, 도구 조건 오류, 최종 5건 표시와 제품 검증 통과다. 당시 첫 도구 인자의 실제 값은 기록에 없으므로 3이었다고 단정하지 않는다. 별도 오프라인 재생에서 기존 계약에 올바른 인자 3을 넣으면 “확정된 표시 개수 limit=200” 오류로 거절됨을 확인했다.

재생은 이전 응답과 감사 계획을 그대로 사용하고, 직렬화에서 생략된 목록 행만 기록된 `followupSources`에서 복원했다. 네트워크는 차단했다. 수정 전에는 잘못된 계획과 5건 답변이 모두 통과했다. 수정 후에는 계획 수락·원천 실행·최종 표시 검증에서 차단됐다. 개수만 3으로 고치면 기존 고객사·미해결·전사 조건을 보존한 채 실행 계약을 만들 수 있었다.

## 변경한 계약

1. 현재 질문에 명시한 Mantis 표시 개수를 공통 함수에서 읽고 계획 확정, 실행 직전, 도구 인자, 최종 목록 대조에 연결했다. 모델이 제안한 값이 틀리면 자동 덮어쓰지 않고 해당 값만 보정하도록 오류를 돌려준다.
2. 보정 안내에 개수만 수정하고 고객사·미해결·범위·정렬을 보존하도록 명시했다. 이전 목록 조건과 상세 대상의 분리는 유지했다.
3. 전체 건수는 표시 개수로 자르지 않는다. 건수 계획의 `limit=None`에서도 목록 도구는 요청한 3건을 사용한다. 결과가 0건 또는 2건이면 실제 건수만 표시한다.
4. 50건 표시 요청과 기존 검색의 기본 20건 상한을 구별한다. `최근 150건 기준` 모집단, 인용된 제목의 숫자, 전체 결과를 가리키는 `그 16건을 하나씩`, 뒤에 요청한 Notion 문서 개수를 Mantis 표시 개수로 쓰지 않는다.
5. 사용자가 5건이나 전체 목록으로 명시적으로 변경하면 허용한다. 기존 조건·근거·수치·인용·최종 전송 검증, 모델 허용 목록, 마스킹, 승인 ID 차단은 변경하지 않았다.

특정 고객사나 3건을 제품 코드에 고정하지 않았다. 기존 개수 해석 함수를 재사용하면서 검증 책임을 공통화했다. 모든 자연어 표현을 새로 해석하는 기능까지 추가한 변경은 아니다.

병렬 1회차 NH는 `call_limit`, 2회차 NH는 `deadline`으로 추가 탐색이 멈췄고, 확보된 조회 결과를 공통 응답으로 반환했다. 각 지연은 76.90초·133.15초였다. 순차에서도 본문 도구 1회가 호출 한도로 실행되지 않았다. 이 종료 사유나 본문 부족을 성공으로 바꾸지 않았다. 나머지 `sufficient_evidence` 종료 역시 직접 가이드 확보를 뜻하지 않으며, 요청 항목별 평가에서는 미완료를 유지했다.

## 검증 계약과 운영 적용

- 모든 요청 전후 저장본 최신성 검사를 통과했다. Notion 목록 나이는 최대 5,967초로 기존 7,200초 이내였다.
- 여섯 실행의 코드·설정·초기 저장본·가격표가 일치하고 동시 도구 수만 달랐다. 이번 제품 변경 10파일은 최종 작업 공간과 해시가 같다. 공유 작업 공간의 다른 변경까지 실측했다는 뜻은 아니다.
- 승인된 27개 ID 차단기는 활성화 상태였고 범위 밖 조회 시도는 0회였다. 조회 조건을 승인 목록으로 교체하거나 틀린 결과를 제거하지 않았다.
- 최종 조건·근거·수치·단계별 조건·전송·인용 검사에는 실패 표시가 없었다. 독립 검토가 필요한 `model_content_review=review` 표시는 그대로 유지했다. 제품 검증 통과를 직접 근거 확보나 전체 요청 완료로 간주하지 않았다.
- 표시 개수 수정은 반복 검증을 통과했지만 운영 확대의 전체 기준은 미충족이다. 직접 가이드 확보 0/18, 전체 완료율 75%, 복합 질문의 p95 지연, 순차 평균 비용의 직전 기준선 대비 120% 기준 초과가 남는다. 12개 고유 질문의 반복은 기능별 100개 독립 표본·7일 관찰을 대체하지 않는다. 운영 플래그·배포는 변경하지 않았다.

회귀 9개를 먼저 실행했을 때 목표 실패 7개가 재현됐다. 수정 후 관련 103개와 추가 경계 26개가 통과했다. 라우팅 fixture에는 고객사 변경 사례 3개를 추가했다. 잘못된 계획·부분 보정·실행 직전 변조·최종 목록이 같은 잘못된 값에 동의하는 경우를 각각 검사한다.

`assistant_web/scripts/check.sh tests`의 3,442개 Python 테스트 중 프런트엔드 Node 묶음 1개가 실패했다. 해당 묶음의 실패는 이번 변경 범위 밖의 고객사 카드·빈 상태·검색 초기화·이슈 화면 배치 4건이다. 이 작업에서는 해당 UI나 테스트를 수정하지 않았다. 전체 테스트 및 커버리지 통과를 주장하지 않는다. 컴파일·셸·Ruff와 mypy 327파일은 통과했다. 실측 종료 후에도 해당 UI 파일의 해시는 같아, 변경 없는 실패 검사를 반복하거나 이 작업에 포함해 수정하지 않았다.
