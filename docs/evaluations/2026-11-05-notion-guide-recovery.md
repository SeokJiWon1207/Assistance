# Notion 가이드 탐색·요청 제한 보완 검증 — 2026-11-05

후속 조사와 수정 후 반복 결과는 [미수집 본문·연결 페이지 재검증](2026-11-05-notion-body-discovery.md)에 기록했다. 아래는 이 보고서 실행 당시의 결과다.

동일한 한투 복합 질문을 최신 목록으로 3회 실행했다. 건수·최근 3건·후속 순번 답변은 모두 정확했고 429·호출 한도 중단은 없었다. **비교차트 가이드 본문은 3회 모두 확보하지 못했다.** 한투 조건검색 서버 접속 가이드는 보조 질문 2회 모두 현재 본문까지 읽었다.

건수·목록 정확도, 관련 가이드 본문 확보, 중단 사유는 각각 판정한다. 단순한 제목 발견이나 다른 기능의 처리 기록은 가이드 확보 성공이 아니다. 이번 결과는 탐색 중단 완화와 서버 가이드 읽기 성공을 보여주지만 비교차트 가이드 누락의 해결을 입증하지는 않는다.

## 변경

- 저장된 본문의 벡터 순위와 제목·본문 키워드 순위를 결합한다. 본문이 아직 수집되지 않은 제목 후보도 포함하며, 키워드가 일치하는 이슈가 많아도 의미가 가까운 설명서가 전부 뒤로 밀리지 않게 했다.
- 검색 단계는 현재 API의 접근·소속·속성을 검증한다. 모든 후보의 본문을 미리 읽지 않고 모델이 선택한 페이지를 `get_notion_page_content`로 읽는다. 저장본의 `candidate_hint`는 후보 선택용이며 최종 근거·인용에서 제외한다. 같은 요청에서 확인한 후보와 본문은 조건을 대조한 뒤 재사용한다.
- `reference_scope=common`은 목록에서 선택된 이슈의 기능에만 허용한다. 고객사 조건을 적용하지 않은 공통 자료임을 표시하고 `reference` 등급을 유지한다. 이슈 건수·목록 조건, 다른 문서 조건, 허용 DB 범위는 보존한다. 선택 순번이 없거나 Notion 단독 질문이면 공통 범위로 바꿀 수 없다.
- 제목 POST와 본문·속성 GET의 `Retry-After`를 공통화했다. 같은 호스트의 동일 연결은 프로세스 간에도 요청 간격·대기를 공유한다. 429·529 후 대기를 유지하며, 남은 예산으로 기다릴 수 없으면 조회 미완료로 반환한다. 일시 실패는 ref를 유지해 재시도하되 이전 본문은 근거에서 내린다.
- 기본 모델·도구 상한을 각각 8회에서 16회로 늘렸다. 요청 한도 180초는 유지한다. 서버가 건수·목록 원장으로 최종 답변을 만들 수 있으면 모델 예약 2회를 조사에 돌려주고 최종 처리 예약은 5초만 남긴다. 일반 설명의 인용 검증 예약은 유지한다.
- 가이드 판정에서 ‘종목·데이터·되지·않는’ 같은 공통 단어를 기능 근거로 쓰지 않는다. 중간 검증에서 IBK 맵차트 처리 기록이 비교차트 가이드로 판정된 사례를 재현해 회귀 테스트로 막았다. 해당 중간 실행은 성공 실적에서 제외한다.
- 설명 주제를 근거 없는 `title equals/contains` 조건으로 바꾸는 계획을 거부한다. 재해석할 때 실패한 JSON과 구체적인 수정 지침을 모델에 전달한다. 실제로 인용한 제목과 명시적인 제목 조건은 유지한다.

## 환경과 데이터

격리 경로: `assistant_web/runtime/two-week-regression-20261104-155759/notion-guide-recovery-20261105/`.

Notion은 읽기 API만 사용했다. 승인된 Luna를 사용하며 본문 임베딩은 기존 로컬 Ollama `bge-m3:latest`를 사용한다. 운영 저장본·서버 설정은 수정하지 않았다.

240개 DB 목록의 갱신 시각은 2026-11-05 14:58~15:01 KST다. 유효기간은 기존 7,200초 그대로다. DB 목록 밖의 하위 페이지 속성은 192건 갱신했고 4건은 완료하지 못했다. 따라서 전체 유지보수 결과는 `incomplete`, DB 목록 최신성은 `fresh`이며 둘을 혼동하지 않는다. 반환할 후보는 실행 중 현재 API로 다시 확인한다.

목록 색인은 16,808페이지이며, 본문 의미 색인은 수집된 비어 있지 않은 본문 3,422페이지·4,717구간이다. 전체 페이지의 본문 수집 완료를 뜻하지 않는다. 최종 6회 실행의 코드와 시작 저장본 지문이 모두 동일하며 실행 전후 목록 최신성이 `fresh`임을 [summary.json](../../assistant_web/runtime/two-week-regression-20261104-155759/notion-guide-recovery-20261105/summary.json)에서 대조했다. 실행 중 목록 나이는 1,553~1,964초였다. 준비 과정의 Notion 요청 893건은 모두 HTTP 200이었고 429는 없었다.

## 같은 질문 반복

> 전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.

매회 “그중 두 번째 이슈 번호와 제목만 다시 알려줘.”도 실행한다. 독립 SQL 대조값은 6건, 최근 등록순 `[31714, 31659, 29186]`, 두 번째는 `#31659 [MTS] 비교차트 내 추가된 종목의 장 중 실시간 업데이트 되지 않는 현상`이다.

3회 모두 독립 SQL과 건수·등록순·두 번째 이슈가 일치했다. 후속 질문도 `#31659`와 정확한 제목을 반환했다. 이슈 건수·목록의 `search_complete`는 모두 참이다. 반면 가이드 설명은 모두 `partial_evidence`이며, 호출 상한이나 180초 시간 한도로 종료된 결과가 아니다. 현재 본문을 읽은 페이지는 각각 2개·2개·1개, 공통 참고자료 검색은 각각 2회·1회·2회였다.

사전 점검에서는 제목에 비교차트가 있는 후보 5건을 현재 API로 읽었다. 본문은 비어 있거나 작업 목록·일정 기록이어서 가이드로 사용할 수 없었다. 저장된 제목·본문의 넓은 키워드 탐색에서도 후보 133건을 확인했지만, 이 후보 집합과 수집된 본문만으로 가이드의 부재를 확정할 수는 없다. 최종 실행 역시 **“가이드 없음”이 아니라 “현재 확보한 근거로 가이드를 설명할 수 없음”**으로 평가한다.

## 보조 질문

서버 질문은 2회 모두 `search_notion_body → get_notion_page_content`를 실행해 **한투 인도네시아 서버 조건검색 원격접속방법**의 현재 본문을 확보했다. 현재 접근·소속, 본문 완전성, VPN 및 Hiware 절차의 존재를 대조했다. 모델의 ‘찾았다’는 문장만으로 성공 처리하지 않았다.

페이지 탐색 질문은 5개 문서 본문을 읽고 링크 탐색 2회로 연결 후보 1개를 찾았다. 이 후보는 본문 요청과 재시도 모두 `source_temporarily_unavailable`로 실패했다. 429나 호출 상한 중단은 아니었지만 연결 문서 읽기는 성공으로 집계하지 않는다. 에이전트 종료 사유는 이미 확보한 본문을 근거로 `sufficient_evidence`였으므로, 이 종료 사유만으로 사용자 요청의 모든 탐색이 완료됐다고 평가해서는 안 된다.

## 회귀와 제한

GET↔POST 대기 공유, 별도 프로세스의 대기 유지, 예산보다 긴 대기의 요청 차단, 60초 대기 후 정상 재개, 일시 실패 재시도, 후보 힌트의 근거 배제, 미수집 제목 후보, 공통 조건 보존, 순위 결합, 가이드 오판정, 플래너 제목 조건을 검사한다.

최종 코드에서 `assistant_web/scripts/check.sh tests compile shell ruff mypy`를 통과했다. Python 테스트는 **3,061개**, 전체 커버리지는 **90%**, mypy 검사 대상은 **284개 파일**이다. `check.sh audit`도 통과했으며 기존 승인 예외 5건 외 새 취약점은 없었다. 이 작업의 신규 회귀 테스트는 14개다. 마지막 실제 반복은 이 검사를 통과한 동일 코드로 실행했다.

실제 검증 6회에 429가 없었으므로 실제 429 발생 후 복구 성공률을 측정한 것은 아니다. 60초 `Retry-After` 대기 후 재개, GET/POST 및 프로세스 간 공유, 남은 시간보다 긴 대기의 안전한 중단은 결정형 회귀 테스트로 확인했다.

남은 문제는 비교차트 가이드 원문 확보와 일부 연결 후보의 본문 읽기다. 본문 미수집 영역이 있어 전사 가이드 부재를 단정할 수 없다. 가이드가 실제로 존재하는지와 접근 가능한 원문 위치를 추가로 확인해야 하며, 이번의 서버 접속 가이드 성공을 비교차트 가이드 성공으로 대체하지 않는다.

요청 제한 정책은 [Notion 공식 문서](https://developers.notion.com/reference/request-limits)의 `Retry-After` 준수 지침을 확인했다. 같은 호스트의 수정된 프로세스끼리만 대기 상태를 공유하며 다른 호스트나 이전 코드로 실행 중인 프로세스까지 조정하지 않는다. 180초 예산을 넘는 대기와 전체 본문 미수집은 여전히 조회 미완료로 남긴다. 운영 서버 재시작·배포·커밋은 수행하지 않았다.
