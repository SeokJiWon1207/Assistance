# 초안 분할과 고객 안내 보정 재검증

**최종 채택한 코드(v6)로 이전 실패 12회를 다시 실행한 결과, 3회가 전체 기준을 통과했고 9회는 미해결 항목이 남았다.**
12회 모두 출력 잘림·JSON 오류·묶음 생성 실패가 없었으며, 후속의 최초 응답까지 포함한 16개 답변 모두
읽은 범위의 이슈를 빠짐없이 요약했다. 다만 일부 조치·회신 완료 표현과 의미 대조에서 거절이 남았으므로
고객 안내 보정까지 모두 해결한 상태로 보고하지 않는다.

후속 시나리오는 최초 문서와 후속 문서가 모두 통과해야 성공으로 센다.
부분 검색·본문 미완료·대량 결과의 `complete=false` 자체는 실패 사유가 아니다.

이전에 승인된 실제 17건과 합성 250건만 사용했다. 과거 목록을 재생하는 평가이며 운영 데이터의 현재 최신성 측정이 아니다.

## 반영한 수정

- 초안·독립 검토를 최대 6건씩 실행한다. 주장 ID를 묶음별로 구분하고, 뒤 묶음이 실패해도 앞 묶음에서 검증한 문장을 보존한다.
- 작성 전에 검토 호출까지 남았는지 확인한다. 아직 읽지 않은 원문을 5건씩 조회하는 데 필요한 호출과
  최대 두 보정 묶음의 여유를 기존 에이전트 모델 호출 16회 안에 예약한다.
- OpenAI 초안·보정 호출에 JSON 스키마를 적용한다. 다른 회사·대체 모델에는 기존 JSON 객체 모드를 사용하며
  실제 전송 모델마다 형식을 선택한다. 잘못되거나 잘린 초안은 검토 호출과 시간이 남았을 때 한 번만 다시 작성한다.
  잘린 응답을 괄호 보충이나 임의 파싱으로 채택하지 않는다. 독립 검토 오류도 통과로 바꾸지 않는다.
- 고객 안내의 수신 대상을 고객으로 지정하고, 기존 허용 영문 목록·거절 용어를 작성과 보정에 전달한다.
  항목당 한 문장으로 요청·실제 수행·가능성을 구분하며 여러 조치를 합치지 않도록 했다.
- `completion_evidence`는 기존 완료 검사에서 단계별 근거가 되는 문단 후보를 알려준다.
  이를 근거로 판정을 바꾸지 않으며, 원문 결속·완료 검사·독립 의미 검토는 모두 다시 수행한다.
- 보정 대상은 이슈별 거절 항목으로 제한한다. 대상 밖의 새 문장은 게시하지 않고 기존 검증 문장을 유지한다.
  원래 거절 항목을 생략하거나 비우면 미해결로 남는다. 누락된 이슈는 필요한 항목을 새로 작성한다.
- `draftBatches`, `failedBatches`, `ignoredRepairSlots`로 작성 범위·실패 단계·보정 대상 밖 항목을 기록한다.

JSON 객체 모드만 적용한 중간 실험에서는 닫히지 않은 객체 뒤에 공백을 계속 출력하는 문제가 재현됐다.
JSON 모드는 스키마 준수를 보장하지 않으므로 초안에 구조화 출력 형식을 적용했다.
[OpenAI 구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs).
응답 종료 사유와 서버 검사는 별도로 유지했다.

문서 요청의 출력 상한은 4,096 토큰, 요청 시간은 180초로 유지했다.
실제 Luna 설정의 `maxOutputTokens`는 2,048이며, 이번 실행에서 전송된 출력 한도도 최대 2,048이었다.

## 유지한 검증 기준과 실제 실행 근거

- 완료·수치·영문·고객용 표현 판정, 단계 이벤트 판정, 독립 검토 판정 코드와 기본 검토 지시 등
  9개 항목을 AST 해시로 대조했다. 완료 근거 전달 보완 전후 및 최종 코드에서 동일했다.
- 같은 이슈의 문단 결속, `supported=false` 차단, 거절 항목 생략 시 미해결 유지, 미완료 0건의 부재 단정 금지를 유지했다.
- 게시된 **622개 문장 모두** 같은 턴의 실제 독립 검토 `supported=true` 기록과 ID·본문·인용 문단이 일치했다.
  이는 검토 기록과의 일치 결과이며, 사람의 정답 판정을 대신하는 정확도 100% 수치는 아니다.
- 최종 12회와 후속 최초 응답을 포함한 16개 답변 모두 읽은 범위와 요약 범위가 일치했다.
  각 답변의 에이전트 모델 호출은 8~16회, 도구 호출은 3~7회였다. 앞단 플래너 호출은 에이전트 한도와 별도다.
- 실제 네트워크는 Luna POST 227회, 승인된 Mantis 원문 GET 210회였고 모두 HTTP 200이었다.
  429는 없었다. 도구 인자 거절 2건은 실행 기록에 남아 있으며 최종 조회 범위 검사는 통과했다.
- 모든 문서 작성·검토 응답의 종료 사유는 `stop`이었다. 원본 목록 파일과 실행 중 코드 해시가 유지됐다.
  최종 작업 파일 4개는 실제 v6 평가에서 사용한 소스와 바이트 단위로 동일하다.
- 대체 모델 전송 정책과 모델별 JSON 형식 선택은 자동 회귀로 확인했다. 이번 실제 실행은 모두 Luna였다.

## 남은 실패

실패 9회는 목록을 놓치거나 초안이 잘린 사례가 아니다. 요약은 확보했지만 요청 항목 일부의 거절이 해소되지 않았다.

1. **회신·전달 완료 표현.** #31593·#31592 등은 생성된 회신 완료 문장이 기존 완료 근거 검사를 통과하지 못하거나,
   보정 이후에도 가능성·확정 수준의 의미 대조에서 거절됐다. 작성 입력에 완료 근거 후보를 전달해도 반복 발생했다.
2. **조건·행위 범위를 보존하는 보정.** #31699 등에서 툴팁 종료라는 범위를 넓히거나 고객용 기술 표현을 바꾸면서
   의미 차이가 생겼다. 보정 문장도 원문에 맞지 않으면 게시하지 않았다.
3. **독립 검토의 판정 편차.** 테스트 서버라는 제한이나 가능성 표현을 보존한 문장에 대해 해당 제한을 누락했다고
   거절한 사례도 있다. 거절 이유가 부정확해 보여도 서버가 `false`를 임의로 `true`로 뒤집지 않았다.

남은 작업은 실제 메일 기록 표현과 완료 판정의 불일치를 대조하고, 의미 검토의 오판을 줄이는 것이다.
이번 수정으로 이 문제가 해결됐다고 보지 않는다.

## 실험 기록과 최종 선택

- v1: 대량 초안 분할 효과를 확인했다. 고객 안내의 JSON 공백 반복이 남았다.
- v2~v4: 스키마 적용, 고객용 작성 지시, 항목별 보정 범위를 확인했다. 중간 실패 결과를 삭제하지 않았다.
- v5: 12회 중 4회 전체 기준 통과. 출력 잘림·JSON 오류 없이 읽은 범위는 모두 요약했다.
- **v6(최종 채택):** 완료 근거 전달과 원문 조회·보정 예산 예약을 보완했다. 12회 중 3회 통과했다.
  소수의 반복 결과로 의미 검토 성공률이 개선됐다고 주장하지 않는다.
- v7(제외): 고객용 규칙을 검토에도 전달하고 판정 지시를 추가했다. 정상·허위 완료·내부정보 노출 반례 8개는
  변경 전후 모두 기대와 일치했으나, 실제 고객 안내 6회 중 1회만 통과했고 보정의 중복 항목 구조 오류가 1회 발생했다.
  최종 코드에서는 이 변경을 제외하고 기존 검토 지시·판정 코드를 유지했다.
- 네트워크가 차단된 환경의 v2 실행 1회는 서비스 품질 평가에서 제외했다. 외부 연결이 가능한 같은 승인 환경에서 다시 실행했다.

## 자동 검증

새 분할·보정 회귀 13개 테스트 메서드를 추가했다. 중간 묶음 실패, 검토 예산 부족, 묶음 간 인용 혼입,
보정 대상 밖의 허위 문장 차단, 기존 검증 문장 보존, 잘못된 JSON의 제한된 재작성,
17건 본문 미완료에서 두 보정 묶음의 호출 확보, 완료 근거 후보와 기존 판정의 일치를 검사한다.
기존 출력 잘림 회귀는 묶음마다 재시도가 한 번 이내인지 확인하도록 바꿨다.

관련 회귀 **48건**, 전체 **3,134건** 통과. 커버리지 **90%**.
`assistant_web/scripts/check.sh tests compile shell ruff mypy`의 모든 단계를 통과했다.
정적 타입 검사는 287개 소스 파일을 검사했다. 의존성 변경은 없어 의존성 감사는 반복하지 않았다.

최종 검증 로그: `/private/tmp/document-batches-check-final.log`.
