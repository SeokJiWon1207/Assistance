# 일반 에이전트 건수·목록·집계 연결 및 실제 비교

## 결과

건수·목록의 shadow 전용 제한을 해제하고, 기존 전송 정책이 활성화된 일반 요청에 조회 도구를 연결했다. `aggregate_mantis_issues`로 기존 서버 집계 엔진도 호출한다. 모델은 도구와 조회 순서를 선택하고 서버는 조건·전체 조회·수치·표시 순서를 보증하는 방향의 1단계 변경이다. 문서 작성 개선 작업은 추가하지 않았다.

동일 저장본과 실제 Luna를 사용한 비교 결과는 다음과 같다. 각 항목은 3회이며, 아래 성공은 서비스의 자체 판정이 아니라 독립 SQL 기준의 결과 판정이다.

| 검증 항목 | 변경 전 일반 경로 | 변경 후 일반 경로 |
| --- | --- | --- |
| 한투 복합 질문의 총건수·최근 3건·순서 | 0/3 | 3/3 |
| 이어지는 두 번째 이슈 번호·제목 | 0/3 | 3/3 |
| 기간 없는 상태별 집계 | 0/3 | 3/3 |
| 2026년 10월 매체별 집계 | 3/3 | 2/3 |

기간 집계의 남은 1회는 집계 엔진 오류가 아니다. 앞단 플래너가 최상위 `group_by`와 `aggregation.group_by`의 중복을 보정하면서 `status=open`을 `unspecified`로 바꿨다. 기존 상태 검증기가 이를 거절해 `unified_plan_clarification`으로 종료했다. 오집계는 전달하지 않았지만 사용자 요청을 완료하지 못했으므로 실패로 집계했다. 이 보정 과정의 조건 보존은 다음 하네스 단계에 남는다.

## 변경 범위

- 일반 Mantis `count/search/aggregate` 및 Mantis+Notion 복합 설명에 건수·목록·집계 도구를 노출한다. 기존 `AGENT_MODE_ENABLED`, 검증된 통합 계획, 허용 모델·전송 주소, 도구 지원 검증, 활성 원천과 시작 예산 조건을 유지한다.
- 일반 정책 활성 요청에서도 모델의 구조화된 해석을 검증하며 `literal_plan` 지름길을 생략한다. 정책 비활성 경로는 기존 동작을 유지한다.
- `aggregate_mantis_issues`는 전체 필터·범위와 함께 그룹·지표·기간·전월 비교·상위 개수를 확정 계획에 대조한다. `condition_ref` 재사용으로 집계 명세 검증을 우회할 수 없다.
- 단순 그룹 건수는 기존 전체 저장본 스캐너, 기간·복수 지표 집계는 기존 `execute_aggregation`을 사용한다. 등록 건수는 등록일, 공수는 고객사전달일 기준을 유지한다. 같은 요청의 저장본 세대를 공유한다.
- 기간 집계의 건수·목록 조회에는 같은 등록일 기간을 적용한다. 공수 전용 집계를 건수·목록 도구로 대신 계산하지 않는다.
- 일반 목록의 기존 최대 200건 표시 계약을 보존한다. 모델 입력의 도구 결과가 축약돼도 서버 원장과 최종 목록은 유지한다. 문서 작성의 20건 상한은 유지한다.
- 모델이 건수만 조회하고 집계·목록을 마쳤다고 답하면 한 차례 추가 조회를 요구한다. 끝내 결과가 없으면 미완료로 표시하며 모델의 임의 숫자나 초안을 확정값으로 쓰지 않는다.
- 최종 `agent_query_result`, `agent_aggregation_result`는 원장과 표시 결과를 대조하고 확정 불일치 시 전달을 차단한다. 집계 설명의 기존 사실 ID·숫자·부호·기간·그룹 검사와 독립 의미 검토를 유지하고 모델 호출을 공통 예산으로 센다.
- “최신 150건 기준”처럼 필터 적용 전 모집단을 제한하는 특수 요청은 기존 엔진에 남겼다. 단순한 표시 개수 제한으로 취급해 전체 모집단을 세지 않는다.

예비 비교에서는 변경 전 플래너가 기간 없는 질문에 오늘 날짜를 추가해 0건으로 답하는 사례를 확인했다. 기간 근거를 요구하는 검증을 보강하고, 기간 없는 단일 그룹 건수는 기존 `group_by` 명세로 표현하도록 안내했다. 날짜·상태 검증을 완화하지 않았다.

## 비교 방법과 기준 데이터

- 질문: “전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.”
- 후속: “그중 두 번째 이슈 번호와 제목만 다시 알려줘.”
- 집계 보조 질문: “전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.” / “2026년 10월 전사 한투 미해결 이슈를 매체별로 집계해줘. 표만 보여줘.”
- 모델: 승인된 OpenAI Luna `gpt-6-luna`. 최종 비교에서 모든 모델 HTTP 응답은 200이며 Gemini 폴백은 발생하지 않았다. 기존 마스킹·원천 읽기 허용 범위를 유지했다.
- 변경 전 코드를 작업 시작 시 복사해 별도 프로세스로 실행했다. 양쪽 모두 `AGENT_MODE_ENABLED=true`, `QUERY_SHADOW=false`다. 따라서 변경 후 결과는 shadow 강제 진입으로 얻은 것이 아니다.
- Mantis 전체 31,349건 저장본 수집 시각은 2026-11-06 11:33:54 KST다. 실행마다 별도 복제본·감사 DB를 사용했다. 선택된 모든 비교 실행의 초기 Mantis SHA-256은 같고 실행 후에도 변하지 않았다.
- Notion 목록은 240개 DB, 기본 TTL 7,200초 안의 유효 상태에서 각 실행을 시작·종료했다. TTL이나 저장 시각을 바꾸지 않았다. 현재 Notion 본문은 실제 API로 읽었다.
- SQL의 프로젝트·상태·등록일 정렬 및 원본 `매체구분` 값으로 기대 건수와 그룹을 만들었다. 모델 답이나 새 도구의 결과를 정답으로 사용하지 않았다.

| 독립 기준 | 값 |
| --- | --- |
| 전사 한투 미해결 | 5건 |
| 최근 등록순 3건 | #31659 → #29186 → #28764 |
| 후속 두 번째 | #29186 및 정확한 제목 |
| 상태별 | 정보 부족 3건 / 할당된 이슈 2건 |
| 2026년 10월 매체별 | MTS 1건 |

이전 11월 5일 비교의 6건·두 번째 #31659와 데이터 시점이 다르다. 이번에는 같은 질문을 11월 6일의 동일 저장본으로 비교했다.

## 시간·호출과 Notion 한계

변경 후 복합 질문 3회는 46.191초, 53.859초, 125.947초였다. 에이전트 모델/도구 호출은 각각 4/4, 4/4, 13/14로 기존 상한 16/16 안에 있었다. 마지막 실행은 Notion 후보 탐색이 늘어 지연됐다. 건수·목록의 정확성이 개선됐다는 결과를 응답 시간이 항상 짧아졌다는 주장으로 해석하지 않는다.

변경 전 복합 질문은 53.625~76.358초였지만 요청한 건수·목록을 완료하지 못했다. 기간 없는 상태별 집계는 2회 확인 질문으로 중단했고, 1회는 질문에 없는 당일 기간을 적용해 0건으로 답했다. 서비스 자체 검증의 `pass`만으로 성공 처리하지 않았다.

변경 후 3회 모두 같은 화면 관련 Notion의 현재 본문을 읽었다. 예를 들어 해외주식 종합차트의 저장·불러오기와 롤백 참고자료가 표시됐다. 이는 **#29186의 화살표 메모 기능을 직접 설명하거나 해결하는 가이드를 확보했다는 뜻이 아니다.** 마지막 실행에는 업무 회의록도 가이드로 분류됐다. 도구의 가이드 플래그만으로 의미 적합성을 성공 처리하지 않았다. 최종 답변은 상태·고객사 미적용 여부와 대상 이슈의 실제 원인·조치 근거가 아니라는 구분을 유지한다. Notion 가이드 관련성 개선은 이번 1단계의 완료 항목에 포함하지 않는다.

최종 비교 18개 본 질문 실행과 그에 딸린 6개 후속 응답에서 429는 없었다. 변경 후 실행의 HTTP 합계는 Luna POST 51회, Mantis GET 4회, Notion GET 124회, 로컬 임베딩 POST 8회였다. 일반 건수·일반 목록의 별도 대조 실행도 각각 정확했으며 조건·수치·전송 정책 검사가 통과했다.

## 회귀 검사와 산출물

`assistant_web/scripts/check.sh tests compile shell ruff mypy`가 종료 코드 0으로 완료됐다. 테스트 **3,150건**, 커버리지 **90%**, Python·프런트엔드 컴파일, 셸 검사, Ruff, mypy 289개 소스가 통과했다. 로그는 `/private/tmp/agent-query-verified.log`다. 의존성을 바꾸지 않아 의존성 감사는 재실행하지 않았다.

새 회귀는 일반 진입/정책 차단, 20건 초과 목록, 집계 인자와 참조 변조, 부분 조회의 0건 차단, 서버 계산 표의 변조 차단, 기간별 날짜 기준, 누락된 집계, 임의 기간 추가, 특수 모집단 제한의 기존 경로 보존을 검사한다. 기존 조건·상태 검사, 근거 투영, 집계 사실 검증, 문서 검증 함수 8개와 전송 정책 파일이 변경 전과 동일함을 별도 대조했다.

런타임 산출물은 Git에서 제외된 `assistant_web/runtime/agent-query-primary-20261106/`에 있다.

- `summary.json`: 독립 정답과 비교 결과.
- `final-provenance.json`: 동일 원천, 최종 코드 일치, 실행 중 코드 불변, shadow 비사용 확인.
- `preserved-validation.json`: 기존 검증·전송 정책 보존 확인.
- `measure.py`, `run_compare.py`, `score.py`: 격리 실행 및 채점 절차.
- `legacy-{compound,groups,period}-{2,3,4}`: 변경 전 최종 비교 9회.
- `primary-compound-{4,5,6}`, `primary-{groups,period}-{3,4,5}`: 최종 동일 코드 비교 9회.
- `primary-count-1`, `primary-list-1`: 일반 건수·목록 단독 대조.

예비 실행과 코드 변경 중 실행은 별도로 보존했으며 최종 3회 통계에 섞지 않았다. 커밋·서버 재시작·배포는 수행하지 않았다.

남은 구조 작업은 앞단 단일 계획의 역할 축소와 보정 중 조건 보존, 단계별 서로 다른 조건 계약, 다른 보고서 도구화, 병렬 실행이다. 이번 변경만으로 모든 작업을 자유롭게 재계획하는 하네스가 완성된 것은 아니다.
