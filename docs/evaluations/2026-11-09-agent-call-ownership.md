# 호출별 상태 소유권·예산·취소 정비

2026-11-09. 도구가 호출별 사본에서 실행되고, 요청 소유자가 유효한 결과만 확정하도록 변경했다. 공통 예산 차감을 원자적으로 처리하고 작업자에 요청 정책·마감·취소 문맥을 전달한다. 실제 도구 실행은 순차 방식을 유지한다.

## 변경한 계약

- `ToolContext.for_call`로 호출 ID를 분리한다. 원장·조건 참조·조회 저장본·중복 호출 기록·Notion 본문 캐시·조건 준비 상태를 호출별 사본에서 변경한다. `PendingCall.publish`에서 버전·마감·취소를 확인한 뒤 한 곳에서 확정한다. 뒤늦은 사본 수정은 확정 근거에 영향을 주지 않는다.
- 다른 호출이 먼저 확정 상태를 변경했으면 `state_conflict`로 거절한다. 아직 독립 호출의 결과를 병합하는 구현은 아니며, 오래된 사본으로 새 결과를 덮어쓰지 않는 경계를 먼저 마련했다. 원장 조건도 같은 호출 ID의 단계에만 연결한다.
- 예외·단계 시간 초과 시 잠정 원장·캐시·계획을 되돌린다. Notion 본문/연결 페이지 실패 시 기존 본문을 철회하고 미완료로 표시하는 계약은 유지한다. 접근 철회 결과도 정상적으로 반영한다.
- 모델/도구 예산의 검사와 차감을 같은 잠금에서 처리한다. 조사 호출은 최종 검증 예약까지 함께 확인한다. 예약 시간 부족은 `deadline`, 호출 수 부족은 `call_limit`로 구분한다. 요청 예산뿐 아니라 더 짧은 하위 단계 마감도 적용한다.
- `submit_with_context`로 기존 Mantis·페이지 선실행 작업자에 전송 정책과 공통 예산을 전달한다. 취소된 대기 작업을 취소하고 실행 전후에 확인한다. 체크포인트 없이 늦게 반환한 작업도 성공 결과로 반영하지 않는다. 취소와 결과 확정은 같은 잠금으로 선후 관계를 정한다.
- 요청 180초, 모델·도구 각 16회, 최종 검증 예약, 조건·근거·수치·인용 검증, 허용 모델/마스킹 정책은 유지한다. 연결별 Notion 429 대기 공유는 기존 구현을 재사용한다.

진행 중인 동기 HTTP를 강제로 중단하지는 않는다. 기존 HTTP 제한 시간과 협력적 취소를 사용하며, 작업이 실제 종료될 때까지 요청 슬롯을 유지한다. 이번 보장은 취소/마감 이후의 늦은 결과가 확정 근거로 들어오지 않는 것이다. 실제 병렬화 전에는 서버가 호출 독립성을 판단하고 독립 결과를 병합하는 규칙을 추가해야 한다.

## 비교 방법

[직전 평가 기준선](2026-11-09-agent-evaluation-baseline.md)의 질문·정답·관련성 판정·평가기·초기 저장본을 유지했다. 변경 전과 최종 변경 후 각각 독립 프로세스로 3회 실행하여, 각 군의 복합·후속·집계 9응답 모두를 채점한다. 도구 인자 거절·재시도·대체·최종 검토가 발생하면 호출·지연·사용량에서 제외하지 않는다.

1. `전사 범위에서 한투 미해결 이슈가 몇 건이야? 최근 3건을 보여주고, 두 번째 이슈와 관련된 Notion 가이드도 설명해줘.`
2. 각 복합 질문의 후속: `그중 두 번째 이슈 번호와 제목만 다시 알려줘.`
3. `전사 한투 미해결 이슈를 상태별로 몇 건인지 알려줘.`

독립 SQL 정답은 전체 **5건**, 최근 **#31659 → #29186 → #28764**, 상태별 **정보 부족 3건·할당된 이슈 2건**이다. 현재 본문을 읽었는지, 같은 화면의 참고 근거인지, 요청한 기능의 직접 가이드인지를 별도로 채점한다. 검색 점수나 제품의 `sufficient_evidence` 표시로 직접 관련성 기준을 대신하지 않는다.

원문 전송은 사전 승인된 Luna와 장애 시 허용된 Gemini 범위로 제한했다. 운영 설정·서버 재시작·배포는 수행하지 않았다.
