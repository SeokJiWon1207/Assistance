최종 운영 릴리스: `20261020T075800Z`. 새 질문의 원문 대조 결과와 동일 질문의 성능 비교를 기록한다. 최종 내용 정확도는 내부 검증 통과 표시와 구분해 판정한다.

## 원인과 변경

같은 원본 트랜잭션에서 고객사·매체·담당자·ID 필드만 연속으로 읽어 기존 조건의 일부를 먼저 검사한다. 통과한 후보에는 전체 원문 조건을 그대로 재검증하며, 같은 세대·조건을 쓰는 두 검색은 허용 ID 집합을 요청 안에서 재사용한다. BM25는 전체 코퍼스 통계를 유지한 채 해당 ID의 구간만 순위대로 소비한다. 후보 수를 임의로 잘라 정확도를 얻는 방식이 아니다. 플랫폼 해제 후에는 FTS에 본문 테이블을 결합하는 비용도 남았다. 최종 구현은 작은 chunks_issue 색인에서 허용 구간 ID만 얻고, 전역 BM25 점수/ID 순위에 이를 적용한 뒤 소비하는 본문만 읽는다. 동일 로컬 저장본에서 후보·원문·점수가 일치했다(결합 방식 2,545.99ms, ID 방식 878.63ms; 헤더 읽기·캐시 효과도 포함된 관측값).

## 검증 집합 구분

발견용 질문을 최종 미사용 통과 건수에 포함하지 않는다. v1의 3개는 LLM 계획이 옛 키워드 검사로 거부되는 문제, v2의 후속은 고객사 조건을 잘못 해제하는 문제와 빈 결과의 기준 근거 누락, v3는 요청·추정의 원인/조치 과장과 리소스 부족 후보 혼입, v4와 v5의 각 3개, v6에서 실행한 4개 질문은 구간 검색 지연과 조건 검사 전의 원문 읽기 병목을 발견하는 데 사용했다.

발견한 추출 문제는 일반화한 회귀 테스트로 고정했다. 요청·완료 질문을 조치로 쓰지 않으며, 가정과 잠정 원인 판단·단순 테스트 가능 설명을 확정 원인으로 쓰지 않는다. 계정 입력 줄은 원인/조치 인용 전에 제거한다. 리소스 부족도 같은 증상 필터를 거친다. 구조화된 원인·조치와 원문 노트의 실제 변경·QC·전달 단계는 계속 구분한다.

최종 미사용 집합은 `runtime/similar_latency_20261020/holdout_v7.json`, SHA-256 `9152969deeef1118872d7124e0bdd0a13efb11b087d1327697b80e19b800ccab`이다. 일부 질문은 앞선 파일에 적혀 있었지만 실행하거나 수정에 쓰지 않았고, 최종 고정 후 처음 실행한다. 내부 검증의 통과 표시에 더해 원천 JSON의 고객사·매체·등록일·상태·노트·실제 문장 의미를 대조한다.

- 같은 로컬 실제 저장본의 좁은 조건 검색을 헤더 선검사 유무로 대조했다. 후보 원문·구간·점수 전체가 일치했고, 큰 원문 조회 25,089→1회, 해당 검색 5,458.31→895.92ms였다. 이는 로컬 검색 구간만의 측정이다.

## 검증의 한계

임베딩 endpoint의 연결 실패 자체는 변경하지 않았다. 운영은 해당 시점의 구간 BM25·RRF 또는 제목 대체 검색을 사용한다. 전수 유사 사례 검색이나 모든 원인 추출이 증명된 것은 아니다. 근거 없는 원인은 확인되지 않았다고 표시한다. 새 Chroma 원문 배포에는 제목 색인을 갱신해야 하며, 갱신하지 않아도 정확성을 우선해 스트리밍 경로를 쓴다. 시간은 실행 시점의 서버 관측값이며 캐시·원천 조회·모델 지연으로 변동한다. 새 질문 전체의 수정 전/후 짝지은 실험을 수행한 것은 아니며, 동일 질문 비교와 미사용 질문의 최종 검증을 구분한다.

## 원문 확인으로 남은 문제

1. **시간·범위 표현이 증상 초점에 섞인다.** K1의 검색 메타데이터에서 `semantic_focus_term=오래된`이 선택됐다. 기준 #16208보다 이전에 등록된 #8904 메모리 부족 사례가 실제로 있고, 기준 #16208 노트 64585에는 #16537과 동일하여 종료했다는 이력도 있다. 답변은 과거 사례를 찾지 못했다는 안내만 반환했다.
2. **후속 조건이 정확해도 비교 후보를 누락한다.** K3의 고객사 NH·기준 16208 유지, 플랫폼 해제는 정확했다. 하지만 원천 #5290(2012-12-04)은 NH의 메모리 부족 메시지 문의와 회신 노트 19428이 있고, #8082(2013-08-27)는 NH 차트 리소스 개선 및 누수 수정, SVN 파일 변경·QC 결과 30158·전달 30171이 있다. 매체 미지정이므로 K2의 HTS 조건에서는 제외하는 것이 맞고, 플랫폼을 해제한 K3에서는 비교 근거로 검토할 수 있는데 빈 결과로 끝났다.
3. **추정 원인과 기술 조치 이력을 충분히 구분·연결하지 못한다.** K4는 #6059 노트 22688의 '느려지는 원인이 될 수 있다'를 원인 칸에 넣고, 실제 수정인 노트 22813의 qsort/bsearch 및 23049의 부분 drawing 개선은 빼고 QC 결과만 표시했다.
4. **미확인·상태 처리 문장과 다른 증상을 비교에 섞는다.** K5는 #30883 노트 108764의 '원인이 명확하지 않아'를 원인 기록으로 표시했다. 노트 108844의 TimeMeterPDLL 해제 처리·정상 해제 확인 및 메모리 증가량에 체감 변화가 없었다는 한계는 빠졌다. #30163 원문은 당일 분배락 표시 문제이며 리소스 부족 비교에 적합하지 않다. #15939 노트 62950의 '완료된 작업 종료처리'는 실제 기술 조치 근거가 아니다.

이 네 항목은 이번 미사용 검증에서 남은 결과다. 속도 개선으로 모든 새 답변의 정확도까지 해결됐다고 판정하지 않는다. 원문 문장이 존재한다는 확인 외에, 질문과 관련된 원인·실제 조치·현재 상태를 구분하고 필요한 이력을 빠짐없이 선택하는 검증이 더 필요하다.
