# 긴 노트 근거 보존과 원문 갱신 지연 보완

## 최종 판정

운영 릴리스 `20261021T051500Z`에서 재로그인 후 검증을 마쳤다. 코드 수정에 사용하지 않은 F 질문 9건의 최종 내용·근거 판정은 **충족 7건, 미흡 2건**이다. 집계는 원천 재수집 후 2 → 0 → 2건으로 독립 SQL과 일치했다.

원래 문제였던 긴 노트의 원인·조치 누락과 기준 이슈 본문 원인 누락은 복구했다. 다만 원천 갱신 뒤 D4에 새로 포함된 비교 사례의 실험 조건을 원인으로 잘못 분류했고, F5/F6에서는 다른 이슈의 본문 이력을 누락했다. **모든 최종 답변의 정확도와 전체 응답시간 개선을 달성한 완료 상태는 아니다.**

자동 통과 배지, 요약 채택률, 근거 ID 연결 여부를 내용 정답률로 사용하지 않았다. F 질문은 코드 수정에 쓰지 않았으며, 최초 집계 실패는 원천 갱신 후 재실행한 결과와 구분해 남겼다.

## 구현

- 노트의 원인·조치·서버별 문장 경계를 보존한다. 일반 문단의 예정·문의 문맥은 통째로 유지하고, 구체적인 메커니즘과 진단이 독립적으로 적힌 본문만 문장 단위로 보완한다. 줄바꿈 앞 함수명도 보존한다.
- ‘라이브러리 반영 중, 재기동 전 조회하여 CPU 증가’라는 발생 시점과 원인 파악 진행 중을 구분한다. 같은 노트의 운영 서버 원인과 백업 서버 미확정 원인을 함께 표시한다. 이후 확정 필드가 있으면 다른 옛 노트의 추측을 현재 미확정 원인으로 되살리지 않는다.
- 빈 ‘조치’ 제목을 실제 행동으로 사용하지 않는다. 메모리 복구와 미로드 메모리 로드를 별도 실행 기록으로 남기고 노트 번호를 보존한다.
- 추가 분류를 강제로 시간 초과시켜도 본문의 정적 참조 진단을 보존한다. 제거 요청·코드 제안은 실제 수정 완료로 바꾸지 않는다. 테스트는 실제 분류 호출과 unavailable 종료까지 검사한다.
- 유사 비교 후보 갱신에만 요청당 1.5초, 외부 갱신 소요시간 합산 5초의 예산과 1회 시도를 적용한다. 같은 요청의 중복 원문은 복사해 재사용한다. 일반 상세 조회의 20초·3회 재시도는 유지한다.
- 예산 소진·연결 실패 시 저장본을 사용하면 답변에 대체 사실과 수집 시각을 표시한다. 접근 거부·확인된 삭제를 저장본으로 되살리지 않고 취소 신호도 보존한다. 연결/읽기 제한과 누적 경과시간으로 관리하며 모든 네트워크 상황의 엄밀한 벽시계 상한 보장은 아니다.
- 집계·조건 해석 코드는 변경하지 않았다. 새로운 의존성이나 인증·쿠키·CORS·모델 보안 완화도 없다.

별도 F9문항은 마지막 보완 전에 고정했다. 기본 질문 3개에 각각 후속 2개로 CPU 비교, 메모리 비교, 집계를 묻는다. F의 짝지은 변경 전 비교본은 `050300Z`이며 이번 전체 작업 시작 전이 아니라 마지막 회귀 보완 전이다. 원래 느린 D6은 최초 `042900Z` 기록과도 별도 비교한다.
