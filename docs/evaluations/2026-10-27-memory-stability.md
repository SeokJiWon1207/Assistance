# 전체 원문 캐시로 인한 메모리 부족 수정

## 원인과 변경

오류 발생 당시 운영 서버는 RAM 1,905MiB 중 가용 253MiB였고, 요청 수용 기본 기준인 320MiB에 미달했다. 서비스 RSS는 약 1,230MiB였다. 재시작하면 회복되지만 기능을 사용할수록 다시 큰 원본 캐시가 채워지는 구조였다.

`read_complete_store()`는 전체 이슈의 요약·본문 두 뷰를 전역 세대 캐시에 유지한다. 요약에서도 사용자 정의 필드 같은 중첩 원본은 남으며, 대시보드용 정규화 결과와 함께 보관됐다. 로컬 실제 저장본의 `tracemalloc` 측정에서 요약 캐시만 387.3MiB, 본문 뷰까지 사용하면 589.1MiB가 요청 종료 후에도 남았다. 캐시 소유권을 해제하자 추적 메모리는 약 0.1MiB로 감소했다. 무한 누수를 입증한 것은 아니며, 작업 종류에 따라 대용량 캐시가 채워져 소형 서버의 여유를 소진하는 원인을 확인했다.

웹 대시보드, 템플릿 통계, 업무 질의, SLA, 주간·월간 보고서를 요청 범위의 SQLite 스트리밍 조회로 전환했다. 전체 원문을 전역 캐시에 적재하지 않고 한 행씩 필터·정규화하며, 대시보드는 정규화한 표시용 결과 한 세대만 공유한다. 보고서 공통 로더도 전체 원문 목록을 다시 만들지 않는다. 요청 종료·예외 시 SQLite 연결을 닫고, 같은 범위의 재조회는 고정된 트랜잭션을 사용한다. 기존 일괄 읽기 API는 오프라인 검증 도구 호환용으로 남겼다.

요청 수용 메모리 기준, 동시 요청 상한, 인증·쿠키·CORS·모델 전송 정책은 변경하지 않았다.

## 추가 동시 부하 시험 — 2026-10-27 12:37~12:57 KST

사용자 요청으로 가상 사용자 4명이 질문을 계속 보내는 시험을 추가했다. 운영 설정은 전체 동시 처리 2건, 사용자별 2건, 분당 사용자별 20건이다. 이 한도를 유지했다.

### 방법과 범위

운영 서버의 현재 릴리스·환경 설정·원본 저장본·실제 회사 모델을 사용한 **별도 검증 프로세스**에서 `ChatService.build_response()`를 실행했다. 서로 다른 가상 UID 4개로 요청 수용 제어와 실제 채팅 파이프라인을 거쳤으며, 로그인 계정이나 권한은 만들지 않았다. 감사 로그는 운영 DB와 분리한 임시 DB에 기록했다. 이 부분은 서비스 계층 부하 시험이며, 4개의 실제 사용자 로그인 세션을 대상으로 한 HTTP 시험은 아니다.

동시에 실제 로그인된 운영 화면의 3개 탭에서도 서로 다른 질문을 보냈다. 같은 로그인 계정의 HTTP 요청 3건 중 2건은 정상 보고서로 끝났고, 1건은 동시 처리 제한 429를 받았다. 이후 같은 질문을 다시 보내 정상 응답하는 것을 확인했다.

6종 질문은 주간·월간 보고서, 장기 미종료, 이슈 상태·원인·조치 설명, 과거 유사 사례 비교, 미종료 목록이다. Mantis와 벡터 검색을 켰고 A/B 비교도 켰다. Notion 검색, 2건을 초과한 실제 병렬 처리, 느린 SSE 수신 클라이언트는 이번 시험 범위에 포함하지 않았다.

4명 모두 정상 응답을 받았고 6종 경로가 모두 실행됐다. 총 **73건 응답**, 동시 제한 재시도 **801건**, 메모리 부족 거절·서버 오류·모델 지연 대체 응답은 각각 **0건**이다. 실제 운영 프로세스와 검증 프로세스가 같은 소형 서버를 사용했으며, 추가 시험의 할당 추적에는 실행 시간과 메모리 비용이 있다. 이 지연 수치를 평상시 운영 지연으로 일반화하지 않는다.

할당 추적은 업무 스냅샷 예열 후 시작했다. 이후 새로 할당되어 남아 있는 Python 메모리는 최초 기능 로딩 후 약 **31.43MiB**였고, 작업 중 최고 **74.88MiB**까지 증가했다. 90초 회복 관찰과 GC 후에는 **31.42MiB**로 돌아왔다. 이는 프로세스 전체 Python 메모리량이 아니라 추적 시작 이후의 할당량이다. 마지막 보관 할당은 모듈 import·클래스 정의가 주를 이루었고, JSON 디코더에 남은 할당은 약 195KiB였다. RSS가 초기값으로 바로 내려가지 않는 현상과 실제로 원문 객체를 계속 보관하는 현상을 구분했다. 이 관찰에서는 이전의 전체 원문 캐시가 요청마다 누적되는 현상은 재현되지 않았다.

정상 응답 73건의 답변 검증 판정은 통과 47건·확인 필요 26건이었다. 이 시험은 메모리와 수용 제어 시험이므로 73건 전체를 답변 정확도 통과로 계산하지 않는다.

### 종료 상태와 판단

운영 PID는 시작부터 끝까지 `606118`, 자동 재시작 0회였다. 운영의 `/ready`와 DB 5개 검사 모두 정상, 커널 OOM 기록과 운영 HTTP 5xx는 0건이었다. 운영 HTTP 429 한 건은 위의 3탭 시험에서 의도한 한도 초과다.

검증 프로세스 2개 종료 후 운영 RSS **363.59MiB**, 프로세스 스왑 **168.35MiB**, 서버 가용 메모리 **1,063.80MiB**를 확인했다. 운영 RSS는 시험 중 최대 약 460MiB였고, 유휴 페이지가 스왑으로 이동했으므로 RSS 감소만으로 메모리 해제를 판단하지 않았다. 검증 프로세스의 스왑도 추가 시험에서 수 MiB 발생했다.

현재 동시 2건 설정에서 4명이 계속 요청해도 이번 시험의 메모리 부족은 재현되지 않았다. 다만 초과 요청을 대기열에 넣지 않고 429로 거절하기 때문에, 4명 모두가 즉시 처리되는 사용 경험을 입증한 결과는 아니다. 현재 체감 제약은 동시 처리 한도와 재시도다. 동시 한도를 늘린 상태의 안정성이나 장시간 운영 전체를 이 결과만으로 보장하지 않는다.

상세 이벤트·요약·분 단위 분석·CSV·화면 증거는 Git에서 제외된 `assistant_web/runtime/concurrent_memory_20261027/`에 보관했다. 이번 시험에서 제품 코드나 운영 설정은 추가 변경하지 않았다.

## 후속 변경: 동시 질문의 FIFO 대기열 — 2026-10-27 13:20 KST

사용자 요청에 따라 동시 처리 초과 질문을 바로 거절하던 동작을 FIFO 대기로 변경했다. 실행 슬롯을 얻기 전에는 모델·검색 워커와 실행 예산을 만들지 않는다. SSE는 대기 순서를 전송하며, 순서 변경 또는 5초마다 상태를 보내 연결을 유지한다. 기존 UI의 상태 표시·생성 중지 버튼으로 대기 확인과 취소가 가능하다.

기본 설정은 전체 대기 32건, 사용자별 대기 4건, 최대 대기 120초다. 실행 제한 180초와 대기 제한은 별도이며, 동시 처리와 메모리 기준은 유지했다. 분당 요청 제한·대기열 포화 시에는 429, 대기 만료 시에는 503으로 안내한다. 취소·연결 종료·만료 티켓은 제거한다. 모델 작업이 이미 시작된 경우 실제 워커 종료까지 실행 슬롯을 유지한다.

현재 단일 Uvicorn 프로세스 안의 인메모리 대기열이다. 실행 시작 순서를 보장하며, 동시 실행한 답변의 완료 시각까지 같은 순서로 맞추지는 않는다. 프로세스 재시작을 넘어 대기 요청을 저장하거나 여러 워커 사이에 공유하는 영속 대기열은 이번 범위에 포함하지 않았다.
