# Mantis 긴 이슈 검색

의미 유사 이슈 검색에 적용한다. 집계, 조건 해석, 일반 조건 검색과 기존 Chroma
문서 형식은 유지한다. 새 의존성은 없다.

## 검색 흐름

1. 전체 원본 저장본의 본문·재현 절차·추가 정보·원인·조치·모든 노트를 1,200자
   구간으로 나눈다. 인접 구간은 150자 겹치며 필드명과 원문 위치를 보존한다.
2. 한국어 단어·글자쌍과 오류 코드로 SQLite FTS5 BM25 후보를 찾는다.
   기존 원본 조건 매처를 적용한 뒤 이슈별로 중복을 제거하고 후보 수를 제한한다.
3. 기존 Chroma 이슈 벡터 순위와 RRF(k=60)로 결합한다. 기존 주제 집중 조건도
   결합 후보에 적용한다.
4. 상위 24개 이슈의 근거 구간을 기존 로컬 임베딩 모델로 비교한다.
   코사인 유사도 85%, 정규화한 RRF 15%로 정렬한다. 전용 교차 인코더는 아니다.
5. 실시간 원본을 재조회해 조건을 확인하고, 동일한 구간만 답변 근거로 전달한다.
   API 연결 장애 때는 저장본 출처를 명시한다. 삭제·접근 거절은 제외한다.

키워드 후보는 가장 잘 맞는 구간 한 개, 벡터 전용 후보는 본문 우선 두 구간을
재순위화한다. 전체 구간을 벡터화하지 않으므로 키워드가 전혀 겹치지 않는 긴 노트의
동의어 검색까지 모두 해결하지는 않는다. 검색 결과는 상위 후보이며 전수 집계가 아니다.

## 인덱스와 장애 처리

`runtime/mantis_chunks.sqlite3`는 검색 전용 파생 파일이다. 원본 전체 저장본과
Chroma DB는 수정하지 않는다. 연결 식별자·원본 세대·건수를 확인하고, 불일치하면
해당 요청은 기존 검색을 사용하면서 백그라운드 갱신을 시작한다.

임시 파일에서 구축하고 완성 후 원자 교체한다. 이슈 내용 해시가 바뀐 이슈만
재분할하고, 삭제된 이슈는 제거한다. 원본 갱신 시각만 바뀌었어도 전체 파일 복사와
해시 확인은 필요하지만 전체 토큰화는 반복하지 않는다. 구축 중 원본 세대가 바뀌면
완성된 중간 세대를 보관하고 증분 구축으로 따라잡으며, 다른 세대를 검색에 섞지 않는다.
여러 요청의 중복 구축은 스레드 잠금과 파일 잠금으로 막는다.

재순위화의 타임아웃·비정상 임베딩은 RRF 순위로 복귀한다. 요청 취소는 전파한다.
실제 사용 방식은 `ranking`, `reranking`, `reranking_fallback_reason`에 기록한다.

수동 준비(저장소 루트):

```bash
assistant_web/.venv/bin/python assistant_web/scripts/build_mantis_chunks.py
```

설정은 `.env.example`의 `MANTIS_HYBRID_SEARCH_ENABLED`,
`MANTIS_HYBRID_RERANK_ENABLED`, `MANTIS_RERANK_TIMEOUT_SECONDS`를 따른다.
기본값은 각각 true, true, 12초다. 모델과 주소는 기존 `CHROMA_EMBEDDING_MODEL`,
`OLLAMA_BASE_URL`을 공유한다.

## 검증 결과와 재현

2026-10-15 실제 원본 31,241개 이슈에서 198,351개 구간을 구축했다.
결과를 보기 전에 고정한 질문 16개(긴 이슈 뒤쪽 근거 9개, 제목 중심 대조 7개)를
동일한 질문·고객사 조건으로 비교했다.

| 검색 | 기대 이슈 Hit@5 | MRR@5 | 시간 중앙값 |
|---|---:|---:|---:|
| 기존 | 10/16 (62.5%) | 0.594 | 0.05초 |
| BM25·벡터 결합 | 15/16 (93.8%) | 0.797 | 0.40초 |
| 구간 재순위화 | 16/16 (100%) | 0.885 | 1.73초 |

이는 미리 지정한 관련 이슈를 찾는 비율이다. 모든 관련 이슈에 대한 재현율이나
생성 답변의 사실 정확도는 아니다. 긴 이슈 중심의 작은 표본이므로 전체 질의로
일반화하지 않는다. 기존 운영 Chroma와 최신 전체 원본을 비교해 데이터 포괄성
차이도 포함된다. 동일한 기존 벡터 결과를 재사용하고 그 소요시간을 합산했으며,
결합만의 시간은 재순위화 구간을 뺀 추정치다. API 재조회·답변 생성 시간은 제외한다.

질문과 상세 결과는 로컬 `runtime/hybrid_verification_20261015/cases.json`,
`results.json`에 보관한다. 내부 이슈 내용이 있어 Git에는 포함하지 않는다.
재현 명령(로컬 임베딩 서버 필요):

```bash
assistant_web/.venv/bin/python assistant_web/scripts/accuracy/verify_hybrid_retrieval.py \
  --cases assistant_web/runtime/hybrid_verification_20261015/cases.json \
  --output assistant_web/runtime/hybrid_verification_20261015/results.json
```

평가 중 원본은 임시 SQLite 복사본으로 고정하고 종료 후 제거한다. 기대 이슈는
검색 결과를 보기 전에 정한다. 반복 개선에 이 문항을 사용하면 별도 미사용 문항으로
다시 평가해야 한다.

기존 집계 보존도 별도로 확인했다. 동일한 원본 SQLite 사본에서 기능을 끈 경우와
켠 경우 각각 고객사·매체·상태·담당자·기간·후속 조건 질문 20개가 모두 통과했고
건수·목록·응답 모드·검증 상태가 동일했다. 오프라인 점검이므로 상태 의미 모델은
고정 응답을 사용했다. 점검 스크립트에 남아 있던 본문 기반 매체 추측과 누락된
기본 팀 범위를 기존 앱 계약에 맞춰 수정했다. 운영 조건 해석은 바꾸지 않았다.
상세 기록은 같은 결과 디렉터리의 `aggregate_comparison.json`,
`aggregate_false.jsonl`, `aggregate_true.jsonl`에 있다.

최종 `assistant_web/scripts/check.sh`의 tests/compile/shell/ruff/mypy/audit가 모두
통과했다(1,629개 테스트, 커버리지 87%, 기존 의존성 감사 예외 유지).
독립 코드 검토에서 주제 집중 조건의 결합 후보 적용과 긴 노트의 조치 근거 전달을
보완했으며 재검토에서 추가 주요 결함은 발견되지 않았다. 로컬 앱 `/health`는
200이고 실제 검색 진입점의 `hybrid_chunk_rrf`/`chunk_embedding_cosine` 실행을 확인했다.

## 설명 답변 보완과 후속 검증 (2026-10-15)

이슈의 원인·조치·재현 조건·진행 경과 질문은 `operation=explain`으로 구분해
일반 목록 답변이 대신 나오지 않도록 했다. 고객사·기간·담당자·명시 상태 조건은
기존 추출 결과를 사용한다. 앱 종료 현상이나 개발 완료 여부를 묻는 서술만 상태
필터와 구분하며, 명시적인 포함·제외 조건과 후속 질문의 상속 조건이 우선한다.
집계·공수·업무보고·건수 및 명시 목록 요청은 기존 경로를 유지한다.

설명용 원문은 검색 구간 외에 본문과 모든 노트에서 질문 관련 구간 및 마지막
노트들을 선택한다. 이슈당 최대 18,000자이며 원문 위치, 노트 번호·시각·작성자,
제공량과 생략 여부를 함께 전달한다. 따라서 여전히 전체 원문이 항상 들어가는
것은 아니다. 유사 이슈 질문에는 기준 이슈도 근거로 포함한다.

원인·조치 추출에서는 기술 문장, 코드 경로, 여러 줄에 걸친 설명을 보존하고
요청·예정과 실제 수정·QC·전달을 구분한다. 설명 초안은 같은 원문을 이용해 한 번
추가 정정한 뒤 기존 검증을 거친다. 설명 질문에는 모델 호출 한 번이 추가되므로
지연과 비용이 늘어난다. 이 정정 과정은 정확성 보증이나 독립 평가를 대신하지 않는다.
검증기의 기능 상태와 이슈 상태, 설명 항목과 명시 메타데이터 혼동도 보완했다.

실제 회사 모델과 저장본으로 기존 24개 및 추가 18개 질문의 **최종 답변**을 평가했다.
추가 질문은 실제 이슈로 작성했으며 사용자 질의 로그는 아니다. 답변 모델의
자체 점수가 아니라 원문과 질문별 기대 내용을 독립 대조했다. 최종 통과 수는
모든 필수 요청에 답하고 중요한 사실·근거 오류가 없는 경우이며, 미답변도 실패다.

| 표본 | 수정 전 | 수정 후 |
|---|---:|---:|
| 기존 설명 질문 20개 | 0/20 | 15/20 |
| 기존 유사 사례 질문 4개 | 0/4 | 1/4 |
| 추가 질문 12개 | 비교 없음 | 3/12 |
| 마지막 미사용 질문 6개 | 비교 없음 | 1/6 |

수정 후 통과에는 저장된 동일 답변을 검증기 수정 후 재검증한 2개가 포함된다.
42개 최초 실행에서는 18개가 통과했고, 검증기 재검증을 반영하면 20개다.
마지막 6개 중 라우팅 누락 2개를 수정해 실제 모델로 다시 실행했으나 내용 평가는
실패를 유지했다. 이 두 재실행은 미사용 평가가 아닌 수정 후 회귀 평가다.

따라서 **최종 답변 정확도는 아직 충분하지 않다.** 수정 요청을 완료로 바꾸는
서술, 부정문 의미 반전, 서로 다른 이슈·후속 수정의 혼합, 필수 처리 이력 누락이
남았다. 날짜의 원문 history 표시와 기존 UTC 날짜 정규화가 충돌한 한 문항은
판정을 유보했다. 추가 집계 2문항에서는 복합 포함 조건 해석 실패도 확인했으며,
이번 설명 수정에서 집계·조건 해석 규칙을 넓혀 성공 처리하지 않았다.

별도의 집계·조건 회귀 20문항은 설명 기능을 켠 경우와 끈 경우 모두 통과하고
건수·목록·응답 모드·검증 상태가 동일했다. 마지막 품질 검사는 1,660개 테스트,
커버리지 87%, compile/shell/ruff/mypy 통과 및 기존 예외를 유지한 의존성 감사다.
브라우저·인증·스트리밍 전송을 종단 검증한 결과는 아니다.

질문·원문·답변·개별 실패 근거·재검증 이력은 로컬
`runtime/hybrid_answer_repair_20261015/report.html`과 하위 JSON에 보관한다.
내부 원문은 Git에 포함하지 않는다. 작은 도전 표본이며 반복 사용한 기존 질문의
개선률을 전체 운영 정확도로 일반화하지 않는다.

## 2026-10-15 추가 수정: 원문 선택과 설명 근거 검증

앞선 18문항에서 남은 완료 과장·다른 이슈 혼합·필수 이력 누락을 줄이기 위해
설명 경로를 원문 인용 중심으로 바꿨다. 모델은 문장을 다시 쓰지 않고 서버가
부여한 문단 ID를 선택한다. 서버는 선택된 이슈·필드·노트의 원문 일치를 검사하고
작성자와 기록 시각을 원문에서 붙인다. 요청·예정·미재현·QC·전달을 모델이 임의로
완료로 바꾸는 자유 서술은 출력하지 않는다. JSON이나 인용 검증에 실패하면
설명을 확정할 수 없다고 응답한다.

첫 선택 뒤에는 선택된 이슈만으로 질문의 세부 항목을 다시 대조한다. 이 단계는
대상을 바꿀 수 없다. 비교 요청을 제외하면 한 이슈를 기준으로 하되, 필요한
초기·후속 이력이 실제 `related-to` 관계로 연결된 같은 프로젝트의 검색 후보에
있을 때만 복수 선택을 허용한다. 선택된 이슈들끼리 관계 그래프가 연결되어야
하며, 검색하지 않은 연결 이슈를 추가로 가져오거나 기존 범위 필터를 풀지 않는다.
각 인용은 실제 출처 이슈에 귀속한다.

이미 조회한 `answer_evidence` 범위의 노트와 초기 등록 내용을 보존해 중간
QC NG·재요청·정정·마지막 보류를 누락하지 않도록 했다. 이는 전체 원문을 항상
제공한다는 뜻이 아니다. 기존 근거 길이 제한은 유지하며, 일부만 제공된 경우
부분 이력임을 표시한다. 지나치게 긴 문단은 잘라 의미를 바꾸지 않고 거부하되
다른 정상 노트는 보존한다. 아이폰/iOS 또는 Android를 물었으나 제공된 원문에
해당 플랫폼 언급이 없으면 판단 근거가 없다고 표시한다.

긴 진행 이력과 등록 내용은 화면에서 별도로 접는다. 원문 안의 코드·Markdown·
이슈 번호는 문자 그대로 표시하고, 서버가 붙인 출처 이슈 번호만 탐색에 사용한다.
검증 도중 발견한 테스트 계정 접속정보 노트는 문단 하나만 가리는 대신 해당
노트·필드 전체를 인용 후보와 최종 답변에서 제외한다. 이 검사는 알려진 접속정보
표현에 대한 방어이며 모든 비밀 형식을 탐지하는 범용 분류기는 아니다.

설명 질문에서 기술적 당일/전일 값, 한 이슈 안의 수정 항목 수, 서술적인
‘문제없이’·‘제외한 항목’을 집계 조건으로 오독하던 사례를 좁게 교정했다.
명시적인 등록 기간·상태·담당자·제외 조건과 기존 집계 경로는 유지한다.
설명 검색에 한해 재순위화가 누락시킨 적격 어휘 검색 1위 후보를 보존한다.

검증 질문은 실제 저장본에서 사람이 작성한 도전 표본이며 사용자 질문 로그가

실제 사용자 로그 표본이 아닌 실제 이슈 기반 합성 질문이며, 고정 저장본과 동일
모델 설정으로 순차 한 번씩 측정했다. 실행 변동을 분리한 반복 실험이 아니므로
시간·정확도 변화의 인과 효과나 일반 정확도를 단정하지 않는다. 접힌 전체 이력의
필수 사실도 완결성에 포함해 핵심 요약만의 완결성을 보장하지 않는다. 실시간
Mantis API·인증·브라우저·스트리밍은 평가 범위에서 제외했다. 문항별 원응답,
실패 이유, 재현 방법은 `runtime/multiquery_evaluation_20261016/REPORT.md`,
`comparison.json`, `REPRODUCE.md`에 보관한다.

로컬 서버의 실행 확인에서는 기존 사용자 DB 버전 2와 현재 인증 코드의 지원 버전
1이 달라 애플리케이션 시작이 실패했다. 이번 검색 변경의 파일 범위에 인증 코드는
없으며, 사용자 DB의 버전이나 인증 설정을 변경하지 않았다. 따라서 브라우저를
포함한 운영 경로의 적용 완료로 해석하지 않는다.

## 설명·담당자 경계 오류 수정과 응답시간 개선 (2026-10-16 후속)

위 독립 평가에서 남은 MQ01·MQ07의 요약 귀속 오류는 정상 동작·빌드의 확인
요청을 확인 완료로 바꾸고 미재현 결과에 임의로 초기 시점을 붙인 고정 요약에서
발생했다. 확인 결과의 대상과 시점을 원문 문장·노트 출처에 유지하고, 의문·간접
질문·미확인·가정·예정 문구는 확인 완료로 표시하지 않는다.

MQ02는 검수·전달 상태를 묻는 설명을 일반 검색으로 분류해 화면번호를 잘못된
매체 조건으로 쓰던 경로를 수정했다. MQ04는 공백을 제거한 `건 수정본`에서
`건수`를 잘못 찾던 원인이었다. 실제 수량의 `건 수·개 수`와 그 조사 표현은
계속 집계하며 `건 수신·건 수정본·개 수정`은 수량으로 해석하지 않는다. MQ10의
`종료되는 원인`은 프로그램 장애의 서술로 처리하되 명시한 이슈 상태와 상속
조건은 보존한다. MQ15·MQ16은 담당자 이름 뒤 `인·이고·이며·이면서`를 처리하고
`김지인` 같은 실제 이름을 자르지 않도록 경계를 검증했다.

응답시간 개선은 검색 후보나 원문 이력을 줄이는 대신 같은 다중 검색 안에서
동일한 원문 구간의 임베딩을 재사용한다. 키에 endpoint·모델·원문 전체를 포함하며
요청이 끝나면 폐기한다. 실패·부분·잘못된 벡터는 저장하지 않고 취소를 전파한다.
모델 입력의 원문 위치 숫자와 JSON 공백도 줄이되 본문·문단 번호·작성자·작성 및
수정 시각·부분 근거 표시는 유지한다. 서버의 검증 원문과 위치 정보는 보존한다.

MQ10의 상태 조건 수정 후에는 대상이 보조 검색에 포함되지만 최종 후보 결합에서
탈락하는 문제가 드러났다. 반복 출현 빈도만으로 후보를 고르지 않고, 동일 조건으로
검증된 후보 전체를 원래 질문과 다시 의미 비교한 뒤 최종 후보 수를 제한한다.
기존 검색 상위 두 후보는 보존하며, 재순위화 장애는 기존 RRF 결합으로 돌아간다.
앞선 검색에서 계산한 원문 벡터를 재사용해 추가 임베딩 계산을 줄인다.

개발 질문의 원문 재검토에서는 과거 통과였던 MQ03·MQ12도 필수 사실이 누락된
것을 확인했다. 이전의 9/16 판정은 같은 엄격 기준으로 재검토하면 7/16이다.
MQ03은 변경 목록 뒤의 이슈번호·첨부파일을 다른 이슈 구획으로 오인해 실제
Standard/Micro 추가·전달 기록이 잘렸다. MQ12는 함께 전달한 라이브러리의
공통 테스트 후 적용 요청이 타 이슈 구획과 함께 잘렸다. 번호 목록과 이슈별
구획을 구분하고 명시적으로 함께 전달한 결과물의 공통 적용 조건은 보존하며,
다른 이슈의 개별 조치는 계속 제외한다. 이는 새 독립 평가를 보고 수정한 결과가
아니며, 기존 개발 질문의 첫 재실행과 판정 정정은
`runtime/multiquery_fix_regression_20261016/first_REPORT.md`에 보존한다.

최종 개발 회귀는 16/16(설명 12/12, 집계 4/4)이다. 원문 발췌 276개, 렌더링
인용 1,032개, 노트 작성자·시각 312개에서 불일치가 없었다. 이 수치는 수정에
사용한 질문의 결과이며 일반 정확도 수치가 아니다. 일부 필수 사실은 접힌 전체
이력에 있으므로 첫 핵심 결론만의 완결성과 동일하지 않다. 최종 소스 경계 보강은
이 실행의 조회 원문 138개 × 질문 16개(2,208 조합)에서 발췌 결과가 동일함을
확인했다. 개발 문항별 최종 답변·근거 판정과 표현상의 한계는
`runtime/multiquery_fix_regression_20261016/REPORT.md`에 기록한다.

고정 코드에서 기존 집계 20문항의 건수·목록·담당자 및 날짜 등 적용 조건을 비교해
변경 전후 모두 20/20, 의미 차이 0개를 확인했다. 전체 테스트 1,919개, 커버리지
88%, compile·shell·Ruff·mypy와 기존 예외 5개를 유지한 의존성 audit를 통과했다.
검증 명령 출력과 코드 고정 해시는 개발 평가의 `final_checks.json`에 연결했다.

수정에 사용하지 않은 실제 저장본 기반 합성 질문 16개를 별도로 동결해 평가했다.
이전 평가에서 사용·검색한 이슈 5,344개와 새 기대 이슈 22개는 중복이 없다.
최초 최종답변 정확도는 6/16→10/16이다. 새 담당자 집계는 0/4→4/4이나,
설명은 6/12→6/12로 개선되지 않았다. 남은 설명 오류는 목록·업무보고 등으로
잘못 분류한 4건과 혼합 노트에서 필수 근거를 제외한 2건이다. 그중 1건은 원문에
전달 기록이 있는데 없다고 단정했다. 인용 195개·발췌 99개·노트 메타데이터
121개가 원문과 일치해도 이러한 의미상 오류는 별도로 실패 처리했다.

통과는 접힌 전체 이력을 포함하는 기준이다. 설명의 펼쳐진 답변만으로 완결된
경우는 2/12→3/12이며, 핵심 결론 자체에 필수 사실이 모두 있는 경우는 전후
0/12다. 최종답변 통과율을 핵심 요약 품질이나 일반 정확도로 확대 해석하지 않는다.

최초 전체 평균 응답시간은 10.118→10.712초, 반복은 9.784→10.833초다.
전후 공통 정답 6문항도 15.062→15.261초(반복 14.669→16.742초)로
속도 개선은 확인되지 않았다. 첫 설명 Chroma 검색은 평균 3.578→2.694초로

같고 첫 AFTER의 planner timeout 1회도 최초 응답과 시간에 포함했다. 그 문항은
fallback으로 최종 집계가 정확했으며 반복 실행에서는 모델 오류가 없었다.

새 평가의 실패를 보고 제품 코드를 추가 수정하거나 최초 응답을 교체하지 않았다.

표본에서 발생하지 않았다. 실시간 동기화·인증·브라우저·스트리밍은 검증 범위가
아니다. 원문 근거·문항별 판정·반복 측정·재현 절차는
`runtime/multiquery_fix_evaluation_20261016/REPORT.md`에 보존한다.
