# 조회·집계·설명 에이전트 경로

모델이 검색 결과를 보고 다음 조회를 정하는 Tool Calling 경로다. 기능 플래그
`AGENT_MODE_ENABLED`의 기본값은 `false`이며, 꺼져 있으면 정책 범위·도구 정의·추가 모델
호출·추가 검색이 생기지 않고 기존 경로와 응답 계약을 그대로 사용한다.

## 적용 범위

- `UNIFIED_QUERY_PLANNER_ENABLED=true`에서 앞단은 인증된 대화·순번만 복원한다. 활성 에이전트는 별도
  `plan_question` 호출 없이 `prepare_query`로 조건과 출력 목적을 제안·검증한다. 검증한 Mantis 단건·건수·목록·집계, 설명 계획과 Mantis 이슈 문서
  `report/handoff`, `report/postmortem`, `report/notice`가 진입한다. 설명의 원천은
  `mantis/notion/both`, 이슈 문서의 원천은 `mantis/both`다. 레거시 규칙 플래너 경로는 지원하지 않는다.
- 모델이 건수·목록·집계 도구를 선택하고 기존 서버 엔진이 계산한다. 단일 원천 설명과 Mantis+Notion 복합 설명에도 조회 도구를
  제공한다. Notion 단독 건수·목록·속성과 결정형 보고서 17종도 읽기 도구로 실행한다.
  쓰기·확인 질문과 지원 계약 밖의 작업은 기존 경로를 유지한다.
- 담당자·상태·기간 조건이 있어도 설명 요청이면 진입한다. 조건은 서버가 확정한 값으로 강제한다.

## 실행 흐름

```text
POST /api/chat
 → request_transfer_scope(modelId)      # 플래그 ON이면 플래너 호출 전부터 허용 목록 강제
 → prepare(서버 감사 문맥·순번 복원)     # 활성 에이전트에서는 별도 모델 계획 없음
 → run_agent_if_eligible
     → prepare_query(proposal)          # 에이전트가 조건/출력 목적 제안, 기존 검증기 재사용
     → 오류 시 prepare_query(changes)   # 생략한 조건 보존, 실패한 변경은 반영하지 않음
     → 검증 완료 후 원천별 조건 계약·읽기 도구 연결
     → 판단 호출(비스트리밍, tools) → 서버 인자 검증 → 도구 순차 실행 → role=tool 결과
     → 반복 또는 최종 초안
     → 결과 수집: 보고서·속성·비교·문서·집계·목록을 기존 렌더러로 작성
     → 요청한 원천 설명: Mantis 원문 인용 검증 / Notion 현재 본문·인용 원장 대조
     → 공통 조합: 모델이 고른 표시 순서, 부분별 기존 검증 모드·원천 보존
     → 부분별 조건·수치 검증 재실행 + 최종 조합의 추가·누락·변조 검사
       예산·본문 부족 시 확인한 범위와 보류 사유 표시
 → 검증된 비대상: plan_chat_query(결정형 즉시 응답) → 기존 검색·생성 경로
 → finalize(기존 검증 + 에이전트 검사 영역, 감사 요약, AB 비교 제외)
```

조건 준비 실패·예산 소진은 `agent_plan_clarification`으로 끝나며 기존 자유 서술 생성으로 우회하지 않는다.
검증된 일반 대화·쓰기·미도구화 보고서만 기존 처리기에 위임한다. 쓰기 권한과 확인 절차는 그대로다.
비활성 정책과 명시적 query shadow는 기존 앞단 계획을 사용한다.

### 조건 준비와 보정

- 최초에는 `prepare_query`만 노출한다. 검증 전 원천 검색·상세 읽기는 실행할 수 없다.
- `proposal`은 기존 호환 계획 형식을 사용한다. `operation`은 출력 의무와 미도구화 작업의 호환 표기이며,
  지원하는 읽기 요청의 실제 건수·목록·집계·본문 도구 순서는 모델이 결정한다.
- 오류가 나면 서버가 초안을 보관한다. `changes`에 바꿀 최상위 필드만 넣고, 생략한 상태·고객사·기간을 보존한다.
  중첩 객체/배열은 해당 필드 전체를 교체한다. 모든 변경을 기존 `validate_plan`, 대화 상속 검사,
  `validate_execution_contract`로 재검증하며 실패한 변경은 적용하지 않는다. 확정 후 같은 요청의 조건 변경은 금지한다.
- 예: 유효한 `aggregation`과 최상위 그룹의 중복은 `changes={"group_by":null}`로 고친다.
  기간 없는 상태별 건수를 복합 명세로 잘못 제안했다면 `changes={"aggregation":null,"group_by":"status"}`로 함께 바꾼다.
  `aggregate`에서 단순 그룹과 계산 명세를 모두 없애면 준비 단계와 실행 계약 검사가 거부한다.
  복합 그룹·공수·기간·비교 요청은 해당 명세를 유지한다. 미해결을 `unspecified`로 바꾸면 기존 누락 검사가 거부한다.
- 해석·부분 보정도 같은 모델/도구 호출 예산에 포함한다. `agentReview.planning`에 통과 여부·변경 필드·거절 사유를 기록한다.
- 질문 전체의 조건 계약을 바탕으로 조회 단계별 인자를 검증한다. 독립 비교 범위와 조사용 조건의 경계는
  아래의 도구 인자·여러 조회 범위 항목을 따른다.

### 공통 응답과 읽기 라우팅

- `prepare_query`의 `answer_sections`는 `results` 또는 `results`와 `explanation`의 순서를 정한다.
  `results` 생략·중복·임의 문구는 거부한다. `explanation_sources`는 계획한 `mantis/notion` 중 설명할 원천만 지정한다.
  한투 건수·목록과 Notion 가이드 설명을 요청했다면 설명 대상은 Notion이다. 조회 필터나 수치를 바꾸는 인자는 아니다.
- 마감 시 처음 맞는 결과 하나로 종료하지 않는다. 보고서와 추가 목록·설명, Notion 속성과 본문을 함께 보존한다.
  문서 작성과 집계의 기존 전용 검증은 그대로 실행한다. 여러 부분이면 `agent_composed`, 단일 부분이면 기존 모드를 유지한다.
- `answer_parts`는 각 부분의 내용·원천·조회 원장·검증 모드를 서버가 기록한다. 최종 검증은 각 부분의 기존 검증기를
  다시 실행하고 `agent_response_composition`으로 조합 내용의 추가·누락·변조를 차단한다. 모델이 건수·표를 다시 쓰지 않는다.
- 속성 조회·제목 후보만으로 본문 설명을 통과시키지 않는다. 구조화 경로의 Notion 설명에는 현재 본문 읽기가 필요하며,
  근거가 없으면 결과를 유지하고 본문 설명을 보류한다. 사후 원문 접근 철회는 앞서 만든 부분까지 포함해 답변을 보류한다.
- 설명의 인용 없는 주장·임의 링크·인용 원문에 없는 수량은 제외한다. 단위 없는 숫자도 검사한다. 이슈 번호는 기존 ID
  대조·1회 보정 절차를 따른다. 이 검사는 서술 전체의 의미 정답을 보증하지 않으므로 기존 사람의 내용 검토 표시는 유지한다.
- 설명은 고정된 세 제목 대신 질문에 맞는 문단·목록을 사용한다. 참고 등급의 관련 가이드를 현재 본문으로 읽은 경우에는
  기존 발췌·조건 미적용 표시를 재사용하며 불필요한 Mantis 설명을 추가 생성하지 않는다.
- 표시 출처는 중복을 제거하고, 별도 번호 목록이 있으면 후속 질문의 순번과 범위를 그 목록으로 한정한다.
  보고서나 설명의 인용 순서가 “두 번째”의 대상을 바꾸지 않는다.
- 일반 경로와 shadow는 `eligibility.py`의 읽기 지원 범위를 공유한다. Notion 도구 연결은 검증된 원천과 사용자 설정을
  사용한다. 인증된 순번 복원·접근 제한·쓰기·일반 대화·미지원 보고서의 기존 경계는 유지한다.
- 비교 범위가 없는 질문의 도구 정의에서는 `query_scope_id`를 숨긴다. 비교가 있으면 현재 원천에 허용된 ID만 제공한다.
  정의와 다르게 보낸 인자는 실행 단계에서도 계속 거부하며, 오류는 해당 인자를 삭제해 보정하도록 안내한다.
- `tests/test_agent_common_response.py`는 결과 동시 보존, 원문 접근 철회, 부분별 수치 변조 차단, 본문 없는 설명,
  번호 목록의 후속 순서, 비교 인자 노출 범위와 검증 유지를 확인한다.

### 조건 기반 이슈 문서

- `report_kind`는 작성 목적이다. 단일 이슈 번호가 없어도 화면·기간·고객사 조건으로 목록을 확인하고
  `get_mantis_issue_detail`로 선택한 각 이슈의 본문을 읽는다. 해당 문서 요청에는 건수·목록 도구를 일반 경로에서도 제공한다.
- `get_mantis_issue_details`는 이미 조회로 확인한 번호를 최대 5개씩 읽는다. 이슈마다 같은 조건 검증을 거치며,
  일부 실패를 전체 성공으로 바꾸지 않는다. 원천 API 요청은 기존 제한 시간 안에서 순차 실행한다.
- 각 도구 응답의 `document_progress`는 원장에 누적된 본문 확보 번호와 아직 읽지 않은 후보를 전달한다.
  표시용 도구 응답이 잘려도 이 상태는 보존한다. `incomplete_body_ids`로 본문 미완료를 구분하며
  `all_listed_complete`는 조건이 적용된 상세 조회의 본문 근거가 모두 완료된 경우에만 참이다.
- Mantis 단독 문서 요청은 조건 조회가 완료되고 표시 대상 본문을 모두 확보하면 서버가 조사 루프를 끝내고
  예약된 문서 작성·독립 검토로 넘어간다. `collection_complete`에 `document_bodies_ready`를 기록한다.
  완전한 0건도 바로 마무리한다. 조회 미완료·본문 미완료·제목만 읽기·참고 등급·Notion 포함 요청은 이 조건으로 끝내지 않는다.
  표시 한도 때문에 전체 결과 중 일부만 읽은 경우에는 문서의 부분 범위 표시를 유지한다.
- 첫 조회의 구조화된 필터·범위·정렬을 질문과 대조한다. 문서 출력 항목을 검색어로 적용하지 않도록 새 문서 계획의
  `terms=[]`를 요구한다. 실제 검색 주제는 근거가 있는 `keyword/title` 필터로 표현한다.
- 최근 N주는 오늘을 포함한 N×7일이다. 누락하거나 잘못 계산한 기간은 재해석하며 그대로 실행하지 않는다.
- 표시 개수 생략 시 최대 20개 후보를 제공한다. 전체 이슈 수, 원문 확보 수, 문장 검증 수를 별도로 표시한다.
  목록이 더 크거나 호출·시간·원문·컨텍스트 한도가 있으면 일부 결과로 명시한다. 제목 조회만으로는 본문 근거가 되지 않는다.
- `documents.py`는 모델이 작성한 문장을 같은 이슈의 안전한 원문 문단에 연결한다. 기존 문서 검증기의 수치·완료 단계·추정
  검사를 적용하고 별도 모델 호출로 의미를 대조한다. 초안·검토 호출은 공통 모델 예산에 포함되며, 목록 도구 사용 후에도
  최종 예약 호출·시간을 해제하지 않는다. 문장 검증이 실패하면 자유 서술로 대체하지 않는다.
- 초안과 독립 검토는 최대 6건씩 나눠 실행한다. 각 묶음의 주장 ID를 구분하며 앞 묶음의 검증된 문장은
  뒤 묶음의 실패에도 보존한다. 작성 전에 검토 호출까지 남았는지 확인한다. 목록 크기에 맞춰 묶음별 작성·검토와
  최대 두 보정 묶음의 호출 여유를 기존 16회 안에 예약한다. 아직 읽지 않은 원문을 5건씩 조회하는 데 필요한
  호출도 고려한다. 요청 180초·출력 4,096 토큰·컨텍스트 한도는 늘리지 않는다.
- 전체 발췌가 기존 문서 컨텍스트 한도 안이면 이슈마다 균등 분할해 긴 본문을 불필요하게 자르지 않는다.
  전체 한도를 넘으면 발췌 제한과 미완료 표시를 유지한다.
- 초안이 이슈를 누락하거나 문장이 거절되면 해당 이슈만 한 번 다시 작성하고 독립 검토한다.
  공통 예산에 모델 호출 2회 이상과 30초 초과가 남아 있을 때만 실행하며, 재검토 실패를 통과로 바꾸지 않는다.
  요약 문장을 확보하지 못한 이슈도 제목·고객사와 `요약 검증 보류` 표시를 남긴다. 고객 안내문은 내부 제목·고객사 대신 안내 순번만 표시한다.
- 작성·검토는 같은 항목 정의를 사용한다. 문의·작업 요청은 증상 항목에서 그 성격을 보존하며,
  재현 확인 중인 절차는 확인 중으로 기록된 절차라고 표현한다. 재현 성공이나 현재 진행으로 단정하지 않는다.
- 초안은 질문에서 요청한 항목만 작성한다. 출력 한도로 잘리거나 JSON 형식이 잘못된 초안은 사용하지 않고, 초안 재작성과
  독립 검토의 2회 호출 및 30초 초과가 남았을 때 한 번 축약 재작성한다. 같은 출력 한도와 공통 호출 예산을 쓰며,
  재시도도 잘리면 문서 작성을 보류한다. 원문 범위나 검증 단계를 줄여 완료 처리하지 않는다.
- OpenAI 초안·보정 호출에는 문서 종류별 JSON 스키마를 적용한다. 고객 안내는 허용 항목만 작성할 수 있다.
  형식 지원이 확인되지 않은 회사·대체 모델과 독립 검토에는 JSON 객체 모드를 사용한다.
  실제 전송 모델마다 형식을 선택하며 전송 허용 목록은 변경하지 않는다. 형식을 강제해도 잘린 응답과 검토 오류는 차단한다.
- 정적 검사와 독립 검토의 거절 단계·사유를 해당 문장·문단 ID와 함께 재작성에 전달한다.
  인용되지 않은 숫자·영문, 요청의 완료 승격, 추정의 확정, 다른 이슈 근거 혼입에 대한 기존 검사는 유지한다.
  검토 사유는 보정용 데이터이며 `supported=false` 판정을 통과로 바꾸는 근거로 사용하지 않는다.
- 작성 입력의 `completion_evidence`는 기존 완료 검사에서 각 단계를 뒷받침하는 문단 후보를 제공한다.
  빈 목록의 단계는 완료로 확정하지 않도록 지시한다. 이 목록은 원문 대조나 독립 검토를 대체하지 않는다.
  판정 함수와 완료·불확실성 기준은 그대로 재사용하며, 목록만으로 실제 주체·범위·전체 완료를 확정하지 않는다.
- 보정은 항목 단위로 병합한다. 이미 검증된 증상 등은 보존하고, 거절된 재현 조건을 생략하거나
  비워 둔 경우에는 미해결로 남긴다. 이슈의 다른 항목이 통과했다는 이유만으로 해당 거절을 해제하지 않는다.
  `correction.required_slots`로 이슈별 보정 대상을 지정한다. 대상 밖의 새 문장은 게시하지 않고
  `ignoredRepairSlots`에 남긴다. 누락된 이슈는 필요한 항목을 작성하며, 실제 보정 대상은 이전과 동일하게 검증한다.
- 고객사 표시는 서버가 맡으며 작성 모델에는 프로젝트 고객사 메타데이터를 별도로 제공하지 않는다.
  문장에 프로젝트 고객사명이 있으면 인용한 문단에서도 확인해야 한다. 프로젝트 소속만으로 문의 발신 주체를 만들지 않는다.
- 고객 안내 초안에는 내부 번호·담당자·경로·코드를 표시하지 않는다. 출처와 내부 조회 조건은 별도 메타에 둔다.
- 고객 안내 작성·보정에는 실제 수신 대상과 기존 허용 영문 목록을 전달한다. 거절된 용어를 보정 데이터에 표시하고
  원문의 조건을 보존한 한국어 표현을 요청한다. 항목당 한 문장으로 고객의 요청·전달과 회사의 실제 수행을 구분한다.
  여러 조치를 한 문장에 합치거나 원문의 구체적 행위를 포괄적인 수정 완료·해결로 확대하지 않는다.
- `documentReview`와 감사 요약의 `agent.document`에 전체 조회 완료 여부, 대상/읽은/문장 검증 이슈 ID,
  본문 미완료 ID, 문단 ID, 거절 문장 수와 단계·사유(`rejections`), 보정 시도·성공·미해결 이슈 ID를 기록한다.
  원문 전체나 모델 대화 이력은 감사 요약에 복제하지 않는다.
- 응답의 `documentReview.draftBatches`와 `failedBatches`는 묶음별 작성 범위 및 실패 단계를 기록한다.
  실패·미해결 항목을 생략해 전체 완료로 바꾸지 않는다.
- `tests/test_agent_document_matrix.py`는 세 문서 유형에서 전체 조회 0건·미완료 0건·부분 검색·본문 미완료·
  합성 250건 중 20건 읽기를 반복 검사한다. 실제 감사 기록의 후속 조건·형식 변경·순번 선택과 원문 재조회,
  수치·완료 표현·의미 검토 거절 및 잘못된 JSON·출력 잘림의 차단도 포함한다.
  모델을 대체한 자동 테스트의 통과와 실제 모델의 문서 작성 성공률은 별도로 기록한다.

## 구성 요소

### 추가된 결정형 도구

- `list_mantis_issues`의 `selected_issue_detail`은 요청한 표시 순번의 상세 조회 인자를 제공한다. 필수 고객사·상태·기간·모집단·비교 범위를 보존하며 실제 목록의 ID만 추가한다. 모델이 이를 선택해 실행하고 기존 단계 조건 검증과 승인 범위 차단을 다시 통과해야 한다. 상세 본문·노트의 기능명과 재현 단서는 검색에 쓰되 본문의 지시를 새 권한이나 조회 조건으로 취급하지 않는다.
- `get_notion_page_content`는 같은 요청의 페이지 ref에서 `offset`으로 구간을 읽고 `next_offset`을 반환한다. 생략하면 관련 구간, 0이면 처음이다. 앞부분이 생략된 경우도 `truncated=true`이며 `content_complete`는 원천 본문 수집 완료를 뜻한다. 현재 접근·본문이 확인된 동일 요청 원장을 재사용하므로 이어 읽기마다 원천 전체를 다시 수집하지 않는다. `content_incomplete_reasons`는 요청 한도 등 원천 미완료 사유를 표시한다. `related_guide_verified`는 관련 절차 후보이며 질문 기능의 직접 근거 판정을 대신하지 않는다.
- `count_notion_pages`, `list_notion_pages`는 검증된 전체 필터를 인자로 받는다. Notion에는 Mantis의 팀 `scope`를 붙이지 않는다. 원천 조회 조건·정렬·검색어·표시 개수가 같은 요청은 저장본을 재사용한다. 의미 검색 후보 수와 전체 항목 수는 별개다. `search_complete`와 `candidate_count_complete`를 함께 확인하며, 표시 창만 완료된 0건을 부재로 확정하지 않는다.
- `get_notion_page_properties`는 현재 요청의 `N*` ref만 받는다. 읽기 범위·현재 접근·전체 속성 페이지네이션을 재검증하고 상태·담당자·기한·배포일 등을 반환한다. 본문을 읽었다고 표시하지 않는다. 일반 Notion 설명에서도 사용할 수 있다.
- `agent_notion_results`는 원장 건수·표시 문서·현재 속성으로 서버가 작성한다. 기존 원문 검증에 `agent_notion_contract`와 `agent_notion_result`를 추가한다. 검증된 계획의 필터를 재사용하므로 ‘담당자 속성’의 ‘속성’을 사람 이름으로 다시 해석하지 않는다. 다른 제목·속성이나 근거 없는 계획은 계속 차단한다.
- `build_issue_report`는 `kind=effort/weekly/monthly`와 검증된 `effort` 방식을 받는다. 보고서 목적·필터·인증 범위를 바꿀 수 없다. 기존 보고서 계산기와 `deterministic_*` 수치 검증기를 그대로 사용한다. 모델이 고른 추가 원문 조회는 같은 도구 루프에서 이어갈 수 있다. 주간·월간의 지표별 날짜 계산 중에도 나머지 명시 필터를 유지한다. 부분 원천은 확인한 범위의 보고서임을 표시한다.
- `tests/test_agent_remaining_tools.py`, `test_agent_report_tools.py`는 전체 0건/부분 조회, 속성 접근 실패, 정렬 계약, 출력 항목 오인, 조건·종류 변조, 모집단 선별 순서, 공수 재합산·수치 변조 차단을 검증한다. 이 테스트의 가짜 원천과 실제 Luna 반복 검증은 별도로 기록한다.

## 조건 대응 규칙

- 단일 원천은 지원하는 확정 조건을 적용한다. 두 원천을 함께 조회할 때 개인·팀·이슈 상태는
  통합 플래너가 확정한 Mantis 의미를 따른다. Notion은 옮길 수 있는 조건으로 조회하고 반환된 속성도 대조한다.
- 계획하지 않은 원천에는 고객사·매체·본문 키워드만 옮긴다. 상태·담당자·요청자·기간·이슈 번호·
  화면번호·팀 범위·Notion DB·목표일은 값 체계가 달라 옮기지도 지우지도 않고 "적용 불가"로 기록한다.
- 적용하지 못한 조건이 있는 결과는 `reference`(일반 기술 참고) 등급이다.
  - 답변 본문에서 인용할 수 없다. 서버가 `## 일반 기술 참고 (조건 미적용 자료)` 목록으로 따로 붙인다.
  - Mantis 인용 검증 경로에는 전달하지 않는다.
  - 검증(`sourcesForFollowUps`)과 후속 질문 생성 근거에서 제외한다.
  - 표시 출처·감사 기록에는 `evidence_grade`, `evidence_note`로 남긴다.

## 예산과 종료

요청 전체 마감(`CHAT_REQUEST_TIMEOUT_SECONDS`)을 연장하지 않는다. 판단·재시도·최종 합성·인용
수정과 Mantis 인용 검증 경로의 선택·검토·재시도·요약 보정은 모두 같은 모델 호출 한도로 센다.
원문 보강과 도구 실행은 같은 도구 한도로 센다.

- 최종 단계 예약은 "1회"가 아니라 인용 검증 경로를 끝내는 최소 호출 수(선택·검토 2회,
  `AGENT_FINAL_RESERVE_CALLS`)와 `AGENT_FINAL_RESERVE_SECONDS`다. 조사 루프는 예약분을 쓰지 않는다.
- 인용 검증 경로의 재시도는 예산이 남을 때만 진행한다. 선택·검토 단계에서 예산이 끝나면
  자유 서술로 우회하지 않고 검증된 근거 목록으로 끝낸다. 요약 보정만 실패하면 검증된 인용 답변을 유지한다.
- 원문 보강 예산이 없으면 보강을 건너뛰고 부분 근거 안내를 붙인다.
- Notion 문서 검색은 일반 도구의 기본 20초보다 오래 걸려도 남은 조사 시간을 쓴다. 시간이 충분할 때는 최종 답변 예약분과 문서 본문을 읽을 도구 호출 한 번의 시간을 남긴다.
- 같은 요청에서 이미 읽은 Mantis 원문은 `issue_reuse_scope`로 다시 요청하지 않는다.

| 종료 사유 | 처리 |
|---|---|
| `sufficient_evidence`, `no_evidence` | 정상 마감. 결과 없음은 "사실 없음"으로 단정하지 않음 |
| `call_limit`, `context_limit`, `model_error` | 확보한 근거로 예약 호출을 사용해 마감, 불가하면 검증된 근거 안내 |
| `deadline` | 조사를 시작하지 않거나 멈추고 근거 안내 |
| `policy_blocked`, `serving_changed` | 추가 모델 호출 없이 근거 안내 |
| 요청 취소·전체 마감 | `RequestStopped`를 그대로 올림(추가 호출 없음) |

## 데이터 전송 정책

- 후보 요청: `AGENT_MODE_ENABLED=true`, 선택 모델 ID가 `AGENT_ALLOWED_MODEL_IDS`에 있고, 실제 전송
  주소의 origin이 `AGENT_ALLOWED_ENDPOINT_ORIGINS`에 있으며, `supportsTools=true`와 유효한 검증 기록이 있을 때.
- 플래그 ON이면 검증 기록이 없거나 만료돼도 플래너 호출 전부터 전송 허용 목록을 적용한다.
  HTTP 리디렉션 차단 시 응답을 닫고 서킷의 기존 장애 횟수와 재시도 시각을 보존한다. 폴백을 명시하지 않은 모델에는 대체 후보가 없다.
- 선택 모델이 실패하면 그 모델의 `fallbackModelIds` 중 허용 목록에 있는 모델로만 바꾼다. 도구 판단
  호출은 도구 호출 검증 기록이 있는 대체 모델만 쓰고, 도구 없는 생성 호출(인용 검증 경로·합성·인용 수정)은
  허용 목록의 대체 모델을 쓴다. 같은 모델의 일시 오류(타임아웃·연결·429·5xx)는 판단 호출에서 1회 재시도하며,
  4xx는 재시도 없이 대체 모델로 바꾼다. 재시도·대체 호출도 요청 공통 호출 예산에 포함한다.
- 현재 구성(2026-11-04): 선택 모델 OpenAI Luna(`gpt-6-luna`), 장애 시 Gemini(`gemini-3.1-flash-lite`).
  허용 목록은 `.env`의 `AGENT_ALLOWED_MODEL_IDS`, `AGENT_ALLOWED_ENDPOINT_ORIGINS`에 둔다. 이 구성에서는
  사내 원문이 외부 서비스(OpenAI, 대체 시 Google)로 전송된다. 회사 Qwen은 허용 목록에 없어 쓰지 않는다.
  Luna·Gemini 모두 합성 입력으로 도구 호출을 검증했으므로 판단 호출과 생성 호출 모두 Gemini로 대체할 수 있다.
- 조사 도중 Luna에서 Gemini로 바뀌면 Gemini가 Luna의 도구 호출 이력을 이어받는다. Gemini는 이전 호출의
  `thought_signature`를 요구하므로 다른 모델이 만든 호출에는 Google이 안내한 대체 값
  (`skip_thought_signature_validator`)을 붙여 보낸다. Gemini가 만든 호출의 서명은 그대로 돌려준다.
- 실패 모델은 호출 종류별로 기록한다. 연결·시간 초과·5xx는 모든 호출에서 제외하고, 4xx(형식 오류 등)는
  그 호출 종류에서만 제외한다.
- 조사·합성·인용 검토를 위한 모델 전송 사본에 마스킹을 적용한다. 서버는 원장에서 문단 ID와 원문을 대조한다.
- 원문 접근 제한이나 조건 불일치로 철회한 검색 결과는 출처 이벤트, 최종 답변, 감사, 후속 질문에서 제외한다.
  사실·추정 문장에서는 원장에 있는 직접 근거를 문장 중간 또는 끝에 인용할 수 있다. 별도로 덧붙인 단정은 자체 근거가 필요하다.
  자료의 한계나 추가로 확인할 항목은 인용 없이 표시하고 빈 제목은 제거한다. 링크는 서버의 출처 목록으로 제공한다.
- 감사에는 도구 이름, 인자 키, 검색어 길이·지문, 결과 수, ref, 소요 시간, 오류 코드, 종료 사유,
  토큰 사용량(미보고 호출 수 별도)만 남긴다. 도구 원문과 모델 메시지는 저장하지 않는다.

## 모델 지원 검증 기록

`config/models.json`의 `supportsTools`는 운영자의 선언이다. 진입에는 같은 구성으로 실제 호출을
확인한 기록이 함께 필요하다.

```bash
assistant_web/.venv/bin/python assistant_web/scripts/agent_tool_probe.py --model-id gpt-6-luna
assistant_web/.venv/bin/python assistant_web/scripts/agent_tool_probe.py --model-id gemini-3.1-flash-lite
```

- 사내 원문 없이 가상의 과일 가격 도구, 합성 질문, 가짜 도구 결과만 보낸다.
- 결과는 커밋하지 않는 `runtime/agent_tool_verification.json`에 저장한다. 키·endpoint 주소는 기록하지
  않고 지문만 남긴다.
- 기록 항목: 검증일, 결과, 모델 ID·이름·provider, endpoint 지문, 구성 지문, 관측한 서빙 설정
  (`system_fingerprint`), 요청 옵션, 확인 항목별 결과, 오류.
- 다음 경우에는 재검증 전까지 진입하지 않는다.
  - 구성 지문(모델 이름·provider·전송 주소·think·추론 설정·출력 한도)이 달라진 경우
  - 기록이 `AGENT_TOOL_VERIFICATION_MAX_AGE_DAYS`(기본 30일)보다 오래된 경우
  - 실행 중 응답의 `system_fingerprint`가 기록과 다른 경우. 이때는 `reverificationRequired`로 표시한다.

## 별도 수정 항목(기존 경로, 이번 범위 밖)

아래는 기존 경로의 별도 검토 항목이다. 플래그 OFF에서는 기존 전송·폴백 규칙을 사용한다.

1. 회사 모델 답변 생성 실패 시 사내 근거가 외부 모델로 넘어갈 수 있다.
   회사 모델에 `fallbackModelIds`가 없어 `generate_model_response`가 활성 모델 전체로 폴백한다.
2. 생성 경로 API 응답의 `raw`에 공급자 원본 JSON(추론 필드 포함 가능)이 그대로 포함된다.
3. AB 비교가 클라이언트의 `abModelId`로 임의 등록 모델(외부 포함)에 근거를 보낸다.
4. `fetch_notion_page_content`는 읽기 범위를 다시 확인하지 않는다. 지금은 검색 결과 ID로만 호출되며,
   에이전트 도구는 원장 번호로만 연다.
5. 통합 경로의 both 검색은 Mantis와 Notion에 같은 검색어와 같은 조건을 적용한다.

### 일반 건수·목록·집계와 shadow 비교

`AGENT_MODE_ENABLED=true`이고 기존 모델 전송·도구 검증 정책을 통과하면 일반 요청에서 건수·목록·집계 도구를 사용한다. 별도의 shadow 문맥은 필요 없다. `--agent query-shadow`는 평가용 강제 진입 방식으로 유지한다. 변경 전 코드와 비교할 때는 같은 저장본을 복제한 별도 실행을 사용한다. 플래그를 끄면 기존 경로를 사용하며 모델·출처 정책과 마스킹은 유지한다.

- `count_mantis_issues`와 `list_mantis_issues`는 같은 실제 조건·정렬·표시 창·집계 기준이면 저장본 스캔을 공유한다. 조건이나 정렬·표시 창이 달라지면 별도로 조회한다. 전체 조회를 마친 경우에만 총건수를 제공하며 목록의 순번은 실제 표시한 ID 순서로 정한다. 원장의 답변용 건수·목록을 응답에 직접 반영한다.
- 일반 목록은 기존 표시 계약인 최대 200건을 보존한다. 모델에 전달하는 도구 결과가 길어 축약돼도 서버 원장과 최종 표시 목록은 보존한다. 문서 작성의 본문 읽기 상한 20건은 유지한다.
- “최신/최근 150건 기준”은 `population_limit=150`으로 검증한다. 기존 API 창 수집기가 응답 순서의 150건을 먼저 고른 뒤 필터를 적용한다. `limit`는 별도의 표시 개수다. 같은 요청의 건수·목록은 창을 재사용하며, 미완료는 `total_count=null`이다. 일반 검색이나 창 밖 ID의 상세 조회로 확대할 수 없다. 기간별 공수·다차원 집계와 보고서에 모집단 제한을 섞으면 지원하지 않는 조건으로 거부하며 전체 집계로 우회하지 않는다.
- `aggregate_mantis_issues`는 단순 그룹 건수와 기존 기간별 등록 건수·공수·전월 비교·상위 그룹/기타 집계를 제공한다. `query_contracts.aggregation`의 그룹·지표·기간·비교·상위 개수를 대조한 뒤 기존 엔진을 실행한다. 공수 전용 집계는 건수·목록 도구로 대신 계산하지 않는다. 등록 건수를 포함한 집계의 건수·목록에는 같은 등록일 기간을 적용한다.
- 집계 결과는 전체 저장본을 확인한 경우만 원장에 등록한다. 요청 단위 저장본 세대를 공유하며 표시한 목록을 집계 모집단으로 사용하지 않는다. 집계 설명은 기존 사실·숫자·부호·기간·그룹 검사와 독립 의미 검토를 유지하고 공통 모델 호출 예산에 포함한다. `MANTIS_AGGREGATION_MODE`는 에이전트 비대상의 기존 집계 경로 설정이다.
- 요청한 목록·집계 결과가 없는 상태에서 모델이 마치려 하면 한 번 더 도구 실행을 요청한다. 끝내 확보하지 못하면 미완료로 표시한다. 최종 `agent_query_result`와 `agent_aggregation_result` 대조 실패는 전달을 차단한다.
- 같은 질문 안에서 특정 순번의 관련 Notion 문서를 요청하면 해당 이슈의 실제 주제로 검색한다. 순번이 없으면 Notion 조회를 시작하지 않는다. 이슈에 적용한 조건을 문서에 적용할 수 없을 때는 별도의 기술 참고 자료로 표시한다. 가이드 본문을 확보하지 못하면 그 범위를 안내한다.
- 다음 턴에서 “그중 두 번째 이슈의 번호와 제목만”을 요청하면 같은 사용자의 감사 기록에 표시된 순번을 복원한다. 검증된 단건 계획의 ID가 일치할 때만 상세 도구로 해당 제목을 읽는다.
- “위 목록 2번”도 실제 표시 순번으로 복원한다. 상세 확인을 거쳤으면 서버가 보존한 목록의 감사 ID·A/B 변형을 사용한다. 없는 순번은 확인 질문으로 끝내며 범위를 넓혀 검색하지 않는다.
- 상세 계획의 `list_context`에는 이전 목록의 조건·정렬·표시 개수와 감사 출처를 분리해 보존한다. 상세 선택 ID를 목록의 필터로 승격하지 않는다. 후속 `prepare_query`의 `followup_context=list`는 이 목록 기준을, `current`는 현재 상세 대상을 사용한다. 건수·목록·집계로 돌아오는 후속은 목록 기준을 사용한다. 원래 목록에 명시한 ID 필터는 그대로 유지한다.
- 고객사 변경은 선택한 목록 기준에 기존 조건 근거 검증을 적용한다. 상태·기간·범위는 상속하고 새 고객사만 원문 근거로 교체한다. 독립 질문은 목록 연결을 끊는다. 과거 목록 조건과 순서는 현재 사실 근거가 아니므로 이슈와 수치는 다시 조회한다.
- 건수 계획의 `limit=null`은 전체 집계 범위에 표시 제한을 적용하지 않는다는 뜻이다. 함께 요청한 “최근 3건”의 표시 개수는 목록 도구 계약에서 별도로 복원하며, 기본 5건으로 덮어쓰지 않는다. 전체 건수·표시 ID·순서를 대조하는 최종 검증은 유지한다.
- 조건 인자 검증이 활성화된 경로에서는 모델이 본문 의미 검색·제목 검색·페이지 탐색·본문 읽기를 선택한다. 이전 호환 경로의 최대 3개 자동 대체 가이드 검색은 이 경로에서 실행하지 않는다. 실제 사용 절차를 읽은 경우만 `relatedReads`에 가이드로 남긴다. 열거한 이슈의 순서는 후속 질문에서도 유지한다.
- 관련 문서의 본문 읽기는 남은 조사 예산 안에서 실행한다. 구조화된 도구 경로는 선택 문서에 최대 90초를 허용해 `Retry-After` 대기 후 재시도할 수 있게 한다. 기존 호환 경로의 자동 대체 후보 검증은 합계 60초·문서당 25초를 유지한다. 복합 질문의 이슈 목록에는 상태·기간 누락 검사도 적용한다. 계획을 재해석할 때는 실패한 JSON과 검증 오류를 함께 전달한다.
- 감사의 `retrievalOutcome`은 원천 조회 결과이고 `stopReason`은 조사를 끝낸 이유다. `complete_empty`는 전체 조회 0건, `search_incomplete`는 일치 여부 미확정, `partial_evidence`는 복합 요청 중 일부만 확인한 경우다. 시간·호출 수 마감은 독립적으로 기록한다.

### 결정형 보고서 도구와 내부 모델 호출

- `build_issue_report`는 기존 공수·주간·월간 외에 고객사 프로필, 처리시간, 공수/처리시간 결합, 유사 사례,
  초동 대응, 우선순위·장기 미종료·기한·과거 대비·완료·회신 대기·고객사 현황, 월별 교차표·급증을 처리한다.
  계산기는 재사용하고 `query_contracts.mantis.report`의 `kind`, `effort`, `options`를 도구 인자와 대조한다.
- 조회 조건을 계산기 내부에서 다시 해석해 삭제하지 않는다. 명시 등록 기간·고객사·상태·전사/팀 범위를 유지한다.
  우선순위·장기 미종료·기한 보고서는 이 범위와 미종료 상태의 교집합이다. 고객사 현황의 기간 생략은 최근 30일,
  공수의 기간 생략은 올해 전달일이며 서버 기본값임을 기록한다. 임의 기간으로 바꾼 인자는 거부한다.
- 기한은 고객사전달→개발완료→QC 완료 등의 목표일 중 우선순위가 앞선 유효 날짜를 사용한다.
  완료 실적일을 목표일로 쓰지 않으며 결측은 포함 여부 미확인이다. 등록 기간과 목표일 기간은 별도다.
  처리시간은 해결·종료 이슈의 등록일→최종수정일 **근사값**이며 날짜 결측·역전은 평균에서 제외한다.
  정확한 해결 시각이나 현재 상태만으로 과거 완료·회신 대기를 추정하지 않는다. 날짜 기준·결측 정책은 `options`에 노출한다.
- 유사 사례는 확인한 기준 ID 한 건을 읽고, ID 조건을 제외한 확정 조건에서 더 작은 ID의 과거 후보를 검색한다.
  기준 원문과 후보 원장을 분리하며 후보는 `reference`다. 초동 대응의 유사 사례는 플랫폼만 유지한 참고 범위다.
  top-k 결과 없음은 전체 부재가 아니며, 후보를 동일 원인이나 해당 고객사의 직접 근거로 승격하지 않는다.
- 유사 보고서 내부의 사실 선택·요약 초안·독립 검토도 공통 `_request_turn`을 사용한다. 재시도·허용 대체 모델을
  포함해 모델 16회 예산과 사용량에 합산한다. 실패 시도의 사용량 미보고도 별도 기록한다.
  전송 허용 목록·마스킹·문맥 한도·서빙 변경·요청 취소와 최종 검증 예약은 유지한다.
  여러 하위 단계를 묶는 보고서 도구는 최종 검증 예약을 제외한 요청 조사 시간을 사용하고, 각 내부 모델의 짧은 마감은 유지한다.
- 보고서 내용과 기존 검증 모드를 최종 응답에 보존한다. 공수 재계산·원문 조건·문장 독립 검토를 생략하지 않는다.
  보고서 실행 실패를 모델 자유 서술로 대체하지 않으며, 전체 0건·부분 자료·미조회/이력 부족을 감사 결과에서 구별한다.
  `completed`, `comparison`, `waiting` 도구 연결은 이력 데이터 수집을 추가한 것이 아니다. 해당 자료가 없으면 미완료다.
- 실행 예산·상태 격리는 공통 실행기에 연결했다. 기본 실행은 순차이며 `AGENT_MAX_CONCURRENT_TOOLS=2`에서 아래 제한 병렬 계약을 적용한다.

구현·실측 기록은 [보고서 도구 확장 검증](../../docs/evaluations/2026-11-09-agent-report-expansion.md)을 따른다.

### 공통 보정 거래

- `backend/evidence/repair.py`는 정상 항목을 복사해 고정하고 실패 ID만 한 번 보정한다. 모델이 정상 항목·새 ID를 반환해도 채택하지 않는다. 호출 경로의 기존 검증기로 변경분을 재검증하고 조합 검사를 통과한 값만 `ExecutionBudget.publish`로 반영한다. 권한·정책 거절, 취소, 조건 불일치, 원문 부족은 재작성 대상이 아니다.
- 일반 설명의 인용·수치 오류는 실패 문장과 실제 확보한 본문을 보낸다. 제목만으로 ref를 고치지 않는다. 구조화된 수정분에 기존 인용·수치 검사와 별도의 의미 검토를 적용한다. 실패한 주장만 제외하며 기존 정상 문장은 보존한다. 문맥 한도를 넘는 원문을 잘라 검토를 생략하지 않고 보정을 보류한다.
- 업무 문서는 기존 원문·고객 안내·완료 수준 검사와 독립 검토를 유지한다. 같은 slot 안에 정상 문장과 실패 문장이 함께 있어도 정상 문장을 교체하지 않는다. 보정 대상 밖 slot은 기존처럼 무시한다. 대량 문서의 배치별 보정은 각 실패 항목에 한 번만 적용한다.
- 집계 설명은 서버 계산의 사실 ID·기간·그룹·단위를 고정한다. 수치 오류는 기존 계산 결과와 다시 대조하고 수정 문장만 독립 검토한다. 정상 설명과 서버 계산표를 보존하며, 남은 설명 실패는 미완료로 표시한다. 건수·목록·후속 순번·집계표는 보정 모델이 작성하지 않는다.
- Mantis 원문 인용 요약도 기존 수치·식별자·후속 정정 검사와 독립 검토를 유지하면서 실패 항목만 보정한다. 확보하지 못한 근거는 명시적인 미확인 항목으로 남기고 원문 인용 답변을 유지한다. 전체 요청의 필수 조건·총 길이·최종 조합 검증도 다시 적용한다.
- 보정·독립 검토·재시도·허용 대체 모델은 기존 요청 예산과 사용량에 포함된다. 보정+검토 2회가 남아 있을 때만 새 보정을 시작한다. 감사의 `agent.repairs`는 경로·실패 사유·보존/보정/미해결 ID·대상 밖 변경·결과를 기록하며 원문 전체나 모델 입출력 전문을 새로 저장하지 않는다. 최종 조건·수치·근거 검증 및 전송 차단 기준은 유지한다.

검증 기록: [공통 보정 통합](../../docs/evaluations/2026-11-09-agent-common-repair.md).

### 후속 질문의 서버 대화 맥락

- 승인된 에이전트 전송 정책이 활성화된 요청은 통합 플래너와 도구 실행 모델에 `conversation_context`를 전달한다. 동일 사용자·이전 질문·선택한 A/B 답변의 감사 기록만 읽으며 클라이언트가 보낸 답변이나 조건으로 요약을 만들지 않는다.
- 이전 질문, 적용 조건, 작업·정렬·표시 개수, 실제 결과 순서, 원문 발췌와 조회 완료 여부를 전달한다. 서버의 `conversation_parent` 연결만 따라 최근 3턴, JSON 기준 최대 8,000자를 사용한다. 연결 정보가 없는 과거 기록은 해당 턴만 사용할 수 있다. 원문 전체와 이전 답변 전문은 포함하지 않는다.
- 모델은 후속·독립 질문과 변경 조건을 판단하고 서버는 조건 근거를 검증한다. 독립 질문은 이전 조건을 상속하지 않으며 다음 턴의 맥락 연결도 새로 시작한다. 조건만 바꾼 목록에서 표시 개수를 임의로 바꾸면 계획 수정을 요청한다. 숫자나 전체 표시를 명시한 변경은 기존 표시 계약을 따른다.
- `followupSources`는 출처 표시 설정과 별개로 감사에 저장한다. 순번은 이 목록에서 복원하며 일반 참고 자료는 제외한다. B 답변은 B의 결과 순서를 사용한다. 전송이 차단된 답변의 후속 출처는 빈 목록으로 저장한다.
- 요약의 문자열을 마스킹하고 사용할 수 없는 원천의 발췌를 제외한다. 표시하지 않은 항목은 추측하지 않도록 생략 여부를 함께 전달한다. 과거 근거를 현재 요청의 근거 원장에 등록하지 않으므로 현재 수치·상태·사실은 도구로 다시 확인해야 한다. 조회 미완료의 0건은 확정 총건수로 전달하지 않는다.
- `tests/test_agent_conversation_context.py`는 사용자·질문·답변 선택, 크기 제한, 마스킹, 미완료, 독립 질문, 표시 개수 유지와 과거 인용 차단을 검사한다. 실제 모델 비교는 별도 런타임 복제본에서 수행한다.

### 도구 인자의 조건 검증

- 정책이 활성화된 에이전트 요청에서는 `prepare_query`로 검증한 질문의 필수 조건과 출력 요구를 `query_contracts`에 보관한다. 필터마다 현재 질문·이전 감사 기록·인증 사용자 중 근거 출처를 표시한다. 이후 모델이 도구 인자로 단계별 조건을 선택하고 서버가 실행 전에 검증한다.
- 일반 경로와 shadow의 `count_mantis_issues`, `list_mantis_issues`, `aggregate_mantis_issues` 첫 호출은 전체 `filters`와 `scope`를 명시한다. 목록의 `limit`은 확정된 표시 개수와 같아야 하며 `sort`를 명시하면 확정 정렬과 대조한다. 검증된 호출 결과의 `condition_ref`는 같은 요청·같은 원천에서만 재사용할 수 있다. 참조를 쓰는 호출에서는 필터·범위·정렬을 함께 보낼 수 없다. 집계 명세는 참조 사용 여부와 무관하게 대조한다.
- `purpose=answer`(기본)는 질문 전체의 건수·목록·집계에 사용한다. 원래 조건·정렬·표시 개수를 유지한다. `purpose=investigate`는 필요한 추가 조사를 위해 전체 `filters`와 `scope`를 명시하고 필수 조건에 AND 조건을 추가할 수 있다. 조사 정렬·표시 개수는 모델이 정한다. `condition_ref`는 요청·원천·용도·조건에 결속되어 추가 조사를 답변 전체 범위로 승격할 수 없다.
- 추가 필터는 현재 질문의 실제 `evidence` 구절 또는 이번 요청에서 확보한 `evidence_ref`로 검사한다. `M#ID`는 해당 이슈의 번호·제목·상태·화면번호·매체 구조화 필드의 같은 값(`equals/in`)만 증명한다. 집계가 반환한 `Q...` 참조는 실제 반환된 그룹 필드·값만 증명한다. 본문 지시나 임의 문자열, 과거 원문은 새 조건이나 권한을 증명하지 않는다. 사용자가 순번을 지정했다면 추가 ID는 원래 표시 목록의 해당 항목이어야 한다.
- 검색 도구에서 조건을 생략하면 질문의 필수 조건을 사용한다. `filters=[]`는 필터 해제 요청이므로 기존 필터가 있으면 거절한다. 필수 조건 누락·부정 방향 변경·범위 확대·근거 없는 추가 조건은 원천 조회와 캐시 접근 전에 `condition_mismatch`로 반환한다. 유효한 조건 계약이 없으면 `condition_context_unavailable`로 막는다. 상세 조회도 단계 조건을 적용하며 다른 조건에서 읽은 본문 캐시를 무조건 재사용하지 않는다.
- 고객사 별칭과 동등한 단일 값 `equals/in`, `not_equals/not_in`은 비교할 수 있지만 실제 조회에는 서버가 확정한 값을 쓴다. Notion으로 옮길 수 없는 Mantis 상태·기간 등의 조건과 `reference` 등급은 유지한다. 조회 완료 여부와 확정 총건수의 기존 계약도 그대로 적용한다.
- 활성화된 에이전트 정책의 일반 요청과 query-shadow는 `literal_plan` 정규식 지름길을 생략하고 모델의 구조화된 해석을 검증한다. 목록 도구에서 질문을 다시 정규식으로 읽어 표시 개수를 덮어쓰지 않는다. 날짜·상태·권한·조건 근거 검사와 순번의 서버 결속은 유지한다. 정책 비활성 경로의 리터럴 해석은 유지한다.
- 추가 조사 건수·목록·집계는 원장의 별도 항목으로 보관하며 원래 질문의 총건수·순서·집계를 대체하지 않는다. 추가 조사의 0건은 전체 질문의 0건 증명이 아니다. 기존 최종 수치·인용 검증을 유지하고 `agent_step_conditions` 검사로 각 단계의 조건 참조·원천·수치·완전성도 대조한다. 불일치하면 답변 전달을 막는다.
- 감사의 `conditionSteps`에는 각 단계의 적용 필터·용도·근거 출처·미적용 조건·완전성을 남긴다. 기존 마스킹을 적용하며 본문 전체는 추가하지 않는다. Notion 공통 참고 검색과 이후 본문 읽기·페이지 탐색에도 같은 조건과 `reference` 등급을 연결한다. `tests/test_tool_condition_arguments.py`와 `tests/test_agent_step_conditions.py`에서 조건 누락·조작·캐시 혼합·참조 승격·수치 변조·순번·부분 조회를 검사한다.
- 추가 조사는 필수 조건에 AND 조건을 더한다. 독립 범위의 비교는 아래의 별도 계약을 사용하며 조사 중 필수 조건을 해제하는 방식으로 구현하지 않는다. 집계 그룹·지표·기간·비교 기준도 검증된 요청 명세를 유지한다.

### 여러 조회 범위와 비교

- 모델은 `prepare_query.proposal`에 `comparison={axis, cohorts}`를 제안한다. 축은 `customer` 또는 `created_at`, 범위는 2~4개다. 각 cohort는 `value`와 질문의 정확한 원문 `evidence`를 갖는다. 고객사는 등록 별칭·질문에 언급된 전체 고객사 집합, 등록 기간은 기존 달력 계산으로 대조한다. 기간 구절 외의 공통 조건을 모델이 재작성해 제거할 수 없다.
- `filters`는 공통 조건, `comparison.cohorts`는 비교 축의 조건이다. 예를 들어 한투·KB 미해결 건수 비교는 공통 `status.mode=open`, `comparison.axis=customer`, 두 회사의 cohorts를 제출한다. 한투의 이번 달·지난달 비교는 공통 `customer=한투`, `status.mode=open`, 날짜 쌍의 cohorts를 제출한다. 각 범위에 기존 단일 계획·근거·인증·실행 조건 검증을 적용한다.
- 독립 범위 비교는 `operation=count/search/aggregate`, `aggregation=null`을 사용한다. 그룹별 건수는 최상위 `group_by`로 지정한다. 기존 `aggregation.period`·전월 대비 명세와 섞지 않는다. 보정 오류에는 실제로 수정해야 할 필드를 안내하며, `changes`에 없는 미해결·고객사 등은 유지한다. 비교 없는 일반 질문의 `comparison=null`은 생략과 같지만, 제안한 비교를 보정 중 null로 바꾸어 단일 조회로 우회할 수는 없다.
- 서버가 S1~S4와 범위별 조건 계약을 만들며, 모델이 기존 조회 도구의 `query_scope_id`를 선택한다. 첫 호출에는 그 범위의 전체 `filters`·`scope`를 명시하고 이후 같은 범위의 `condition_ref`를 재사용한다. 다른 범위의 조건·참조로 바꾸거나 범위를 생략하면 원천 조회 전에 거절한다. 조회 순서는 모델이 정한다.
- 원장과 감사의 `comparisonResults`·`conditionSteps`는 범위를 구분한다. 추가 조사 결과는 계속 `investigation_*`에 남으며 범위별 총건수를 덮어쓰지 못한다. 캐시는 실제 조건·정렬·표시 창·집계 기준으로 구분하고 요청 안에서 같은 저장본 세대를 사용한다.
- 최종 `agent_comparison_results`에는 범위별 조건·건수·목록·조회 완전성을 표시한다. 모든 범위가 완료되면 전체 일치 ID로 각 쌍의 차이(왼쪽−오른쪽), 단순 합계, 중복 제외 합계와 중복 집계분을 서버가 계산한다. 표시한 일부 목록이나 모델 초안의 수치를 계산 근거로 쓰지 않는다. 하나라도 미조회·미완료이거나 요청한 목록·집계가 없으면 차이와 합계는 미확정이다. 전체 조회를 마친 0건은 그대로 0건으로 표시한다.
- 범위별 기존 `agent_query_result`·`agent_aggregation_result`·`agent_step_conditions` 검사에 `agent_comparison_result`를 추가한다. 범위 계약, 전체 ID 집합, 저장 시각, 서버 계산과 응답을 대조하고 불일치하면 전달을 차단한다. 전송 허용 목록·마스킹·호출 및 시간 한도는 그대로다.
- 현재 범위는 Mantis 건수·목록·단일 그룹의 이슈 건수 집계다. 서로 다른 원천의 합계, 공수, 여러 비교 축, 조사 중 필수 조건 해제는 포함하지 않는다. 비교 다음 턴의 생략된 조건·순번을 여러 목록에서 하나로 합쳐 복원하지 않는다. 후속 조회는 이슈 번호 또는 고객사·기간·공통 조건을 명시해야 한다. 기존 단일 목록의 후속 질문은 유지한다.
- `tests/test_agent_multi_query.py`와 routing fixtures에서 누락·중복·기간·공통 상태, 교차 범위 참조, 겹치는 전체 ID, 0건·부분·미조회, 큰 목록, 그룹 집계, 숫자·저장 시각·조건 변조, 일반 질문 회귀 및 후속 경계를 확인한다. 실제 비교 기록은 `docs/evaluations/2026-11-06-agent-multi-query.md`에 정리한다.

### 호출별 상태 소유권·예산·취소

- 공용 `ToolContext.call_id`를 덮어쓰지 않는다. 실행 루프는 `for_call(call_id)`로 호출을 구분하고, `ToolRegistry` 진입 시 확정 상태의 독립 사본을 만든다. 원장·Notion 참조·조건 참조·조회 저장본·중복 호출 기록·본문 재사용 캐시·조건 준비 상태는 이 사본에서만 변경한다.
- `PendingCall.publish`가 요청 소유자의 유일한 도구 결과 반영 지점이다. 호출 시작 때 읽은 원장 버전과 현재 버전을 대조하고, 같은 잠금 안에서 취소/마감을 확인한 뒤 확정 원장에 반영한다. 버전이 달라졌으면 `state_conflict`를 반환하고 결과를 버린다. 반영 후에도 작업 사본과 확정 상태가 객체를 공유하지 않는다.
- 도구 예외·단계 시간 초과 시 실행 직전 상태로 되돌린다. 실패한 실행이 만든 완전 조회 표시·캐시·계획을 확정하지 않는다. Notion 본문/연결 페이지 실패 시 기존의 본문 철회·미완료 표시·재시도 정책은 유지한다. 정상적으로 반환한 접근 철회 결과는 확정 상태에 반영해 이전 근거를 계속 사용하지 못하게 한다.
- 조건 준비의 `PlanningSession`도 호출 지역 상태로 처리한다. 준비 호출이 시간을 넘기거나 취소되면 외부 세션에 계획을 남기지 않는다. 정상 반환 후 반영된 세션만 다음 보정이나 실행 계획으로 사용한다. 상태·고객사 등 기존 조건 검증과 부분 보정 규칙은 그대로다.
- 원장의 단계 조건은 호출 ID가 일치하는 단계에만 붙인다. 이미 존재하는 다른 호출의 근거에 조건·출처를 덧씌우지 않는다. 단계별 조건·수치·전체 조회 검증도 기존대로 수행한다.
- 모델/도구 예산 차감은 잠금 안에서 검사와 증가를 함께 수행한다. 조사 모델 호출은 같은 잠금에서 최종 예약 호출까지 확인한다. 기본 상한 16회와 기존 동적 예약 정책을 유지한다. 요청에 결속된 취소/마감과 현재 단계의 더 짧은 마감을 모두 확인한다.
- `ExecutionBudget.publish`는 취소와 상태 반영의 선후를 직렬화한다. `run_with_deadline`은 작업 시작뿐 아니라 반환 후에도 마감/취소를 확인해 체크포인트 없이 늦게 돌아온 성공값을 차단한다. 요청 취소는 대기 중인 Future도 취소하고, 실행 중인 작업은 공통 체크포인트에서 멈춘다.
- 기존 Mantis 페이지 작업자는 `submit_with_context`로 요청의 전송 정책·마감·취소 문맥을 상속한다. 제출 전, 작업 시작, 반환 후에 취소를 확인하며 요청이 모든 Future를 추적한다. 실행 중인 동기 HTTP를 강제로 종료하지는 않는다. 기존 연결 시간 제한을 유지하고 작업이 끝날 때까지 요청 슬롯을 보유하며 늦은 결과는 사용하지 않는다.
- Notion의 동일 연결 간 429 대기는 기존 `rate_state`와 GET/POST 공용 대기 구현을 유지한다. 평가기는 논리 도구 시도와 실제 모델/원천 HTTP 요청을 따로 측정한다. 목록→순번 상세 등의 의존 호출은 계속 순차 실행한다.

### 독립 읽기 도구의 제한 병렬 실행

- `AGENT_MAX_CONCURRENT_TOOLS` 기본값은 1이다. 2로 설정하면 모델이 같은 턴에 제안한 인접 호출 중 서버가 독립성을 확인한 두 개만 함께 실행한다. 모델의 복수 도구 호출 지원과 `AGENT_MAX_CALLS_PER_TURN` 상한도 계속 적용한다. 운영 전환·복귀는 이 설정으로 분리한다.
- 허용 범위는 저장본 건수·목록·집계, 이미 확인한 서로 다른 이슈 상세, 순번·가이드 복구 의존성이 없는 Notion과 Mantis 읽기 조합이다. 중복 호출, 신규 조건/근거 참조, 근거 필드 기반 추가 조사, 최근 N건 API 모집단, 계획 변경과 내부 모델 호출이 있는 보고서는 순차 처리한다. 두 Notion 호출은 참조 번호·본문 무효화·가이드 재탐색을 공유하므로 함께 실행하지 않는다.
- 작업자는 기준 상태의 사본에서 기존 조건·원천 권한·예산 검증을 모두 통과해야 한다. 요청 조정자가 호출 순서대로 변경분을 병합하고 `condition_steps.stage_indices`를 다시 매긴다. 기존 단계 수정이나 캐시 키가 충돌하면 해당 결과를 게시하지 않는다. 요청 외부에서 소유자 버전이 바뀌면 묶음 전체를 거절한다. 취소/마감 후에는 성공 결과도 게시하지 않는다.
- 요청 정책·취소·마감·저장본 문맥을 작업자에게 복사한다. 모델/도구 예산의 원자적 차감과 최종 검증 예약은 유지한다. Mantis 최초 요청 캐시는 잠금 안에서 고정하며 SQLite 검색 스트림은 기존 직렬 잠금을 유지한다. 따라서 병렬 허용이 실제 원천 조회의 속도 향상을 보장하지는 않는다.
- 감사 trace는 호출별 `executionGroup`, `concurrentTools`, 실제 실행 `elapsedMs`를 기록한다. 평가기는 병렬 호출도 논리적 시도로 세고 게시된 본문만 근거 읽기로 기록한다. `parallelGroups`, `maxConcurrentTools`와 HTTP 요청·재시도·사용량을 별도로 비교한다. 미확인 금액·본문 관련성은 기존처럼 미확인으로 남긴다.

실측 및 회귀 기록은 [호출 상태·예산·취소 비교](../../docs/evaluations/2026-11-09-agent-call-ownership.md)에 정리한다.

### 평가 기준선과 운영 전환

전달 성공·항목별 완료·현재 본문·직접 관련성을 구분하는 채점과 실제 호출/사용량/지연 계측은 [평가 기준](AGENT_EVALUATION.md)을 따른다. 확인 질문은 요청 완료로 세지 않으며 사용량·단가 미확인은 비용 0으로 처리하지 않는다. 기능별 운영 확대와 기존 경로 제거는 문서의 최소 표본·관찰 기간·정확도·완료율·지연·비용 기준을 통과한 뒤 진행한다.

### Notion 본문 의미 검색과 페이지 탐색

- `NOTION_SEMANTIC_SEARCH_ENABLED=true`가 기본이다. `notion_body_index.sqlite3`에 수집된 본문을 1,200자 구간(200자 중첩)으로 나누고, 기존 loopback Ollama의 `CHROMA_EMBEDDING_MODEL`(기본 `bge-m3:latest`)로 임베딩한다. 원격 임베딩 주소와 HTTP 리디렉션은 거절한다. 인증정보·개인정보는 기존 마스킹을 적용하며 `Pass:` 형식도 가린다.
- `runtime/notion_semantic.sqlite3`의 벡터는 연결 지문·모델/구간 버전·본문 해시로 구분한다. 수정된 구간만 재임베딩하며 삭제·소속 변경도 반영한다. 첫 구축은 저장소 루트에서 `assistant_web/.venv/bin/python assistant_web/scripts/sync_notion_semantic_index.py --max-chunks 10000 --max-seconds 900`으로 실행한다. 서버 캐시 갱신 주기에는 최대 256구간·30초만 갱신한다. 새 본문 수집은 기존 `sync_notion_body_index.py` 유지보수를 사용하며, 검색에서 읽은 현재 본문도 다음 증분 갱신에 반영된다.
- 현재 읽기 범위 안에서 벡터 후보와 제목·본문 키워드 후보의 순위를 결합한다. 본문 미수집 문서도 제목으로 후보가 된다. 저장된 고객사·매체는 순서 결정용이며 현재 API의 접근·소속·전체 속성으로 재검증한다. 한 검색에서 최대 10후보·60요청·90초와 남은 요청 예산을 적용한다. 설명 경로의 제목 탐색은 후보 조회만 하고 240개 DB의 실시간 전수 검색으로 확대하지 않는다. 정확 제목·건수·목록의 기존 완전성 경로는 유지한다.
- 후보 검색은 모든 후보의 본문을 읽지 않는다. `candidate_hint`는 마스킹한 저장본 힌트이고, 후보는 최종 근거·인용 목록에서 제외한다. 모델이 `get_notion_page_content`를 선택하면 현재 본문을 읽어 근거로 승격한다. 같은 요청에서 확인한 후보·본문은 조건을 대조한 뒤 재사용한다. 의미 검색은 항상 `search_complete=false`, `coverage=top_k`다. 색인 미준비·임베딩 장애·빈 후보는 전체 부재가 아니다.
- 진행상황 문서에서도 해당 기능의 독립된 구간에 구체적인 설정·변환·저장 절차와 파일/API가 함께 있으면 본문 절차 후보로 올린다. 다른 기능의 구간과 예정·요청만 있는 기록은 제외한다. `procedure_candidate`와 `unread_procedure_refs`는 다음 본문 읽기를 위한 저장본 힌트이며 가이드 검증 결과가 아니다. 선택된 이슈가 있으면 그 기능명이 없는 절차 힌트를 제외한다. 실제 가이드 판정은 현재 본문을 읽은 뒤에만 한다.
- 링크는 탐색 힌트일 뿐 접근 권한이 아니다. 현재 문서의 자식·Notion 링크·page mention·관계형 속성에서만 대상을 찾으며, 이동·삭제·허용 DB 밖·조건 불일치 대상은 제외한다. 최대 20개 링크를 확인해 5개를 반환한다. 관계 속성의 일부·순환·시간 한도 등으로 전체 그래프 완전성은 주장하지 않는다. 다른 페이지 본문을 부모 근거로 합치지 않는다.
- 현재 속성에서 확인한 링크는 부모 본문 전체를 먼저 읽지 않고 따라갈 수 있다. 대상 페이지의 현재 접근·소속·조건 검증은 그대로 수행한다. 관측된 링크의 조회 실패·범위 미확인은 `unavailable_link_count`와 `incomplete_reasons`에 남긴다. 본문 읽기 실패 시 이전 본문·발췌·확인 표시를 원장에서 내리며, 다른 근거가 있어도 요청한 본문이 미완료이면 `partial_evidence`다. 남은 시간·요청 한도 또는 예산보다 긴 `Retry-After`는 즉시 재시도 가능한 장애로 표시하지 않는다.
- 본문 읽기 실패가 원장에 남아 있으면 서버가 최종 답변에 문서명과 미완료 사유를 붙인다. 모델이 이 설명을 빠뜨려도 부분 조회가 완료처럼 보이지 않게 한다. 다시 읽어 성공하면 실패 표시를 지우며, 단순히 아직 선택하지 않은 검색 후보에는 실패 안내를 붙이지 않는다.
- 검색 점수나 제목이 맞아도 가이드로 확정하지 않는다. 현재 본문에서 해당 기능의 절차를 확보한 경우만 `related_guide_verified=true`다. 모델이 `reference_scope=common`을 명시하면 목록에서 선택한 이슈의 기능에 한해 고객사 조건을 적용하지 않은 공통 참고자료를 찾을 수 있다. 순번·기능 근거가 없거나 Notion 단독 조건인 경우에는 거부한다. 고객사 미적용을 검색·본문·연결 페이지에 표시하고 `reference` 등급을 유지한다. 이슈 건수·목록 조건과 다른 문서 조건은 변경하지 않는다.
- 복합 질문의 최종 참고자료 목록에도 문서별 미적용 조건을 표시한다. 다른 고객사의 같은 기능 절차를 읽었더라도 대상 이슈의 실제 원인·조치·완료 근거로 바꾸지 않는다.
- Notion 설명 질문의 기능·주제를 임의로 `title equals` 조건으로 만들면 계획을 거절하고 모델이 고치게 한다. 인용한 제목·명시한 제목 조건·이전 대화에서 검증된 제목 조건은 보존한다. 예를 들어 “조건검색 서버 문서에서 접속 방법을 설명”은 실제 문서 제목을 단정하지 않고 검색 주제로 처리한다.
- 기본 모델·도구 상한은 각각 16회(환경변수로 최대 20회), 요청 한도는 180초다. 검증된 건수·목록 원장이 생기면 최종 모델 예약 호출 2회를 돌려주고 최종 처리 예약 시간을 5초로 줄인다. 일반 설명에서는 비어 있지 않은 현재 본문을 모든 조건이 적용된 근거로 완전하게 읽었을 때 예약 시간을 45초에서 15초로 줄여 연결 페이지 읽기에 돌려준다. 인용 검증 예약 호출 2회는 유지하며 최종 검증 예산이 모자라면 기존의 검증된 근거 전용 답변으로 제한한다. 후보·미완료·참고 등급만 있을 때는 예약 시간을 줄이지 않는다. 각 도구 결과에 남은 조사 시간·호출 수를 전달한다.
- 제목 POST와 본문·속성 GET은 같은 `Retry-After` 상태를 쓴다. `429`·`529` 대기는 마지막 재시도 뒤에도 유지한다. `NOTION_SHARED_RATE_LIMIT_ENABLED=true`가 기본값이며 같은 호스트의 동일 연결은 사용자 전용 임시 디렉터리의 잠금 파일로 요청 간격과 대기를 공유한다. 키 원문은 저장하지 않는다. 여러 호스트나 수정 전 프로세스는 이 상태를 공유하지 않는다. 일시 실패는 ref를 유지하되 이전 본문을 근거에서 제외하고 재시도를 허용한다. 삭제·접근 거부·소속 이탈은 계속 철회한다.
