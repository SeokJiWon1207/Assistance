# Notion 본문 색인 구현·검증 계획

목표는 제목 조건 없이 오래된 페이지와 뒤쪽 본문·표·코드에서 후보를 찾는 것이다.
현재 요청마다 최근 30페이지의 앞 20블록을 읽는 방식만으로는 이를 보장할 수 없다.

1. SQLite에 연결 식별값, 페이지 메타데이터, 소유 페이지·유형을 보존한 블록을 저장한다.
   설정된 읽기 범위의 DB를 직접 열거하며 빈 제목도 포함한다. 본문 원문은 runtime에만 둔다.
2. 동기화는 재개 가능하게 만들고 DB 목록을 끝까지 읽은 경우에만 삭제를 반영한다.
   페이지 본문 교체는 트랜잭션으로 처리한다. 수정·오류·미지원 하위 페이지는 완전 수집으로 표시하지 않는다.
3. 양성 본문 검색과 일반 키워드 검색은 색인 후보를 현재 API로 재검증한 뒤 유형·소유자·기존 속성 조건을 적용한다.
   삭제·권한 철회·범위 이동과 변경된 본문을 제외한다. 색인 스냅샷을 실시간 전체 건수로 확정하지 않는다.
   현재 검색과 색인 결과를 병합하고 제목 우선순위를 유지한다. 부정 조건만 있는 검색은 기존 경로를 유지한다.
4. 저장·갱신·검색 회귀를 먼저 실패시킨 뒤 수정하고 전체 테스트, Ruff, mypy를 실행한다.
5. 실제 API에서 DB 단위로 독립 수집한 색인을 만들고 이전 본문/표/코드 정답 9개를 제목 없이 재검증한다.
   검증 정답 문서만 색인에 주입하지 않는다. 전수 색인 진행률과 검증 표본의 적중률을 분리해 보고한다.

Notion 원문 변경이나 배포는 수행하지 않는다. 최초 제목 목록에 14,208개 페이지가 있으므로
최초 수집 완료 전에는 검색 범위를 부분으로 표시한다. 수집 명령·재개 방법은 README에 남긴다.

완료 판정 규칙 변경 시 본문별 `content_policies.version`을 함께 기록한다.
버전이 없거나 현재 `CONTENT_POLICY_VERSION`과 다르면 본문 후보는 보존하되 완료 통계에서 제외하고
재수집 대상으로 반환한다. 읽기만으로 기존 SQLite를 마이그레이션하지 않으며, 실제 본문 갱신
트랜잭션에서 버전을 기록한다. DB 목록 갱신만으로 본문 검증 버전을 올려서는 안 된다.
미지원 블록을 놓치던 이전 수집의 완료 판정은 전체 페이지를 최신 규칙으로 재검증해야 한다.
